> **Цел на урока:** да разбереш какво точно разрешава `unsafe`, да извикаш функция от библиотека на C и да я скриеш зад безопасен интерфейс.

## Какво ще научиш
- кои пет неща отключва `unsafe` и кои правила остават в сила;
- как работят суровите указатели и защо `*p` се нуждае от `unsafe` блок;
- как да декларираш и извикаш функция от C с `extern "C"`, `#[repr(C)]`, `CString` и `CStr`;
- как да компилираш C библиотека с `gcc` и да я свържеш с Rust, с `build.rs` или с аргументи на `rustc`;
- как да пишеш безопасна обвивка и да я проверяваш за изтичане на памет.

## Какво отключва unsafe
Безопасният Rust ти дава силни гаранции, но някои неща компилаторът не може да докаже: четене от суров указател, разговор със C, хардуерни регистри. За тях има ключова дума `unsafe`. Тя не изключва проверките, а само разрешава пет конкретни операции:

1. дереференциране на суров указател (`*const T`, `*mut T`);
2. извикване на `unsafe` функция, включително на външна функция от C;
3. достъп до изменяема статична променлива (`static mut`);
4. имплементиране на `unsafe` черта (например `unsafe impl Send`);
5. достъп до полета на `union`.

Всичко останало, включително проверката за заемане, важи и вътре в блока. `unsafe` означава „аз, програмистът, поемам отговорността да спазя правилата на езика тук“. Ако ги нарушиш, поведението е недефинирано (undefined behavior): програмата може да работи, да се срине или да даде грешен резултат при друга компилация. Затова блоковете се пазят малки и се коментират с `// SAFETY:`: защо този конкретен код е допустим.

Ето пример за указател. Без блок компилаторът отказва:

```
error[E0133]: dereference of raw pointer is unsafe and requires unsafe block
 --> src/main.rs:4:20
  |
4 |     println!("{}", *p);
  |                    ^^ dereference of raw pointer
  = note: raw pointers may be null, dangling or unaligned; ...
```

Суровите указатели са като тези в C: може да са нулеви, висящи или неизравнени. Създаването им е безопасно (`&x as *const i32`), опасно е само четенето и писането през тях.

Класически случай за полезен `unsafe` е функция от стандартната библиотека, каквато е `split_at_mut`: тя дава две изменяеми парчета от един масив. Компилаторът не може да докаже, че не се застъпват, а ние можем:

```rust
fn раздели<'a>(s: &'a mut [i32], k: usize) -> (&'a mut [i32], &'a mut [i32]) {
    let len = s.len();
    let ptr = s.as_mut_ptr();
    assert!(k <= len);
    // SAFETY: двете парчета не се застъпват и лежат в s.
    unsafe {
        (
            std::slice::from_raw_parts_mut(ptr, k),
            std::slice::from_raw_parts_mut(ptr.add(k), len - k),
        )
    }
}
```

При `раздели(&mut v, 2)` върху `[1, 2, 3, 4, 5]` и промяна на първия елемент на двете парчета се получава `[10, 2, 30, 4, 5]`. Забележи `assert!`: проверката е в безопасната част, а `unsafe` е само там, където е нужно. Това е същността на модела: опасното ядро е малко и обвито в безопасен интерфейс.

## Свързване с C: библиотеката
Много от най-добрите библиотеки са написани на C. Rust може да ги ползва без допълнителен слой, защото и двата езика следват един и същ двоичен интерфейс (ABI) на платформата. Ще направим малка библиотека за смесване на цветове, подобна на тези във VJ софтуера.

Заглавният файл `mixer.h` описва интерфейса:

```c
typedef struct { double r, g, b; } Color;

double mixer_average(const double *data, size_t len);
Color  mixer_blend(Color a, Color b, double t);
char  *mixer_greeting(const char *name);   /* освобождава се с mixer_free_string */
void   mixer_free_string(char *s);
typedef void (*mixer_cb)(double value, void *user);
void   mixer_each(const double *data, size_t len, mixer_cb cb, void *user);
int    mixer_safe_div(double a, double b, double *out); /* 0 = успех, -1 = грешка */
```

Реализацията (`mixer.c`) е няколко десетки реда на C. Компилира се с предупреждения и се пакетира като статична библиотека:

```
gcc -Wall -Wextra -O2 -c csrc/mixer.c -o mixer.o
ar crs libmixer.a mixer.o
```

Без предупреждения. Връзката с Rust е на едно място: в Rust пишеш декларации, които съвпадат с тези в `.h`.

## Свързване с C: Rust страната
Декларациите стоят в блок `unsafe extern "C"` (от издание 2024 на езика `unsafe` пред `extern` е задължително; в по-стари издания пишеш просто `extern "C"`). Структурата, която се подава на C, трябва да има `#[repr(C)]`, за да се подреди в паметта като в C. Без него Rust може да смени реда на полетата.

```rust
use std::ffi::{c_char, c_void, CStr, CString};

#[repr(C)]
#[derive(Debug, Clone, Copy)]
struct Color { r: f64, g: f64, b: f64 }

type Cb = extern "C" fn(f64, *mut c_void);

unsafe extern "C" {
    fn mixer_average(data: *const f64, len: usize) -> f64;
    fn mixer_blend(a: Color, b: Color, t: f64) -> Color;
    fn mixer_greeting(name: *const c_char) -> *mut c_char;
    fn mixer_free_string(s: *mut c_char);
    fn mixer_each(data: *const f64, len: usize, cb: Cb, user: *mut c_void);
    fn mixer_safe_div(a: f64, b: f64, out: *mut f64) -> i32;
}
```

Типовете съответстват: `double` е `f64`, `size_t` е `usize`, `const char *` е `*const c_char`, `void *` е `*mut c_void`. Ако декларацията не съвпада с истинската функция, компилаторът не може да го разбере: грешката излиза като срив по време на изпълнение. Затова я пренаписвай внимателно от заглавния файл.

Ако извикаш такава функция без `unsafe`, получаваш `error[E0133]: call to unsafe function` с пояснение, че извикването изисква `unsafe` блок.

## Свързване: как да подадеш библиотеката на компилатора
Има два начина, и двата работят без интернет и без външни пакети.

**Начин 1: `build.rs`.** Cargo изпълнява този скрипт преди компилацията и чете от него специални редове:

```rust
use std::{env, path::PathBuf, process::Command};

fn main() {
    let out = PathBuf::from(env::var("OUT_DIR").unwrap());
    let obj = out.join("mixer.o");
    let lib = out.join("libmixer.a");

    let ok = Command::new("gcc")
        .args(["-Wall", "-Wextra", "-O2", "-c", "csrc/mixer.c", "-o"])
        .arg(&obj).status().expect("gcc не е намерен").success();
    assert!(ok, "gcc се провали");
    let ok = Command::new("ar").arg("crs").arg(&lib).arg(&obj).status().unwrap().success();
    assert!(ok, "ar се провали");

    println!("cargo:rustc-link-search=native={}", out.display());
    println!("cargo:rustc-link-lib=static=mixer");
    println!("cargo:rerun-if-changed=csrc/mixer.c");
}
```

`OUT_DIR` е папка за генерирани файлове. Двата реда `cargo:rustc-link-*` казват къде да търси и коя библиотека да вземе. Популярни пакети (crates) като `cc` улесняват това, но тук ползваме само стандартната библиотека.

**Начин 2: ръчно с `rustc`.** Без Cargo:

```
rustc --edition 2024 src/main.rs -L . -l static=mixer -o app
```

И двата начина дадоха еднакъв резултат при реално пускане. Със статична библиотека (`-l static=mixer`) кодът на C влиза в самия изпълним файл. Ако ползваш динамична (`.so`), трябва `-l dylib=mixer` и при пускане `LD_LIBRARY_PATH` да сочи папката, иначе `ldd` показва `libmixer.so => not found`. Статичното свързване е по-преносимо: получаваш един самодостатъчен файл.

## Безопасна обвивка
Сега скриваме `unsafe` зад нормални функции. Обвивката трябва да гарантира предусловията на C функцията, така че извикващият никога да не може да ги наруши.

```rust
fn average(data: &[f64]) -> f64 {
    // SAFETY: указателят и дължината идват от валидно парче.
    unsafe { mixer_average(data.as_ptr(), data.len()) }
}

fn greeting(name: &str) -> Result<String, std::ffi::NulError> {
    let c = CString::new(name)?;   // грешка, ако има вътрешен \0
    // SAFETY: c е валиден низ с нулев край; резултатът се освобождава с функцията на C.
    unsafe {
        let p = mixer_greeting(c.as_ptr());
        let s = CStr::from_ptr(p).to_string_lossy().into_owned();
        mixer_free_string(p);
        Ok(s)
    }
}

fn safe_div(a: f64, b: f64) -> Option<f64> {
    let mut out = 0.0;
    let код = unsafe { mixer_safe_div(a, b, &mut out) };
    (код == 0).then_some(out)
}
```

`CString` създава низ с нулев край, какъвто очаква C, и отказва, ако в него има нулев байт. `CStr` чете такъв низ обратно. Низът, върнат от C, е заделен там, затова го връщаме с `mixer_free_string`, а не с Rust: двата заделяча може да са различни. Кодът за грешка (0 или -1) се превръща в `Option`, а не в число, което някой може да забрави да провери.

Обратно извикване (callback) се пише като `extern "C" fn`. Потребителските данни пътуват през `void *`:

```rust
extern "C" fn събери(v: f64, user: *mut c_void) {
    let сума = unsafe { &mut *(user as *mut f64) };
    *сума += v;
}
```

Важно правило: паника не бива да излиза от такава функция към C. В съвременния Rust тя прекратява програмата, като съобщава `panic in a function that cannot unwind`, което е по-добре от недефинирано поведение, но все пак край.

Резултат от програма, която вика всичко от `main`:

```
average = 2.625
average(празно) = 0
Color { r: 0.75, g: 0.0, b: 0.25 }
Ok("Здравей, Рая!")
true
callback сума = 10.5
Some(0.25) None
```

(`true` е отговорът на въпроса дали името с вътрешен `\0` е отхвърлено.)

## Проверка за изтичане на памет
Valgrind работи и с Rust програми. При правилния код: `definitely lost: 0 bytes` и `ERROR SUMMARY: 0 errors`. Ако в обвивката закоментираш `mixer_free_string(p)`, компилаторът дори предупреждава `function mixer_free_string is never used`, а Valgrind показва:

```
26 bytes in 1 blocks are definitely lost in loss record 1 of 2
   by 0x1207EB: mixer_greeting (in .../target/debug/ffi)
ERROR SUMMARY: 1 errors from 1 contexts
```

Това е добра рутина: всеки нов FFI код пускай през Valgrind или през санитайзери като AddressSanitizer. Rust ти показва къде е заделено, но не може да знае, че C очаква освобождаване.

## Стъпка по стъпка
1. Опиши интерфейса в `.h` и реши кой е собственик на всяка памет.
2. Напиши декларациите в `unsafe extern "C"` и `#[repr(C)]` за структурите.
3. Компилирай C с `-Wall -Wextra` и свържи библиотеката чрез `build.rs`.
4. Обвий всяка функция в безопасна: проверки, `CString`/`CStr`, `Option`/`Result`.
5. Към всеки `unsafe` блок напиши `// SAFETY:`.
6. Пусни под Valgrind.

## Пример от практиката
Да кажем, че имаш стара библиотека на C за обработка на цветове във VJ инструмент и искаш новата ти програма на Rust да я ползва, без да я пренаписваш. Правиш обвивка само за три функции, които ти трябват: средно, смесване и поздрав. Останалият проект ползва `average(&[f64])` и `greeting(&str)` като обикновен Rust и никога не вижда указател. Ако по-късно подмениш C кода, променяш само обвивката.

## Чести грешки
- **Прекалено голям `unsafe` блок** – тогава не се вижда кое е опасното. Затваряй само един-два реда.
- **Декларация, която не съвпада с C** – грешен тип или брой аргументи води до срив без съобщение. Сверявай с `.h`.
- **Забравено `#[repr(C)]`** – структурата може да е подредена различно.
- **Освобождаване с неправилния заделяч** – памет от `malloc` се връща с `free`, а не с Rust.
- **Низ без нулев край** – подаването на `&str.as_ptr()` вместо `CString` дава четене след края.
- **`static mut` за брояч** – сочи към състезание за данни. Ползвай `AtomicU32` или `Mutex`.

## Упражнение
Добави към библиотеката функция на C `mixer_max(const double *data, size_t len, double *out)`, която връща 0 при успех и -1 при празен масив. Опиши я в Rust и напиши безопасна обвивка `max(data: &[f64]) -> Option<f64>`. Свържи я с `build.rs` и напиши два теста: с непразен и с празен масив.

Критерии:
- C кодът се компилира с `-Wall -Wextra` без предупреждения;
- всеки `unsafe` блок има `// SAFETY:` коментар;
- обвивката е безопасна функция без указатели в подписа;
- `cargo test` минава;
- програмата показва `0 errors` под Valgrind.

## Бърза справка

| C | Rust |
|---|---|
| `double`, `int` | `f64`, `i32` |
| `size_t` | `usize` |
| `const char *` | `*const c_char` (с `CString`) |
| `void *` | `*mut c_void` |
| `struct` | `#[repr(C)] struct` |
| указател на функция | `extern "C" fn(...)` |
| код за грешка | `Option` или `Result` в обвивката |

Нивото на C, нужно за този урок, е от курса `c-sistemno`, а как се виждат такива извиквания на ниво инструкции – в курса `reverse-engineering`.

## Обобщение
`unsafe` отключва пет операции и поставя върху теб отговорността за правилата, които компилаторът обикновено пази. FFI е най-честото му приложение: декларираш функциите на C, подаваш правилно подредени данни и опаковаш всичко в безопасен интерфейс. Малките блокове, коментарите `SAFETY` и проверката с Valgrind правят този код надежден.
