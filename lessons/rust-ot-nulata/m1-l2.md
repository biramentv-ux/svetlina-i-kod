> **Цел на урока:** да описваш общо поведение с трейтове, да пишеш код за много типове с генерици и да заместваш ръчните цикли с итератори.

## Какво ще научиш
- Как се дефинира и имплементира трейт, и какво е метод по подразбиране
- Как генериците с ограничения (`T: Trait`) работят и каква е разликата между `impl Trait` и `dyn Trait`
- Какво казват грешките `E0369`, `E0046` и `E0277`
- Как се ползват `map`, `filter`, `collect`, `sum` и колегите им
- Защо итераторите са мързеливи и как да напишеш свой

## Трейтове: общо поведение

Трейтът (trait) описва какво **може** да прави един тип, без да казва как е устроен. Най-близкото в други езици е интерфейсът. Да опишем фигури с площ:

```rust
trait Shape {
    fn area(&self) -> f64;
    fn name(&self) -> String;

    fn describe(&self) -> String {
        format!("{} с площ {:.2}", self.name(), self.area())
    }
}
```

`area` и `name` нямат тяло: всеки тип сам решава как. `describe` има **имплементация по подразбиране**, която ползва другите два. Типовете имплементират трейта в отделен блок:

```rust
struct Circle { r: f64 }
struct Rect { w: f64, h: f64 }

impl Shape for Circle {
    fn area(&self) -> f64 { std::f64::consts::PI * self.r * self.r }
    fn name(&self) -> String { String::from("кръг") }
}

impl Shape for Rect {
    fn area(&self) -> f64 { self.w * self.h }
    fn name(&self) -> String { String::from("правоъгълник") }
    fn describe(&self) -> String {
        format!("правоъгълник {}x{}", self.w, self.h)
    }
}
```

`Rect` презаписва `describe`, а `Circle` ползва версията по подразбиране. Ако забравиш задължителен метод, компилаторът казва точно кой:

```
error[E0046]: not all trait items implemented, missing: `name`
 --> src/main.rs:6:1
  |
3 |     fn name(&self) -> String;
  |     ------------------------- `name` from trait
...
6 | impl Shape for Sq {
  | ^^^^^^^^^^^^^^^^^ missing `name` in implementation
```

Трейтовете, които вече срещна, са същата идея: `Debug` и `Clone` от `derive`, `Display` и `Default` от предишните уроци, `Iterator` по-долу. Правило, което е добре да знаеш: имплементираш трейт за тип само ако поне единият от двата е твой (правило за сирачетата). Не можеш сам да имплементираш `Display` за `Vec`.

## Генерици с ограничения

Генерична функция работи с много типове. Опитай да напишеш `largest` без ограничение:

```rust
fn largest<T>(items: &[T]) -> &T {
    let mut best = &items[0];
    for it in items {
        if it > best { best = it; }
    }
    best
}
```

```
error[E0369]: binary operation `>` cannot be applied to type `&T`
 --> src/main.rs:4:15
  |
4 |         if it > best { best = it; }
  |            -- ^ ---- &T
  |
help: consider restricting type parameter `T` with trait `PartialOrd`
  |
1 | fn largest<T: std::cmp::PartialOrd>(items: &[T]) -> &T {
  |             ++++++++++++++++++++++
```

Компилаторът не знае нищо за `T`, затова не позволява сравнение. Поставяш **ограничение** (trait bound): „`T` е всеки тип, който умее да се сравнява“:

```rust
fn largest<T: PartialOrd + Copy>(items: &[T]) -> T {
    let mut best = items[0];
    for &it in items {
        if it > best { best = it; }
    }
    best
}

println!("{} {:.1} {}", largest(&[3, 9, 2]), largest(&[1.5, 0.2]), largest(&['a', 'я', 'k']));
// 9 1.5 я
```

Когато ограниченията станат много, ги изнасяш в `where`:

```rust
fn show_all<T>(items: &[T]) -> String where T: Display {
    items.iter().map(|x| x.to_string()).collect::<Vec<_>>().join(", ")
}
```

Генерични са и типовете. Структура `Pair<T>` може да има методи само за онези `T`, които отговарят на условие: `impl<T: PartialOrd + Display> Pair<T> { fn bigger(&self) -> &T { ... } }`.

И обратното – ако викаш функция с тип, който не имплементира нужния трейт, получаваш `E0277`:

```
error[E0277]: the trait bound `Sq: Shape` is not satisfied
 --> src/main.rs:4:33
  |
4 | fn main() { println!("{}", show(&Sq(2.0))); }
  |                            ---- ^^^^^^^^ unsatisfied trait bound
  |                            |
  |                            required by a bound introduced by this call
  |
help: the trait `Shape` is not implemented for `Sq`
```

Ограниченията живеят в подписа, така че читателят вижда какво изисква функцията, без да чете тялото ѝ.

## Статично и динамично: impl Trait и dyn Trait

Има два начина да приемеш „нещо, което е `Shape`“:

| Начин | Запис | Как работи | Кога |
|---|---|---|---|
| Статично | `fn f<T: Shape>(s: &T)` или `fn f(s: &impl Shape)` | компилаторът прави отделно копие на функцията за всеки тип (мономорфизация) | стандартният избор; няма разход по време на работа |
| Динамично | `Box<dyn Shape>` или `&dyn Shape` | едно копие на кода; методът се намира по таблица по време на работа | различни типове в една колекция |

Колекция от различни фигури изисква динамичния вариант, защото `Vec` държи елементи от един тип:

```rust
fn total_area(shapes: &[Box<dyn Shape>]) -> f64 {
    shapes.iter().map(|s| s.area()).sum()
}

let shapes: Vec<Box<dyn Shape>> =
    vec![Box::new(Circle { r: 1.5 }), Box::new(Rect { w: 3.0, h: 4.0 }), Box::new(Circle { r: 0.5 })];
```

```
кръг с площ 7.07
правоъгълник 3x4
кръг с площ 0.79
общо: 19.854
```

`Box` е собствена стойност в купчината, а `dyn Shape` означава „тип, известен само чрез трейта“. Не всеки трейт може да се ползва с `dyn` (например такъв с генерични методи), но за нашите случаи е достатъчно.

## Итератори

Итераторът е всичко, което имплементира трейта `Iterator` с метод `next()`, връщащ `Option<Item>`. Вместо цикли с индекси описваш **конвейер**:

```rust
let v = vec![1, 2, 3, 4, 5, 6];
let squares_of_even: Vec<i32> = v.iter().filter(|&&x| x % 2 == 0).map(|x| x * x).collect();
println!("{:?}", squares_of_even);       // [4, 16, 36]
let sum: i32 = v.iter().sum();            // 21
let any_big = v.iter().any(|&x| x > 5);   // true
let pos = v.iter().position(|&x| x == 4); // Some(3)
```

Делят се на два вида:

| Адаптери (връщат нов итератор) | Консуматори (връщат резултат) |
|---|---|
| `map`, `filter`, `enumerate`, `zip`, `skip`, `take`, `take_while` | `collect`, `sum`, `count`, `max`, `min`, `any`, `all`, `position`, `for_each` |

Забележи, че в `|&&x|` са нужни два амперсанда: `iter()` връща референции, а `filter` получава референция към тях. Ако това те обърква, използвай `.copied()` или `|x| *x % 2 == 0`. Компилаторът ще ти каже кога типът не пасва.

`collect` е особено полезен, защото строи различни колекции според типа, който искаш, и дори е умен за `Result`:

```rust
let r: Result<Vec<i32>, _> = ["1", "2", "x"].iter().map(|s| s.parse::<i32>()).collect();
// Err(ParseIntError { kind: InvalidDigit })
```

Ако всички са `Ok`, получаваш `Ok(Vec)`; при първата грешка спираш. Това е елегантният начин за „прочети всичко или се провали“ от предишния урок.

## Мързеливост и собствен итератор

Адаптерите **не вършат нищо**, докато няма консуматор:

```rust
let lazy = v.iter().map(|x| { println!("map {x}"); x * 2 });
println!("още нищо не е изпълнено");
let firsts: Vec<i32> = lazy.take(2).collect();
println!("{:?}", firsts);
```

```
още нищо не е изпълнено
map 1
map 2
[2, 4]
```

Само два елемента са обработени, защото `take(2)` не поиска повече. Ако забравиш консуматор, компилаторът предупреждава:

```
warning: unused `Map` that must be used
 = note: iterators are lazy and do nothing unless consumed
help: you might have meant to use `Iterator::for_each`
```

Свой итератор пишеш с един метод:

```rust
struct Countdown(u32);

impl Iterator for Countdown {
    type Item = u32;
    fn next(&mut self) -> Option<u32> {
        if self.0 == 0 { None } else { self.0 -= 1; Some(self.0 + 1) }
    }
}

println!("{:?}", Countdown(3).collect::<Vec<_>>()); // [3, 2, 1]
```

Получаваш безплатно всички адаптери: `Countdown(4).zip(Countdown(4).skip(1)).map(|(a, b)| a * b).sum()` дава 20 (4·3 + 3·2 + 2·1). Итераторите се компилират в обикновени цикли и в режим `--release` обикновено не отстъпват на ръчно написания код, но като при всяко твърдение за скорост, мери върху своя случай.

## Стъпка по стъпка
1. Реши какво общо поведение имат типовете и го запиши като трейт с минимален брой методи.
2. Имплементирай трейта за всеки тип; общата логика сложи като метод по подразбиране.
3. Пиши функциите с генерици и ограничения (`T: Shape`), а `Box<dyn Shape>` ползвай само за смесени колекции.
4. Замени цикъл, който събира резултат, с конвейер от адаптери и един консуматор.
5. При грешка за ограничение прочети `help:`: компилаторът обикновено предлага точния трейт.
6. Пусни `cargo build` без предупреждения.

## Пример от практиката

Да кажем, че твоят VJ инструмент има различни източници на кадри: видео клип, изображение и генериран шейдър. Описваш трейт `Layer` с методи `update(dt_ms)` и `opacity()`. Всеки източник го имплементира по свой начин. Сцената държи `Vec<Box<dyn Layer>>` и сборът на видимите слоеве се смята с итератор: `layers.iter().filter(|l| l.opacity() > 0.0).count()`. Като добавиш нов вид слой, не променяш нищо по сцената, само пишеш нова имплементация.

## Чести грешки
- **Генерична функция без ограничения** – `E0369`. Добави `T: PartialOrd` или съответния трейт.
- **Липсващ метод в `impl`** – `E0046`. Прочети кой метод липсва.
- **Адаптер без консуматор** – нищо не се изпълнява. Добави `collect`, `sum` или `for_each`.
- **`dyn Trait` навсякъде** – по-бавно и по-ограничено. Започни със `T: Trait`.
- **Объркване на `iter()`, `iter_mut()` и `into_iter()`** – заемане за четене, заемане за промяна, поглъщане. Избери според нуждата.
- **Пропуснато `Vec<_>` при `collect`** – компилаторът не знае какво да строи. Дай тип.

## Упражнение

Напиши трейт `Shape` за няколко фигури и пресметни общата площ с итератор.

1. Трейт `Shape` с `area` и `name`, и метод по подразбиране `describe`.
2. Поне три фигури (например кръг, правоъгълник, триъгълник).
3. Функция `total_area` над `&[Box<dyn Shape>]` с итератор.
4. Функция `largest_shape`, която връща името на най-голямата фигура (подсказка: `max_by` и `partial_cmp`).
5. Генерична функция с ограничение, например `print_area<T: Shape>(s: &T)`.
6. Тест, който проверява площите с допустима грешка (дробни числа не се сравняват с `==`).

Критерии: няма ръчни цикли за събиране; няма `unwrap` върху `partial_cmp` без обяснение; `cargo build` е без предупреждения; можеш да обясниш защо тук е нужен `dyn`, а `print_area` е статична.

## Бърза справка
- `trait Име { fn метод(&self); }`; `impl Име for Тип { ... }`
- Ограничения: `T: A + B`, `where T: A`, `&impl A`
- Статично: `T: Trait`; динамично: `Box<dyn Trait>`
- Адаптери: `map`, `filter`, `enumerate`, `zip`, `skip`, `take`
- Консуматори: `collect`, `sum`, `count`, `max`, `any`, `all`
- Итераторите са мързеливи; свой итератор = `impl Iterator` с `next()`

## Обобщение
Трейтът описва общо поведение, а генериците с ограничения пишат код за всички типове, които го имат. Статичният вариант е бърз и обичаен, а `dyn` се ползва, когато в една колекция живеят различни типове. Итераторите заместват цикли с конвейери от адаптери, които се изпълняват едва когато някой консуматор поиска резултат. Компилаторът ти казва кой трейт или метод липсва и често предлага точната поправка.
