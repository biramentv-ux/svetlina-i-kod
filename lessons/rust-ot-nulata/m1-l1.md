> **Цел на урока:** да обработваш грешките и липсващите стойности по начина на Rust, с `Result` и `Option`, да използваш оператора `?` и да направиш собствен тип грешка с ясни съобщения.

## Какво ще научиш
- Защо в Rust няма изключения и как `Result<T, E>` и `Option<T>` ги заместват
- Кога да ползваш `unwrap`, кога `match` и кога `?`
- Най-полезните методи: `map`, `unwrap_or`, `ok_or`, `map_err`, `ok`
- Как се пише собствен тип грешка с `Display` и `From`
- Как програма на Rust връща код за грешка от `main`

## Две грешки, два типа

Има две групи проблеми. **Невъзстановими** са грешките в самата програма (индекс извън масива, нарушено предположение). Тях Rust обработва с паника (`panic!`): програмата спира и казва къде. **Възстановими** са очакваните проблеми на средата: файл, който го няма, текст, който не е число, мрежа, която пада. Те се връщат като **стойности**:

```rust
enum Result<T, E> { Ok(T), Err(E) }
enum Option<T>    { Some(T), None }
```

И двете са обикновени `enum`, които вече познаваш от предишния урок. Разликата с изключенията е в това, че грешката е част от **подписа на функцията**. Който вика `fn read(path: &str) -> Result<String, io::Error>`, вижда от типа, че може да се провали, и компилаторът го принуждава да реши какво прави тогава. Няма скрит път за изход, който да изненада читателя.

Кога кое:

| Ситуация | Тип |
|---|---|
| Стойността може да липсва и това е нормално (търсене, първи елемент) | `Option<T>` |
| Операция може да се провали и има причина | `Result<T, E>` |
| Нарушено вътрешно предположение (баг) | `panic!` |

## Първи контакт: match и unwrap

Най-явният начин е `match`:

```rust
match "12x".parse::<i32>() {
    Ok(n) => println!("число {n}"),
    Err(e) => println!("не е число: {e}"),
}
```

Често се вижда и `.unwrap()`, което връща стойността от `Ok` или спира програмата. В кратка проба е приемливо, в истинска програма почти никога:

```rust
fn main() {
    let n: i32 = "abc".parse().unwrap();
    println!("{n}");
}
```

```
thread 'main' panicked at src/main.rs:2:32:
called `Result::unwrap()` on an `Err` value: ParseIntError { kind: InvalidDigit }
```

Съобщението е точно, но потребителят вижда паника, а не обяснение. (Ако в средата ти е включено `RUST_BACKTRACE`, ще се появи и дълъг списък с извиквания.) Две сродни функции са `.expect("съобщение")`, която добавя твой текст, и `.unwrap_or(стойност)`, която подава резервна стойност.

## Методи, които спестяват match

Ето малък набор, който покрива повечето ежедневни нужди. Изходите са от реално пускане:

```rust
let names = vec!["Ана", "Борис"];
println!("{:?} {:?}", names.get(1), names.get(5));      // Some("Борис") None
let third = names.get(5).copied().unwrap_or("няма");     // няма
let len = names.first().map(|s| s.chars().count());      // Some(3)
let r: Result<i32, _> = "12x".parse::<i32>();            // Err(ParseIntError { kind: InvalidDigit })
println!("{:?}", "7".parse::<i32>().ok());                // Some(7)
println!("{:?}", names.get(9).ok_or("липсва елемент"));   // Err("липсва елемент")
```

| Метод | Какво прави |
|---|---|
| `.map(f)` | прилага `f` към съдържанието, ако има такова |
| `.unwrap_or(x)` | стойността или резервна `x` |
| `.ok()` | превръща `Result` в `Option` и изхвърля грешката |
| `.ok_or(e)` | превръща `Option` в `Result` със зададена грешка |
| `.map_err(f)` | променя типа на грешката |
| `.and_then(f)` | свързва стъпки, всяка от които може да се провали |

Забележи, че `Option<i32>` не може да се събира с число. Опитът `x + 1` дава `E0369: cannot add {integer} to Option<i32>`. Първо решаваш какво правиш при липса.

## Операторът ?

Ако във всяка функция пишеш `match` за всяка грешка, кодът става тромав. Операторът `?` върху `Result` значи: „ако е `Ok`, извади стойността; ако е `Err`, веднага върни тази грешка от текущата функция“. Функцията ти трябва да връща съвместим тип.

```rust
fn average(path: &str) -> Result<f64, ReadError> {
    let nums = read_numbers(path)?;
    Ok(nums.iter().sum::<i64>() as f64 / nums.len() as f64)
}
```

`?` работи и върху `Option`: при `None` функцията връща `None`.

```rust
fn first_char_upper(s: &str) -> Option<char> {
    let c = s.chars().next()?;
    c.to_uppercase().next()
}
// first_char_upper("даа") -> Some('Д'), first_char_upper("") -> None
```

Ограничението е, че `?` може да се ползва само във функция, чийто тип на връщане е `Result` или `Option`. Забравиш ли го в `main`, получаваш:

```
error[E0277]: the `?` operator can only be used in a function that returns `Result` or `Option` (or another type that implements `FromResidual`)
 --> src/main.rs:3:46
  |
2 | fn main() {
  | --------- this function should return `Result` or `Option` to accept `?`
3 |     let t = fs::read_to_string("missing.txt")?;
  |                                              ^ cannot use the `?` operator in a function that returns `()`
  |
help: consider adding return type
  |
2 ~ fn main() -> Result<(), Box<dyn std::error::Error>> {
```

Подсказката е добра: `main` също може да връща `Result`. Тогава при `Err` програмата печата `Error: ...` и излиза с ненулев код (проверено: кодът е 1), което е точно каквото очакват скриптовете и `&&` в терминала:

```
Error: ParseIntError { kind: InvalidDigit }
```

`Box<dyn Error>` е „кутия с коя да е грешка“. Удобна е в малки програми, а в библиотеки се предпочита собствен тип. За `dyn` ще говорим при трейтовете.

## Собствен тип грешка

Нека четем файл с по едно число на ред. Какво може да се обърка? Файлът не се отваря, ред не е число или няма нито едно число. Това са три различни причини, затова `enum`:

```rust
use std::fmt;
use std::num::ParseIntError;

#[derive(Debug)]
enum ReadError {
    Io(std::io::Error),
    Parse { line: usize, source: ParseIntError },
    Empty,
}

impl fmt::Display for ReadError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            ReadError::Io(e) => write!(f, "грешка при четене: {e}"),
            ReadError::Parse { line, source } => write!(f, "ред {line}: невалидно число ({source})"),
            ReadError::Empty => write!(f, "файлът няма числа"),
        }
    }
}

impl std::error::Error for ReadError {}

impl From<std::io::Error> for ReadError {
    fn from(e: std::io::Error) -> Self { ReadError::Io(e) }
}
```

Три неща, които правят типа „добра грешка“:

- `Debug` (чрез `derive`) за програмиста и `Display` за потребителя. `Display` определя какво се вижда при `{e}`.
- `impl std::error::Error` – празен блок е достатъчен; така грешката се вписва в `Box<dyn Error>`.
- `impl From<io::Error>` – това е магията зад `?`: при `Err` операторът автоматично вика `From::from`, за да превърне грешката в типа на функцията. Така `fs::read_to_string(path)?` работи в функция, която връща `ReadError`.

Самата функция:

```rust
fn read_numbers(path: &str) -> Result<Vec<i64>, ReadError> {
    let text = fs::read_to_string(path)?;
    let mut out = Vec::new();
    for (i, line) in text.lines().enumerate() {
        let line = line.trim();
        if line.is_empty() { continue; }
        let n = line.parse::<i64>()
            .map_err(|e| ReadError::Parse { line: i + 1, source: e })?;
        out.push(n);
    }
    if out.is_empty() { return Err(ReadError::Empty); }
    Ok(out)
}
```

За реда с `parse` няма автоматично `From`, защото искаме да добавим номера на реда. Затова ползваме `map_err`. Като пуснем програмата върху три файла (един с числа 10, 20, 30; един с `abc` на третия ред; един липсващ), получаваме:

```
good.txt: средно 20.0
bad.txt: ред 3: невалидно число (invalid digit found in string)
missing.txt: грешка при четене: No such file or directory (os error 2)
```

Текстът на системната грешка идва от операционната система и може да е различен на твоята машина. Със `{:?}` същата грешка се показва за програмиста: `Err(Parse { line: 3, source: ParseIntError { kind: InvalidDigit } })`.

Външни пакети като `thiserror` и `anyhow` автоматизират този шаблон. Тук го пишем на ръка, за да видиш какво правят.

## Стъпка по стъпка
1. Реши за всяка функция: може ли да се провали, и ако да, по колко различни причини?
2. Ако е една, върни `Option` или `Result` със стандартна грешка. Ако са няколко, направи `enum` за грешките.
3. Имплементирай `Display` (за хората) и `Error`.
4. Добави `From` за грешките, които искаш да се превръщат автоматично.
5. Вътре във функциите разпространявай с `?`; ползвай `map_err`, когато добавяш контекст.
6. Само на най-горно ниво (`main`) реши какво се показва на потребителя и какъв е кодът за изход.

## Пример от практиката

Да кажем, че пишеш инструмент, който чете файл с времена на смяна на сцени (`12000`, `18500`, …) и подава на лайв сет списък с точки. Ако един ред е развален, не искаш инструментът да „гръмне“ с паника насред изпълнение. Връщаш `Err(ReadError::Parse { line: 7, .. })` и `main` печата „ред 7: невалидно число“. Техникът вижда кой ред да поправи, а програмата се връща с код 1, така че скриптът за подготовка на сета да спре, вместо да продължи с половин списък.

## Чести грешки
- **`unwrap()` на данни от потребител или от файл** – при първия лош вход програмата спира. Връщай `Result`.
- **`?` в `main`, която връща `()`** – `E0277`. Смени типа на `main`.
- **Загубена информация с `.ok()` или `_`** – не изхвърляй грешката, ако не си сигурен, че няма значение.
- **Едно голямо `String` вместо тип на грешката** – не можеш да различиш причините. Ползвай `enum`.
- **Паника за очаквани проблеми** – липсващ файл не е баг. Паника е за нарушени предположения.
- **Съобщения без контекст** – добавяй номер на ред, име на файл и т.н. с `map_err`.

## Упражнение

Напиши програма, която чете файл с числа (по едно на ред) и връща ясна грешка при невалиден ред.

1. Дефинирай `enum` с поне три варианта: проблем с файла, невалиден ред (с номер) и празен файл.
2. Имплементирай `Display`, `Error` и `From<io::Error>`.
3. Напиши `read_numbers` с `?` и `map_err`.
4. `main` да връща `Result` и да извежда средното, минимума и максимума.
5. Пробвай с три файла: правилен, с развален ред и несъществуващ.
6. Добави тест, който записва временен файл с развален ред и проверява, че получаваш `Parse` с правилния номер.

Критерии: няма `unwrap` и `expect` в основния код; съобщенията са на български и съдържат номера на реда; празните редове се пропускат; `cargo build` е без предупреждения; кодът за изход е ненулев при грешка.

## Бърза справка
- `Result<T, E>`: `Ok` или `Err`; `Option<T>`: `Some` или `None`
- `?` разпространява грешката или `None` и иска подходящ тип на връщане
- `unwrap_or`, `map`, `ok_or`, `map_err`, `ok` за бързи преобразувания
- Собствена грешка: `enum` + `Display` + `Error` + `From`
- `fn main() -> Result<(), Box<dyn Error>>` дава ненулев код при `Err`
- `panic!` само за бъгове

## Обобщение
В Rust грешките са обикновени стойности, видими в подписа на функцията. `Option` показва, че нещо може да липсва, а `Result` – че може да се провали с причина. Операторът `?` прави разпространението кратко, а `From` превръща грешките по пътя. Собственият `enum` за грешки с `Display` дава ясни съобщения. Паниката остава за случаите, в които програмата е сгрешила.
