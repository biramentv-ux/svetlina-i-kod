> **Цел на урока:** да опаковаш играта в един преносим HTML файл без външни зависимости и да измериш с числа колко гладко върви, вместо да гадаеш по очите си.

## Какво ще научиш
- Защо играта в един файл е по-надеждна за споделяне и какво се чупи при отваряне от файл
- Как да вградиш стилове и код с малък скрипт за сглобяване
- Как да измериш кадрите: средна стойност, 95-и персентил и най-бавен кадър
- Кои рисувания са скъпи и как се заменят със спрайтове, нарисувани веднъж
- Как да направиш платното рязко на екрани с висока плътност на пикселите

## Защо един файл
Файл с `.html` може да се прати по пощата, да се сложи на флашка или да се отвори с двоен клик. Няма папки, които да се загубят, и няма сървър за настройване. Когато даваш играта на приятел за тест, това е огромно предимство.

Цената е, че браузърът гледа на отворен от диска файл (адрес от вида `file://`) по-строго. В Chromium три неща се държат така:

```
[error] Access to script at 'file:///.../mod.js' from origin 'null' has been blocked by CORS policy: Cross origin requests are only supported for protocol schemes: chrome, chrome-untrusted, data, http, https.
[error] Fetch API cannot load file:///.../data.json. URL scheme "file" is not supported.
[log] fetch грешка: Failed to fetch
заглавие: тест | вграден модул: ok
```

Външен модул (`<script type="module" src="...">`) и `fetch()` към съседен файл са блокирани, а модул, вграден в страницата, работи. Други браузъри могат да се държат различно, затова правилото е простото: **всичко е в самия файл**. Данните за нивата са обект в кода, а не отделен JSON.

## Какво се вгражда и как
- **Стилове:** `<style>` вместо `<link>`.
- **Код:** `<script>` с кода вътре вместо `src`.
- **Картинки:** най-добре е изобщо да ги няма. Спрайтовете се рисуват с код при старта (долу). Ако наистина трябва файл, може да е `data:` адрес, но base64 е по-голям от оригинала: 3000 байта стават 4000 знака.
- **Звук:** синтезиран с Web Audio, както в предишния урок, без аудио файлове.

По време на работа е удобно да държиш `index.html`, `style.css` и `game.js` отделно. Малък скрипт ги слива в един файл. За него е нужен само Node.js:

```js
import { readFileSync, writeFileSync } from "node:fs";

let html = readFileSync("index.html", "utf8");
html = html.replace(/<link rel="stylesheet" href="(.+?)">/g,
  (_, f) => "<style>\n" + readFileSync(f, "utf8") + "</style>");
html = html.replace(/<script src="(.+?)"><\/script>/g,
  (_, f) => "<script>\n" + readFileSync(f, "utf8").replaceAll("</script", "<\\/script") + "</script>");
writeFileSync("igra.html", html);
console.log("igra.html: " + Buffer.byteLength(html) + " байта");
```

Забележи `replaceAll("</script", "<\\/script")`: ако в кода ти има текстът `</script`, браузърът би решил, че скриптът е свършил. Така го обезопасяваме.

Проверка, че нищо не е останало отвън: `grep -c -E 'src=|href=' igra.html` печата `0`.

## Измерване на кадрите
Усещането „върви гладко“ лъже. Измери. Кадърът на 60 Hz екран трае около 16,7 ms, така че всичко над това е пропуснат кадър. В играта измерителят пази интервалите между последните 300 извиквания на `requestAnimationFrame`:

```js
const meter = { last: 0, times: [], show: false };
function tick(now) {
  if (meter.last) { meter.times.push(now - meter.last); if (meter.times.length > 300) meter.times.shift(); }
  meter.last = now;
}
```

`tick(t)` се вика в началото на `frame`, а клавишът F включва малък надпис с fps и най-бавния кадър. Три числа са важни:
- **Средно** показва общата скорост.
- **95-и персентил** – 95% от кадрите са по-бързи от него. Показва какво е „лошо, но не най-лошо“ за играча.
- **Най-бавен кадър** – единичните „запъвания“, които средното скрива.

Скриптът за автоматично измерване пуска играта, чака шест секунди и чете `meter.times`. Нужен е Playwright (`npm install playwright` и сваляне на браузъра), а резултатите зависят от машината, затова ги приемай за ориентировъчни:

```js
import { chromium } from "playwright";
import { resolve } from "node:path";

const browser = await chromium.launch();
const page = await browser.newPage();
const errors = [];
page.on("pageerror", e => errors.push(e.message));
page.on("console", m => { if (m.type() === "error") errors.push(m.text()); });
await page.goto("file://" + resolve(process.argv[2]));
await page.keyboard.press("Enter");
await page.waitForTimeout(6000);                      // 1,2 s въведение + играта върви
const t = await page.evaluate(() => meter.times.slice());
t.sort((a, b) => a - b);
const avg = t.reduce((a, b) => a + b, 0) / t.length;
console.log("кадри:", t.length);
console.log("средно:", avg.toFixed(1), "ms (" + (1000 / avg).toFixed(0) + " fps)");
console.log("95-и персентил:", t[Math.floor(t.length * 0.95)].toFixed(1), "ms");
console.log("най-бавен:", t[t.length - 1].toFixed(1), "ms");
console.log("кадри над 20 ms:", t.filter(x => x > 20).length);
console.log("грешки:", errors.length ? errors.join("; ") : "няма");
await browser.close();
```

Реалният изход от тази среда (Chromium в headless режим):

```
igra.html: 7740 байта
кадри: 300
средно: 16.8 ms (60 fps)
95-и персентил: 16.7 ms
най-бавен: 33.3 ms
кадри над 20 ms: 2
грешки: няма
```

Файлът е под 8 KB и върви на 60 fps. Два бавни кадъра от 300 са в рамките на шума на машината; причината не е изследвана. При друго пускане същият файл показа средно 17,1 ms и най-бавен кадър 50,1 ms – разликите между пусканията са нормални, затова сравнявай само измервания, направени по един и същи начин.

## Скъпото рисуване
Най-често забавя играта рисуването, не логиката. Ето сравнение на три начина да се нарисуват 800 светещи топчета на кадър. Измерва се колко време тече рисуването, но има уловка: `ctx.fillRect()` само записва команда, а браузърът я изпълнява по-късно. Без принуда `shadowBlur` изглежда само 0,1 ms, което е измама. Затова след рисуването се вика `ctx.getImageData(0, 0, 1, 1)`, която принуждава браузъра да приключи:

```js
const a = performance.now();
modes[name]();                  // gradient, shadow или sprite
ctx.getImageData(0, 0, 1, 1);   // принуждава завършване на рисуването
cost.push(performance.now() - a);
```

Chromium предупреждава за многократни четения с `getImageData`. За теста е нормално, но в играта такова извикване не оставяш.

| Начин | Рисуване на кадър (медиана) | Интервал между кадрите |
|---|---|---|
| `createRadialGradient` за всяко топче | 16–20 ms | 16,7 ms |
| `shadowBlur` за всяко топче | 25–43 ms | 33–50 ms |
| `drawImage` от готов спрайт | 5–10 ms | 16,7 ms |

Числата са от две пускания в тази среда; редът е един и същ и в двете. Спрайтът е най-евтин, а `shadowBlur` е най-скъп и води до пропуснати кадри. Спрайтът се рисува веднъж:

```js
function makeSprite(size, draw) {
  const c = document.createElement("canvas");
  c.width = c.height = size;
  draw(c.getContext("2d"), size);
  return c;
}
```

В играта `starSprite` е готов при старта, а на всеки кадър само се вика `ctx.drawImage(starSprite, x - 16, y - 16)`.

Още навици срещу ненужна работа:
- Не създавай градиенти, шрифтове и обекти във всеки кадър, ако не се променят.
- Не слагай `shadowBlur` на много фигури; нарисувай сянката в спрайта.
- Премахвай обекти извън екрана. В „Звездопад“ `drops.filter(...)` прави нов масив на кадър, което е приемливо при десетки обекти, но не при хиляди; тогава вземи пул от обекти за повторна употреба.
- Статичният фон се рисува веднъж в отделно платно, а после се копира с `drawImage`.

## Рязко платно на всеки екран
На екран с плътност 2 платно 480 на 320 се разтяга и изглежда размазано. Решението е буферът да е по-голям от размера на екрана, а координатите на играта да останат същите:

```js
function fitCanvas() {
  const r = window.devicePixelRatio || 1;
  cv.width = W * r; cv.height = H * r;
  cv.style.width = W + "px"; cv.style.height = H + "px";
  ctx.setTransform(r, 0, 0, r, 0, 0);
}
```

Проверка с плътност 1 и 2: буферът става 480 на 320 и съответно 960 на 640, CSS размерът остава 480 на 320, а пикселът върху героя има цвят (95, 214, 200) и в двата случая, т.е. героят си е на мястото.

## Пример от практиката
Да кажем, че играта ти има 200 светещи частици и на твоя компютър върви гладко, но на телефона на приятел се запъва. Измерваш: най-бавният кадър е 60 ms. Откриваш, че всяка частица има `shadowBlur`. Рисуваш светещата частица веднъж в спрайт и вземаш `drawImage`. Най-бавният кадър пада, а ти знаеш това със сигурност, защото си мерил преди и след.

Скриптът за сглобяване е обикновена програма за Node.js; повече за нея има в курса „Node.js: сървър, API и бази данни“ (`node-api-bazi`).

## Чести грешки
- **Външен модул или `fetch` към файл** – работи през сървър, но не от диска. Вгради данните.
- **Измерване на едно пускане** – числата се менят. Пускай няколко пъти и гледай най-бавния кадър, а не само средното.
- **Измерване без принудително завършване** – `drawMs` изглежда прекрасен, но не показва реалното време.
- **Остава `getImageData` в кода на играта** – принуждава браузъра да чака и забавя всеки кадър.
- **Размазано платно** – забравена плътност на пикселите.

## Бърза справка
| Задача | Решение |
|---|---|
| Един файл | `<style>` и `<script>` вътре, без `src`/`href` |
| Проверка за външни | `grep -c -E 'src=\|href=' igra.html` дава `0` |
| Бюджет на кадър на 60 Hz | около 16,7 ms |
| Метрики | средно, 95-и персентил, най-бавен кадър |
| Светещо топче | спрайт с `drawImage`, не `shadowBlur` |
| Рязко платно | `devicePixelRatio` и `setTransform` |
