> **Цел на урока:** да построиш игрови цикъл с `requestAnimationFrame`, да мериш времето между кадрите и да движиш обекти със скорост, която не зависи от честотата на кадрите.

## Какво ще научиш
- Какво е игров цикъл и от какви стъпки се състои един кадър
- Как работи `requestAnimationFrame` и защо не се ползва `setInterval`
- Как делтата на времето прави движението еднакво на всеки компютър
- Как фиксираната стъпка с натрупване дава стабилна логика
- Как да разделиш обновяването (update) от рисуването (render)

## Какво е игров цикъл

Играта не е програма, която „изпълнява и приключва“. Тя е безкраен цикъл, който много пъти в секунда върши три неща:

1. **Вход** – чете какво прави играчът (в следващия урок).
2. **Обновяване** (update) – променя света: премества героя, проверява правила.
3. **Рисуване** (render) – изчиства платното и рисува света такъв, какъвто е сега.

Една такава обиколка е **кадър** (frame). Ако кадрите са 60 в секунда, окото вижда плавно движение. В браузъра цикълът не се пише с `while (true)`, защото това би заключило страницата и браузърът никога не би получил възможност да покаже нарисуваното. Вместо това играта казва на браузъра: „извикай ме пак преди следващото рисуване“.

## requestAnimationFrame

`requestAnimationFrame(функция)` подрежда функцията да се изпълни точно веднъж преди следващото рисуване на екрана. Браузърът ѝ подава един аргумент – време в милисекунди с дробна част (`DOMHighResTimeStamp`). Обикновено кадрите следват честотата на монитора, а когато страницата е в скрит раздел, браузърът обикновено спира да вика функцията и така не хаби батерията.

Функцията **не се повтаря сама**. Всеки кадър трябва да поиска следващия, като извика `requestAnimationFrame` в края си. Затова цикълът изглежда така:

```js
function frame(now) {
  // update + render
  requestAnimationFrame(frame);
}
requestAnimationFrame(frame);
```

`setInterval(f, 16)` изглежда подобен, но не е синхронизиран с екрана: кадрите могат да се рисуват двойно или да се пропускат, а в скрит раздел продължава да работи. За игри ползвай `requestAnimationFrame`.

## Делта на времето

Първият ученически опит е да се движи обектът на всеки кадър:

```js
ball.x += 5;      // 5 пиксела на кадър
```

Проблемът е, че броят на кадрите не е еднакъв. Монитор със 144 Hz ще изпълни тази линия 144 пъти в секунда, а бавен телефон – 30. Топката ще е пет пъти по-бърза на единия от тях.

Решението е да мериш времето. **Делтата** (`dt`) е времето в секунди от предишния кадър. Скоростта се задава в **пиксели за секунда**, а преместването е `скорост * dt`. Ето симулация в Node.js на топка със скорост 300 px/s през една секунда при три честоти:

```js
function naive(fps){ let x=0; for(let i=0;i<fps;i++) x+=5; return x; }
function withDt(fps){ let x=0; const dt=1/fps; for(let i=0;i<fps;i++) x+=300*dt; return x; }
for (const fps of [30,60,144])
  console.log(`${fps} кадъра/с  на кадър: ${naive(fps)} px   с делта: ${withDt(fps).toFixed(1)} px`);
```

```
30 кадъра/с  на кадър: 150 px   с делта: 300.0 px
60 кадъра/с  на кадър: 300 px   с делта: 300.0 px
144 кадъра/с  на кадър: 720 px   с делта: 300.0 px
```

Преместването „на кадър“ дава 150, 300 и 720 пиксела за една секунда. С делта всички дават 300. Това е правилото, което ще следваш през целия курс: **всичко, което се движи, се умножава по `dt`**.

### Две защити за делтата

Първо, `last` трябва да се инициализира с времето на първия кадър. Ако остане 0, първата делта е „времето от зареждането на страницата“, а не от предишния кадър:

```js
requestAnimationFrame((t) => { last = t; requestAnimationFrame(frame); });
```

Второ, **ограничи делтата отгоре**. Ако играчът смени раздела и се върне след минута, първата делта ще е 60 секунди и героят ще прелети през стените. Затова `dt = Math.min(dt, 0.25)` или подобна граница.

## Фиксирана стъпка

Делтата решава скоростта, но има друг проблем: логиката започва да зависи от случайните колебания на кадрите. Числените резултати (например височината на скок) зависят леко от размера на стъпката, а сблъсъците стават по-неточни при големи стъпки. Затова повечето игри обновяват логиката с **постоянна стъпка**, например 1/60 секунда, а рисуват колкото кадъра успеят.

Техниката се казва **натрупване** (accumulator). Всеки кадър добавяш изминалото време в „буркан“ и докато в него има поне една стъпка, изпълняваш `update(STEP)` и я изваждаш.

Още един принцип: `update` променя света, `render` само го чете. Така можеш да рисуваш по-често или по-рядко от логиката и двете да не си пречат.

Пример на цялата страница:

```html
<!doctype html>
<meta charset="utf-8">
<canvas id="c" width="480" height="270"></canvas>
<script>
const canvas = document.getElementById("c");
const ctx = canvas.getContext("2d");

const STEP = 1 / 60;          // една стъпка на логиката
const ball = { x: 40, y: 135, r: 14, vx: 300 };   // 300 px в секунда

let acc = 0;                  // натрупано, още неизиграно време
let last = 0;
let updates = 0, frames = 0;

function update(dt) {
  ball.x += ball.vx * dt;
  if (ball.x > canvas.width - ball.r) { ball.x = canvas.width - ball.r; ball.vx = -ball.vx; }
  if (ball.x < ball.r) { ball.x = ball.r; ball.vx = -ball.vx; }
  updates++;
}

function render() {
  ctx.fillStyle = "#0b1020";
  ctx.fillRect(0, 0, canvas.width, canvas.height);
  ctx.fillStyle = "#f97316";
  ctx.beginPath();
  ctx.arc(ball.x, ball.y, ball.r, 0, Math.PI * 2);
  ctx.fill();
  ctx.fillStyle = "#94a3b8";
  ctx.font = "14px monospace";
  ctx.fillText("x = " + ball.x.toFixed(1), 10, 20);
}

function frame(now) {
  const dt = Math.min((now - last) / 1000, 0.25);
  last = now;
  acc += dt;
  while (acc >= STEP) { update(STEP); acc -= STEP; }
  render();
  frames++;
  requestAnimationFrame(frame);
}

requestAnimationFrame((t) => { last = t; requestAnimationFrame(frame); });
</script>
```

Ограничението на `dt` пази и от „спирала на смъртта“: ако един кадър е много бавен, натрупаното време нараства, `while` изпълнява много стъпки, това бави още следващия кадър и така нататък. С горна граница цикълът не излиза извън контрол.

## Проверка в браузър

Заредих страницата в Chromium без грешки в конзолата. Измерих една секунда:

```
измерено за 1.005 с: кадри 60 обновявания 60 преместване 300.0
```

Шестдесет кадъра, шестдесет стъпки на логиката и точно 300 пиксела преместване. След това нарочно забавих `render` с 30 милисекунди заетост на кадър, за да симулирам слаб компютър:

```
бавни кадри: за 1.01 с кадри 33 обновявания 59 (очаквани ~ 61)
```

Кадрите паднаха до 33 в секунда, но логиката направи 59 стъпки – почти толкова, колкото при 60. Светът върви със същото темпо, само рисува по-рядко. Прочетох и пиксел в средата на кръга при `x = 190`: цветът беше `[249, 115, 22, 255]` (оранжев), а на фона `[11, 16, 32, 255]`.

Фиксираната стъпка проверих и без браузър, с проста симулация в Node.js:

```js
function fixed(frameTimes){ const STEP=1/60; let acc=0, x=0, updates=0;
  for(const dt of frameTimes){ acc+=Math.min(dt,0.25); while(acc>=STEP){ x+=300*STEP; acc-=STEP; updates++; } }
  return {x:+x.toFixed(2), updates}; }
console.log("144 Hz:", fixed(Array(144).fill(1/144)));
console.log("пауза от 5 с:", fixed([5]));
```

```
144 Hz: { x: 295, updates: 59 }
пауза от 5 с: { x: 75, updates: 15 }
```

Резултатите за четирите случая:

| Условие за една секунда | Изиграни стъпки | Положение |
|---|---|---|
| 60 кадъра по 1/60 с | 60 | 300 px |
| 30 кадъра по 1/30 с | 60 | 300 px |
| 144 кадъра по 1/144 с | 59 | 295 px |
| една пауза от 5 секунди (с таван 0,25 с) | 15 | 75 px |

При 144 кадъра последната стъпка не се събира в първата секунда заради закръгляне на дробните числа (останалото време остава в `acc` и се изиграва в следващия кадър). Паузата от 5 секунди е орязана до 0,25 секунди, затова логиката прескача напред само 15 стъпки.

## Стъпка по стъпка

1. Направи страница с платно и вземи контекста.
2. Опиши обекта с позиция и скорост в пиксели за секунда.
3. Напиши `update(dt)`, която променя позицията, и `render()`, която само рисува.
4. Напиши `frame(now)`: пресметни делта, ограничи я, извикай `update`, `render` и поискай следващия кадър.
5. Първият кадър подреди така, че `last` да е вярно число.
6. Опитай с различни скорости и сравни.

## Пример от практиката

Да кажем, че правиш игра, в която космически кораб прелита екрана за три секунди. Приятел я пуска на стар лаптоп и корабът едва пълзи. Без делта на времето трябва да ги направиш на две версии. С делта и скорост „160 пиксела в секунда“ корабът прелита за същото време и на двата компютъра; на стария просто има по-малко кадри.

## Чести грешки
- **Скорост „на кадър“** – движението зависи от честотата. Умножавай по `dt`.
- **`last` останало 0** – първата делта е огромна. Инициализирай `last` с първия кадър.
- **Липса на таван за `dt`** – след пауза героят „телепортира“. Ограничи делтата.
- **Две заявки в един кадър** – ако извикаш `requestAnimationFrame(frame)` два пъти, всеки кадър ражда две нови заявки. При опит страницата се заключи и броячът отчете 1 572 864 извиквания за около девет секунди.
- **Промяна на света в `render`** – обновяването и рисуването се смесват и всяка промяна става трудна. `render` само чете.
- **Забравено изчистване** – без `clearRect` или залят фон всеки кадър рисува върху предишния и остават следи.

## Упражнение

Направи страница с кръг, който се движи с постоянна скорост 240 px/s и се отблъсква от краищата на платното. Добави на екрана броячи за кадри и за обновявания в секунда.

Критерии:
- скоростта е в пиксели за секунда и се умножава по `dt`;
- `update` и `render` са отделни функции, `render` не променя света;
- делтата е ограничена;
- когато нарочно забавиш `render`, кръгът изминава същото разстояние за секунда;
- конзолата е без грешки.

## Бърза справка

| Понятие | Значение |
|---|---|
| `requestAnimationFrame(f)` | вика `f` преди следващото рисуване |
| `now` | време в милисекунди, подава се на `f` |
| `dt` | `(now - last) / 1000`, секунди |
| `Math.min(dt, 0.25)` | таван срещу големи скокове |
| `STEP = 1 / 60` | фиксирана стъпка на логиката |
| `acc` | натрупано, още неизиграно време |
| `update(dt)` | променя света |
| `render()` | само рисува |

## Обобщение
Игровият цикъл е кадър след кадър: вход, обновяване, рисуване. `requestAnimationFrame` го синхронизира с екрана. Делтата на времето прави скоростта еднаква на всеки компютър, а фиксираната стъпка с натрупване държи логиката стабилна. Таванът на делтата те пази от паузи и скокове. Разделяй `update` от `render` и ще бъде лесно да добавиш управление и сблъсъци.

## Бележки за видеото
- Цикъл с `requestAnimationFrame`, който движи квадрат по 3 пиксела на кадър.
- Преобразуване към скорост в пиксели за секунда с делтата на времето.
- Брояч, който след секунда показва в конзолата колко кадъра са минали.
- Покана да направиш свое движение с постоянна скорост.
