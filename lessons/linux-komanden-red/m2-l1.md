> **Цел на урока:** да разбереш разликата между образ и контейнер, да пускаш, влизаш в и изтриваш контейнери с Docker или Podman, да споделяш папка с хоста и да решаваш кога ти трябва цяла виртуална машина.

## Какво ще научиш
- Какво е образ, какво е контейнер и защо контейнерът е „за еднократна употреба“
- Основните команди: `run`, `ps`, `exec`, `stop`, `rm`, `images`
- Как се монтира папка от хоста (том) и какво става с правата на файловете
- Как да ограничиш контейнер: без мрежа, само за четене, с лимит на паметта
- Кога е нужна виртуална машина вместо контейнер

## Образ и контейнер

**Образът (image)** е неизменим шаблон: файловата система на една минимална Linux среда плюс настройки какво да се стартира. **Контейнерът** е работещо копие на образа: процес (или няколко), който вижда само своя файлов изглед, свои процеси и своя мрежа. Образът е като рецептата, контейнерът – като приготвеното ястие. От един образ може да направиш десет контейнера, а изтриването на контейнера не пипа образа.

Контейнерът не е малка виртуална машина. Той споделя **ядрото** на хоста, няма зареждане на операционна система, затова стартира за част от секундата. Изолацията идва от функции на ядрото (пространства от имена, cgroups), не от хардуерна симулация. Това обяснява и силните, и слабите му страни: бърз е и лек, но изолацията е по-слаба от тази на виртуалната машина, защото уязвимост в общото ядро засяга всички.

Двата най-разпространени инструмента са **Docker** и **Podman**. Командите им са почти еднакви: в повечето примери можеш да замениш `docker` с `podman`. Основната разлика е, че Podman няма постоянно работещ демон и лесно работи без root права (rootless). Във Windows ги ползваш през WSL 2.

## Какво е изпълнено тук и какво не

В средата, в която са пуснати примерите, имаше Docker (версия 29.9.2), но демонът трябваше да се стартира на ръка, а достъпът до публичния регистър на образи беше забранен. Затова **командите `docker pull` и всичко, което тегли образ от интернет, не са изпълнявани**. Вместо готов образ е използван миниатюрен собствен: `bash` и няколко команди със системните им библиотеки, пакетирани с `docker import`. Резултатът е образ `lab-mini:1` с размер около 7 MB. Podman не е инсталиран, затова за него няма изход. Командите с реални образи (като `python:3.12-slim`) са дадени според документацията и са отбелязани.

## Първият контейнер

```
$ docker run --rm lab-mini:1 bash -c 'echo "здравей от контейнера"; id; uname -sr'
здравей от контейнера
uid=0 gid=0 groups=0
Linux 6.18.44-fc-v726
```

Флагът `--rm` изтрива контейнера, щом приключи. Забележи два факта. Първо, вътре си `root` (uid 0) по подразбиране, но това е root на контейнера, а не пълен root на хоста; ще видиш защо ограниченията все пак са важни. Второ, `uname` показва същото ядро като на хоста: потвърждение, че ядрото се споделя.

Със стандартен образ командата изглежда така (не е изпълнявана тук, защото изисква теглене от регистъра):

```
docker run --rm python:3.12-slim python -c "print(2 + 2)"
```

При първо пускане Docker изтегля образа, после го ползва от локалния кеш. Етикетът след двоеточието (`3.12-slim`) е **таг**; фиксирай го, а не разчитай на `latest`, за да е лабораторията повторяема.

## Живот на контейнера: ps, exec, stop, rm

Фонов контейнер се пуска с `-d` (detached) и име с `--name`:

```
$ docker run -d --name lab2 --network none lab-mini:1 bash -c 'while true; do sleep 1; done'
$ docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
NAMES     IMAGE        STATUS
lab2      lab-mini:1   Up 1 second
$ docker exec lab2 bash -c 'echo exec-ok; ls /'
exec-ok
bin
dev
etc
```

`docker exec` пуска допълнителна команда в работещия контейнер; с `-it` получаваш интерактивна обвивка (`docker exec -it lab2 bash`). Спирането и триенето са отделни стъпки:

```
$ time (docker stop -t 2 lab2 >/dev/null)
real    0m2.152s
$ docker ps -a --format 'table {{.Names}}\t{{.Status}}'
NAMES     STATUS
lab2      Exited (137) Less than a second ago
$ docker rm lab2
```

Тук има поука за предишния урок за сигнали. `docker stop` праща SIGTERM и чака; ако процесът не спре в срока (`-t 2` секунди), праща SIGKILL. Кодът 137 е 128 + 9, т.е. процесът е бил убит със сигнал 9. Причината: в контейнера `bash` е процес номер 1, а ядрото не прилага на такъв процес стандартното действие по подразбиране за SIGTERM, ако той не е инсталирал обработчик. Програмите, които искат да спират чисто, трябва да обработват SIGTERM сами; често за това се ползва `docker run --init`.

## Томове: споделяне на папка с хоста

Файловата система на контейнера изчезва заедно с него. Данните, които искаш да останат, или файловете, до които достъпва хостът, се свързват с **том** (`-v хост:контейнер[:опции]`).

```
$ docker run --rm -v "$PWD/host-data:/work:ro" lab-mini:1 bash -c 'ls /work; cat /work/*.txt'
belezhka.txt
данни от хоста
$ docker run --rm -v "$PWD/host-data:/work:ro" lab-mini:1 bash -c 'echo x > /work/novo.txt'
bash: line 1: /work/novo.txt: Read-only file system
```

Опцията `:ro` прави папката само за четене: контейнерът вижда данните, но не може да ги променя. Това е добър избор за входни данни, които анализираш. Без `:ro` записът минава:

```
$ docker run --rm -v "$PWD/host-data:/work" lab-mini:1 bash -c 'echo "от контейнера" > /work/izhod.txt'
$ ls -ln host-data
-rw-r--r-- 0 0 belezhka.txt
-rw-r--r-- 0 0 izhod.txt
```

Файлът `izhod.txt` е с владелец uid 0. В тази среда и хостът работи като root, така че не се вижда разлика. На обикновен хост с Docker файловете, създадени от root в контейнера, ще са на root и после ще трябва `sudo`, за да ги изтриеш. Затова: пускай с `--user "$(id -u):$(id -g)"`, за да пише контейнерът с твоя uid. Пример от изпълнението с чужд uid и папка, която той не притежава:

```
$ docker run --rm --user 1000:1000 -v "$PWD/host-data:/work" lab-mini:1 bash -c 'id; echo x > /work/u.txt'
uid=1000 gid=1000 groups=1000
bash: line 1: /work/u.txt: Permission denied
```

(Забележи: `Permission denied`, защото папката е на uid 0 с права 755. Правата от първия урок важат и тук.) Освен т.нар. bind mount с път има и именувани томове (`docker volume create име`), които Docker управлява сам.

## Ограничаване: лабораторията не трябва да е врата

Когато разглеждаш недоверен код, контейнерът е първата ти преграда. Полезни ограничения:

| Цел | Опция | Ефект |
|---|---|---|
| Без мрежа | `--network none` | Остава само loopback интерфейс |
| Само за четене | `--read-only` | Коренната файлова система не се пише |
| Лимит на паметта | `-m 64m` | Горна граница за RAM |
| Лимит на процесите | `--pids-limit 50` | Спира „fork бомби“ |
| Ограничен процесор | `--cpus 0.5` | Половин ядро |
| Не root | `--user 1000:1000` | Намалени права вътре |
| Публикуване на порт само локално | `-p 127.0.0.1:8080:80` | Достъпен само от хоста |

Проверка на първите три от изпълнението:

```
$ docker run --rm --network none lab-mini:1 bash -c 'while read -r l; do echo "${l%%:*}"; done < /proc/net/dev'
lo
$ docker run --rm lab-mini:1 bash -c 'while read -r l; do echo "${l%%:*}"; done < /proc/net/dev'
lo
eth0
$ docker run --rm --read-only lab-mini:1 bash -c 'echo x > /tmp/f'
bash: line 1: /tmp/f: Read-only file system
$ docker run --rm -m 64m lab-mini:1 bash -c 'cat /sys/fs/cgroup/memory/memory.limit_in_bytes'
67108864
```

(Двата заглавни реда на `/proc/net/dev` са пропуснати.) Лимитът 67108864 е 64 MiB. Пътят до файла с лимита зависи от версията на cgroups (`memory.max` при v2).

Публикуването на портове (`-p`) не е изпълнявано, защото в минималния образ няма уеб сървър. Запомни само правилото: `-p 8080:80` публикува на всички интерфейси, а `-p 127.0.0.1:8080:80` – само локално. И още едно предупреждение: достъпът до Docker демона (членство в групата `docker`) практически е равен на root на хоста, защото чрез него можеш да монтираш всяка папка.

## Собствен образ с Dockerfile

Образ се описва с текстов файл. Минимален пример, изграден върху локалния образ:

```
FROM lab-mini:1
WORKDIR /work
COPY skript.sh /work/skript.sh
CMD ["bash", "/work/skript.sh"]
```

```
$ docker build -q -t lab-demo:1 .
sha256:5cf2d7a6bbea...
$ docker run --rm lab-demo:1
Здравей от образа, аз съм: 0
$ docker history lab-demo:1 --format '{{.CreatedBy}}' | head -3
CMD ["bash" "/work/skript.sh"]
COPY skript.sh /work/skript.sh # buildkit
WORKDIR /work
```

Всяка инструкция е слой. В реален проект началото е `FROM python:3.12-slim` (не е изпълнявано тук), а зависимостите се инсталират с `RUN pip install ...`.

## Кога ти трябва виртуална машина

Контейнерът е достатъчен, когато искаш изолирана среда за **Linux програма** със същото ядро. Виртуалната машина (ВМ) е нужна, когато:
- анализираш зловреден код, който може да атакува ядрото (силна изолация, снимки и връщане назад);
- ти трябва друго ядро или друга операционна система (Windows гост на Linux хост);
- тестваш драйвери, зареждане, мрежови настройки на ниско ниво.

Инструментите за ВМ са: KVM с QEMU и libvirt (виртуален мениджър `virt-manager`) под Linux, VirtualBox или VMware Workstation на повечето платформи, Hyper-V във Windows, Multipass за бързи Ubuntu машини. В тази среда няма `/dev/kvm`, затова ВМ не съм пускал и не показвам изход. За курса по reverse engineering (`reverse-engineering`) ВМ с изолирана мрежа е препоръчителната лаборатория; контейнерът е за по-безобидна работа като инструменти и скриптове.

## Стъпка по стъпка
1. Провери инструмента: `docker --version` или `podman --version`. Ако ползваш Docker, увери се, че демонът работи (`docker ps` не дава грешка).
2. Направи работна папка с входен файл и пусни контейнер с `-v "$PWD/данни:/work:ro"`, който го чете.
3. Опитай да пишеш в `:ro` папката и запиши грешката.
4. Пусни фонов контейнер с `--name` и `--network none`; влез с `docker exec -it`.
5. Спри го с `docker stop`, изтрий го с `docker rm` и провери с `docker ps -a`.
6. Напиши Dockerfile от три реда и го изгради.

## Пример от практиката
Да кажем, че имаш папка с подозрителни скриптове за преглед и не искаш да ги пускаш на основната си система. Пускаш Python образ със закрепен таг, монтираш папката `:ro`, добавяш `--network none` и `--pids-limit 100`. Скриптът не може нито да промени файловете ти, нито да се обади навън. След като приключиш, `--rm` е изтрил всичко. Но ако скриптът може да е насочен към самото ядро, правилният избор е ВМ, а не контейнер.

## Чести грешки
- **Данни само в контейнера** – с `--rm` или `docker rm` изчезват. Важното държи в том.
- **`latest` вместо фиксиран таг** – лабораторията „работи вчера“, а днес образът е друг.
- **Монтиране на `/` или на домашната папка без `:ro`** – контейнерът може да изтрие твои файлове.
- **`docker run --privileged` за удобство** – изключва повечето защити. Ползвай го само съзнателно.
- **Забравени спрени контейнери и образи** – заемат място; `docker system df` показва колко, а `docker system prune` чисти (прочети какво ще изтрие).
- **Парола или ключ в образа** – остават в слоевете. Подавай ги при пускане, не при изграждане.

## Упражнение
Направи „изхвърляема лаборатория“: Dockerfile (или готов образ по твой избор), от който пускаш контейнер с папка за четене `:ro`, папка за резултати с твоя uid, без мрежа и с лимит на паметта. Контейнерът прочита входен файл и записва резултат.

Проверка: (1) `docker ps -a` след края не показва остатъци; (2) резултатът е в папката на хоста и е твой; (3) опитът за запис във входната папка е отказан; (4) можеш да обясниш защо за изследване на зловреден код би избрал ВМ.

## Бърза справка
- `docker run --rm -it образ:таг команда` – еднократен контейнер
- `docker ps -a`, `docker images` – какво има
- `docker exec -it име bash` – вход в работещ
- `-v хост:контейнер:ro`, `--network none`, `--read-only`, `-m`, `--user`
- `docker stop`, `docker rm`, `docker rmi`, `docker system df`

## Обобщение
Образът е шаблон, контейнерът е изхвърляемо работещо копие, което споделя ядрото на хоста. С `run`, `exec`, `stop` и `rm` управляваш живота му, а с томове с `:ro` пускаш данни вътре, без да рискуваш оригинала. Ограничения като `--network none` и лимити правят контейнера лаборатория. Когато заплахата е насочена към ядрото или ти трябва друга ОС, използвай виртуална машина.

## Бележки за видеото
- Покажи разликата между `docker images` и `docker ps -a`
- Направи `run --rm`, после фонов контейнер с `exec` и `stop`
- Покажи отказа при запис в `:ro` том
- Покажи Dockerfile от три реда и `docker build`
- Обясни с пример защо код 137 означава SIGKILL
