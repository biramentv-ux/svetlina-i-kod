> **Цел на проекта:** да сглобиш със собствен идемпотентен Bash скрипт работна лаборатория за анализ и локален ИИ, която се създава наново на чиста машина с една команда и сама проверява дали е здрава.

## Какво ще научиш
- Как се проектира скрипт, който може да се пуска многократно без вреда (идемпотентност)
- Как се разделят стъпките, режимът „на сухо“ и режимът само за проверка
- Как да докажеш, че работи: проверки, журнал и повторно пускане на чиста среда
- Как да документираш, за да може друг (или ти след година) да възстанови лабораторията от нулата

## Условие

Лабораторията е твоето постоянно място за експерименти: папки за данни и модели, изолирана Python среда, няколко инструмента и ясен запис какво е инсталирано. Идеята е да не я правиш на ръка, а със скрипт `setup-lab.sh`, който:

1. създава структурата от папки;
2. подготвя Python виртуална среда (`python3 -m venv`) и инсталира зависимостите от файл `requirements.txt`;
3. проверява и (при нужда) инсталира нужните инструменти;
4. записва конфигурация и журнал;
5. завършва с набор от проверки, които казват **ОК** или **ГРЕШКА**.

Скриптът е **идемпотентен**: второто пускане не променя нищо, ако всичко е наред, а ако нещо липсва, поправя само него. Това е най-ценното му свойство. Скрипт, който чупи системата при второ пускане, е по-опасен, отколкото никакъв.

Връзка с другите пътеки: лабораторията е подходяща основа за курсовете `ii-ot-perceptrona-do-llm` (локален модел) и `reverse-engineering` (инструменти за анализ). Ако ги следваш, добави съответните инструменти като по-късно разширение; за този проект са достатъчни основните.

## Изисквания

**Задължителни (минимум за оценка):**
- Папки: `data`, `models`, `logs`, `scripts`, `notes` под корен, който се задава с `--root`.
- Python venv с поне една зависимост от `requirements.txt` (по твой избор; може да е и празен файл, ако няма мрежа).
- Проверка и инсталиране (или ясно съобщение какво да се инсталира) за: `python3`, `git`, `curl` и поне един инструмент по твой избор (`jq`, `tmux`, `ripgrep` и др.).
- Режими `--dry-run` (само показва) и `--check` (само проверява).
- Код на излизане: `0` при успех, различен от `0` при провал.
- `set -euo pipefail`, кавички около променливите и осмислени съобщения.

**По избор (бонус):**
- Поддръжка и на Ubuntu/Debian (`apt`), и на Fedora (`dnf`).
- Стъпка за локален ИИ: проверка за инсталиран `ollama` (инсталирай по официалната му документация; не копирай команди от случайни места) или `llama.cpp` и изтегляне на **малък** модел.
- Контейнерен вариант на лабораторията с `Dockerfile`.
- Автоматичен журнал с времеви печати във файл в `logs/`.

**Забрани:**
- Без `rm -rf` на пътища, изчислени от променливи без проверка.
- Без пароли, ключове и токени в скрипта или в README.
- Без `sudo` за цялото изпълнение: повишени права само за пакетния мениджър и само когато пакетът липсва.
- Без команди от вида „изтегли и изпълни“ (`curl ... | sh`) без документирано обяснение и проверка на източника.

## Работещ скелет

Скелетът по-долу е тестван (Bash 5.2, Ubuntu 24.04, Python 3.13) и покрива основните идеи: аргументи, `run` за `--dry-run`, идемпотентни стъпки и проверки. Не е готовото решение: няма инсталиране на инструменти и зависимости, няма журнал във файл и е само за една дистрибуция. Тези части са твоят принос.

```bash
#!/usr/bin/env bash
# setup-lab.sh - идемпотентно сглобяване на учебна лаборатория.
# Употреба: ./setup-lab.sh [--dry-run] [--check] [--root ПАПКА]
set -euo pipefail

LAB_ROOT="${LAB_ROOT:-$HOME/lab}"
DRY_RUN=0
CHECK_ONLY=0
LOG_FILE=""
FAILED=0

log()  { printf '%s [%s] %s\n' "$(date +%H:%M:%S)" "$1" "$2"; }
info() { log INFO "$1"; }
warn() { log WARN "$1" >&2; }
die()  { log ERROR "$1" >&2; exit 1; }

run() {  # изпълнява команда или само я показва при --dry-run
  if [ "$DRY_RUN" -eq 1 ]; then log DRY "$*"; else "$@"; fi
}

done_msg() { [ "$DRY_RUN" -eq 1 ] || info "$1"; }

usage() { sed -n '2,3p' "$0" | sed 's/^# \{0,1\}//'; }

while [ $# -gt 0 ]; do
  case "$1" in
    --dry-run) DRY_RUN=1 ;;
    --check)   CHECK_ONLY=1 ;;
    --root)    [ $# -ge 2 ] || die "липсва стойност за --root"; LAB_ROOT="$2"; shift ;;
    -h|--help) usage; exit 0 ;;
    *)         die "непознат аргумент: $1" ;;
  esac
  shift
done

step_dirs() {
  local d
  for d in data models logs scripts notes; do
    if [ -d "$LAB_ROOT/$d" ]; then info "папката $d вече съществува"
    else run mkdir -p "$LAB_ROOT/$d"; done_msg "създадена папка $d"; fi
  done
}

step_venv() {
  local venv="$LAB_ROOT/.venv"
  if [ -x "$venv/bin/python" ]; then info "venv вече съществува"
  else run python3 -m venv "$venv"; done_msg "създадено venv"; fi
}

step_config() {  # записва файла само ако съдържанието се е променило
  local f="$LAB_ROOT/lab.conf" tmp
  tmp="$(mktemp)"
  printf 'LAB_ROOT=%s\nCREATED_BY=setup-lab.sh\n' "$LAB_ROOT" > "$tmp"
  if [ -f "$f" ] && cmp -s "$tmp" "$f"; then info "lab.conf е актуален"
  else run cp "$tmp" "$f"; done_msg "записан lab.conf"; fi
  rm -f "$tmp"
}

check() {  # check ОПИСАНИЕ команда...
  local desc="$1"; shift
  if "$@" >/dev/null 2>&1; then log OK "$desc"
  else log FAIL "$desc"; FAILED=$((FAILED + 1)); fi
}

run_checks() {
  check "python3 е наличен"            command -v python3
  check "git е наличен"                command -v git
  check "папка data"                   test -d "$LAB_ROOT/data"
  check "venv има python"              test -x "$LAB_ROOT/.venv/bin/python"
  check "venv изпълнява код"           "$LAB_ROOT/.venv/bin/python" -c 'print(1)'
  check "lab.conf е непразен"          test -s "$LAB_ROOT/lab.conf"
  [ "$FAILED" -eq 0 ] || die "проверките с грешка: $FAILED"
  info "всички проверки минаха"
}

main() {
  info "лаборатория в $LAB_ROOT (dry-run=$DRY_RUN, check=$CHECK_ONLY)"
  if [ "$CHECK_ONLY" -eq 0 ]; then
    command -v python3 >/dev/null || die "липсва python3"
    run mkdir -p "$LAB_ROOT"
    step_dirs; step_venv; step_config
  fi
  [ "$DRY_RUN" -eq 1 ] || run_checks
}
main
```

**Идеи в скелета, на които да обърнеш внимание:**
- `run` е единственото място, което променя системата; затова `--dry-run` е лесен.
- Всяка стъпка първо пита „направено ли е вече?“, и чак тогава действа.
- `step_config` пише във временен файл и сравнява с `cmp`, така че файлът не се презаписва без нужда.
- `check` брои неуспехите и в края се излиза с код различен от нула. Така скриптът може да се ползва в друг скрипт.

## Какво показват изпълненията на скелета

Всички изходи са от тестване в празна временна папка. Пътят е заменен с `$L`.

Първо пускане създава всичко:

```
$ ./setup-lab.sh --root "$L"
13:05:51 [INFO] лаборатория в $L (dry-run=0, check=0)
13:05:51 [INFO] създадена папка data
...
13:05:54 [INFO] създадено venv
13:05:54 [INFO] записан lab.conf
13:05:54 [OK] python3 е наличен
...
13:05:54 [INFO] всички проверки минаха
```

Второ пускане не променя нищо:

```
13:05:54 [INFO] папката data вече съществува
13:05:54 [INFO] venv вече съществува
13:05:54 [INFO] lab.conf е актуален
```

Освен това контролната сума на всички файлове (без `.venv`) преди и след второто пускане е еднаква. Това е един прост начин да докажеш идемпотентност:

```
$ find "$L" -path "$L/.venv" -prune -o -type f -print0 | sort -z | xargs -0 sha256sum | sha256sum | cut -c1-16
bacd44f20959158e
```

След нарочна повреда (изтрити `data` и `.venv/bin/python`) режимът `--check` казва какво не е наред и излиза с код 1, а нормалното пускане поправя само повреденото:

```
[FAIL] папка data
[FAIL] venv има python
[FAIL] venv изпълнява код
[ERROR] проверките с грешка: 3
exit=1
```

Още една проверка: трасирането `bash -x` при пълно здрава лаборатория показва само един ред, който променя нещо – `mkdir -p`, а той при съществуваща папка е безвреден.

## Стъпка по стъпка
1. Създай папка `lab-project` и копирай скелета. Пусни `bash -n setup-lab.sh` за проверка на синтаксиса (ако имаш `shellcheck`, пусни и него).
2. Пусни скелета с `--dry-run` и прочети какво би направил.
3. Добави `requirements.txt` и стъпка, която инсталира зависимостите в `.venv` (`"$LAB_ROOT/.venv/bin/pip" install -r requirements.txt`). Помисли как да избегнеш повторно инсталиране без нужда.
4. Добави стъпка за инструменти: за всеки пакет провери `command -v` и чак тогава инсталирай. За Ubuntu/Debian това е `sudo apt-get install -y пакет`, за Fedora – `sudo dnf install -y пакет`. Разпознай дистрибуцията от `/etc/os-release`.
5. Добави журнал: насочи съобщенията и към `logs/setup.log` (например с `tee -a`).
6. Допълни проверките: версии, права на папките, дали виртуалната среда може да импортира инсталирана библиотека.
7. Тествай на чиста среда: нова временна папка, а най-добре – контейнер или виртуална машина. Запази изходите в `evidence/`.
8. Напиши README (виж по-долу).

## README: какво трябва да съдържа

- Какво е лабораторията и за какво служи (2–3 изречения).
- Изисквания: операционна система, `python3`, интернет (нужен ли е).
- Употреба: примери за `--dry-run`, `--check`, `--root`.
- Структура на папките (таблица).
- Как се възстановява от нулата: точна последователност от команди.
- Как се премахва: кои папки може да се изтрият и кои съдържат твои данни.
- Известни ограничения (на какви дистрибуции е тествано, какво не е).

## Чести грешки
- **`mkdir` без `-p`** – при второ пускане скриптът пада с „File exists“.
- **Презаписване на конфигурацията при всяко пускане** – губиш ръчни промени. Сравнявай, преди да пишеш.
- **Некавичени променливи** – път с интервал чупи командата, а празна променлива в `rm -rf $dir/` може да е катастрофа.
- **`sudo` в целия скрипт** – създава файлове на root в твоята папка. Повишавай само там, където е нужно.
- **Проверка „минава, защото го има при мен“** – тествай в празна среда, не в такава, която вече има всичко.
- **Скрипт, който тегли и пуска код без проверка** – не доверявай на източник, който не познаваш.
- **Липсващ `python3-venv`** – на някои дистрибуции (например Debian и Ubuntu) `python3 -m venv` изисква отделен пакет. Скриптът трябва да го засече и да каже какво да се инсталира.

## Упражнение: предаване

Предай папката `lab-project` с четирите елемента:

1. **Скрипт** `setup-lab.sh`, който покрива всички задължителни изисквания.
2. **`requirements.txt`** (може да е с една зависимост).
3. **README.md** по описанието по-горе.
4. **Доказателство за работа на чиста машина** в `evidence/`: изходът от първо пускане, второ пускане, `--check` и `--dry-run`, плюс кратко описание в какво среда е тествано (чиста виртуална машина, контейнер или нова временна папка).

Самопроверка преди предаване:
- Пускал ли си скрипта поне два пъти подред и сравнил ли си състоянието?
- Премахна ли `.venv` и пусна ли отново – възстановява ли се?
- Има ли `--check` ненулев код при повреда?
- README съдържа ли възстановяване от нулата, което си следвал буквално?
- Има ли в някой файл парола, ключ или лично име на папка?

## Бърза справка
- `set -euo pipefail`, `"$променлива"`, `local` във функции
- Идемпотентно: `mkdir -p`, проверка с `[ -d ... ]`, `command -v`, `cmp -s`
- `dpkg -s пакет` (Debian/Ubuntu), `rpm -q пакет` (Fedora)
- `bash -n скрипт` (синтаксис), `bash -x скрипт` (трасиране)
- Код на излизане: `0` успех, `1` проверка с грешка

## Обобщение
Проектът събира целия курс в един артефакт: файлове и права, конвейери и проверки, процеси и пакети, Bash, а по избор и контейнери. Мерилото за качество е повторяемостта. Ако лабораторията се създава със същия резултат при всяко пускане и можеш да го докажеш с изходи, значи си овладял основното умение на системния администратор: превръщаш ръчната работа в код, на който може да се вярва.
