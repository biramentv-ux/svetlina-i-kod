> **Цел на урока:** да изградиш REST API за списък със задачи с правилни методи, адреси, JSON тела и статус кодове, и да валидираш входа.

## Какво ще научиш
- Какво е ресурс и как REST API свързва методите GET, POST, PUT, PATCH и DELETE с действия
- Как се проектират адреси като `/api/zadachi` и `/api/zadachi/3`
- Кога се връща 200, 201, 204, 400, 404, 405 и 413
- Как се валидира JSON тяло и как се ограничава размерът му
- Как се проверява цялото API с `curl`

## Ресурси, методи и адреси

REST е стил за проектиране на API върху HTTP. Основната идея е **ресурсът**: именувано нещо, с което клиентът работи, например „задача“. Адресът назовава ресурса (съществително, обикновено в множествено число), а **методът казва какво правим с него**. Не пишеш `/api/dobaviZadacha` или `/api/iztriiZadacha`: адресът е същият, а методът се сменя.

| Заявка | Действие | Успешен отговор |
|---|---|---|
| `GET /api/zadachi` | списък на всички | `200` + масив |
| `GET /api/zadachi/3` | една задача | `200` + обект |
| `POST /api/zadachi` | създай нова | `201` + новата задача |
| `PUT /api/zadachi/3` | замени цялата задача | `200` + задачата |
| `PATCH /api/zadachi/3` | промени част от нея | `200` + задачата |
| `DELETE /api/zadachi/3` | изтрий | `204`, без тяло |

Различията между методите имат значение:
- `GET` само чете и не променя нищо. Може да се повтаря безопасно.
- `PUT` замества целия ресурс: ако не изпратиш поле, то получава стойността си по подразбиране. Повторен `PUT` със същото тяло дава същия резултат.
- `PATCH` променя само изпратените полета.
- `POST` създава и всяко повторение създава нов ресурс.
- `DELETE` премахва ресурса.

Параметрите за **филтриране** стоят в заявката за търсене: `GET /api/zadachi?gotovi=true`. Идентификаторът на конкретен ресурс е част от пътя.

## Статус кодовете като част от договора

Клиентът вярва на статуса преди да чете тялото. Затова кодът трябва да е точен:

| Код | Кога |
|---|---|
| `200 OK` | успешно четене или промяна |
| `201 Created` | създаден е ресурс; добавяш и заглавие `Location` с адреса му |
| `204 No Content` | успех, но няма какво да върнеш (след `DELETE`) |
| `400 Bad Request` | клиентът е изпратил невалидни данни или счупен JSON |
| `404 Not Found` | няма такъв ресурс или маршрут |
| `405 Method Not Allowed` | адресът съществува, но методът не е позволен; добавяш `Allow` |
| `413` | тялото е над допустимия размер (в Node текстът е „Payload Too Large“) |
| `500 Internal Server Error` | неочаквана грешка на сървъра |

Телата на грешките са еднакви по форма: `{ "greshka": "съобщение" }`. Клиентът така знае къде да търси текста. Не връщай вътрешни подробности (стекове, пътища до файлове).

## Целият код

Данните стоят в масив в паметта: при рестарт се губят. В модул 3 ще ги преместим в база. Всичко е във файл `api.js`:

```js
import { createServer } from "node:http";

const PORT = Number(process.env.PORT ?? 3000);
const MAX_TIALO = 10_000; // байта

const zadachi = [
  { id: 1, tekst: "Купи хляб", gotova: false },
  { id: 2, tekst: "Прочети урока", gotova: true },
];
let sledvashtId = 3;

class HttpGreshka extends Error {
  constructor(status, saobshtenie) {
    super(saobshtenie);
    this.status = status;
  }
}

function json(res, status, data) {
  res.writeHead(status, { "Content-Type": "application/json; charset=utf-8" });
  res.end(JSON.stringify(data));
}

async function chetiJson(req) {
  const chastichki = [];
  let razmer = 0;
  for await (const chast of req) {
    razmer += chast.length;
    if (razmer > MAX_TIALO) throw new HttpGreshka(413, "Тялото е твърде голямо");
    chastichki.push(chast);
  }
  try {
    return JSON.parse(Buffer.concat(chastichki).toString("utf8"));
  } catch {
    throw new HttpGreshka(400, "Невалиден JSON");
  }
}

function proveriZadacha(danni, chastichno = false) {
  if (typeof danni !== "object" || danni === null || Array.isArray(danni)) {
    throw new HttpGreshka(400, "Очаква се JSON обект");
  }
  const rezultat = {};
  if (!chastichno || "tekst" in danni) {
    if (typeof danni.tekst !== "string" || danni.tekst.trim() === "" || danni.tekst.length > 200) {
      throw new HttpGreshka(400, "Полето tekst трябва да е непразен низ до 200 знака");
    }
    rezultat.tekst = danni.tekst.trim();
  }
  if (!chastichno || "gotova" in danni) {
    if (danni.gotova !== undefined && typeof danni.gotova !== "boolean") {
      throw new HttpGreshka(400, "Полето gotova трябва да е true или false");
    }
    rezultat.gotova = danni.gotova ?? false;
  }
  return rezultat;
}

function nameri(idNiz) {
  const id = Number(idNiz);
  if (!Number.isInteger(id) || id < 1) throw new HttpGreshka(400, "Невалиден идентификатор");
  const zadacha = zadachi.find((z) => z.id === id);
  if (!zadacha) throw new HttpGreshka(404, "Задачата не е намерена");
  return zadacha;
}

async function obrabotka(req, res) {
  const url = new URL(req.url, `http://${req.headers.host}`);
  const chasti = url.pathname.split("/").filter(Boolean); // ["api","zadachi","2"]

  if (chasti[0] !== "api" || chasti[1] !== "zadachi" || chasti.length > 3) {
    throw new HttpGreshka(404, "Не е намерено");
  }

  const idNiz = chasti[2];

  if (idNiz === undefined) {
    if (req.method === "GET") {
      const gotovi = url.searchParams.get("gotovi");
      const spisak = gotovi === null ? zadachi : zadachi.filter((z) => z.gotova === (gotovi === "true"));
      return json(res, 200, spisak);
    }
    if (req.method === "POST") {
      const { tekst, gotova } = proveriZadacha(await chetiJson(req));
      const nova = { id: sledvashtId++, tekst, gotova };
      zadachi.push(nova);
      res.setHeader("Location", `/api/zadachi/${nova.id}`);
      return json(res, 201, nova);
    }
    res.setHeader("Allow", "GET, POST");
    throw new HttpGreshka(405, "Методът не е позволен");
  }

  const zadacha = nameri(idNiz);

  if (req.method === "GET") return json(res, 200, zadacha);
  if (req.method === "PUT") {
    const { tekst, gotova } = proveriZadacha(await chetiJson(req));
    Object.assign(zadacha, { tekst, gotova });
    return json(res, 200, zadacha);
  }
  if (req.method === "PATCH") {
    Object.assign(zadacha, proveriZadacha(await chetiJson(req), true));
    return json(res, 200, zadacha);
  }
  if (req.method === "DELETE") {
    zadachi.splice(zadachi.indexOf(zadacha), 1);
    res.writeHead(204);
    return res.end();
  }
  res.setHeader("Allow", "GET, PUT, PATCH, DELETE");
  throw new HttpGreshka(405, "Методът не е позволен");
}

const server = createServer(async (req, res) => {
  try {
    await obrabotka(req, res);
  } catch (e) {
    if (e instanceof HttpGreshka) return json(res, e.status, { greshka: e.message });
    console.error(e);
    json(res, 500, { greshka: "Вътрешна грешка" });
  }
});

server.listen(PORT, "127.0.0.1", () => console.log(`API на http://127.0.0.1:${PORT}/api/zadachi`));
process.on("SIGINT", () => server.close());
```

Ключовите решения:
- **Клас `HttpGreshka`** носи статус код. Всеки помощник просто хвърля, а **един** `catch` в `createServer` превръща грешката във верния отговор. Непознатите грешки стават `500`, а подробностите се пишат само в конзолата на сървъра.
- **`proveriZadacha`** не приема сляпо данните. Проверява типа, празния низ и дължината, и връща нов обект само със познатите полета. Непознати полета от клиента се игнорират.
- **`chetiJson`** брои байтовете и прекъсва при над 10 000.
- **Идентификаторът** се превръща в число и се проверява, преди да се търси. Съобщенията различават „лош идентификатор“ (`400`) от „няма такава задача“ (`404`).

## Проверка с curl

Адресът е в променлива на обвивката: `B=http://127.0.0.1:3000/api/zadachi`. Създаване:

```bash
curl -si -X POST -H "Content-Type: application/json" -d '{"tekst":"Позвъни на леля"}' $B
```

```text
HTTP/1.1 201 Created
Location: /api/zadachi/3
Content-Type: application/json; charset=utf-8

{"id":3,"tekst":"Позвъни на леля","gotova":false}
```

Четене, филтър, частична и пълна промяна:

```text
$ curl -s $B/2
{"id":2,"tekst":"Прочети урока","gotova":true}
$ curl -s "$B?gotovi=true"
[{"id":2,"tekst":"Прочети урока","gotova":true}]
$ curl -s -X PATCH -d '{"gotova":true}' $B/3
{"id":3,"tekst":"Позвъни на леля","gotova":true}
$ curl -s -X PUT -d '{"tekst":"Позвъни на баба","gotova":false}' $B/3
{"id":3,"tekst":"Позвъни на баба","gotova":false}
```

Изтриване и повторно търсене:

```text
$ curl -si -X DELETE $B/3 | head -1
HTTP/1.1 204 No Content
$ curl -s $B/3
{"greshka":"Задачата не е намерена"}
```

Невалидни заявки:

```text
$ curl -s -X POST -d '{"tekst":"  "}' $B
{"greshka":"Полето tekst трябва да е непразен низ до 200 знака"}
$ curl -s -X POST -d '{"tekst":"x","gotova":"да"}' $B
{"greshka":"Полето gotova трябва да е true или false"}
$ curl -s -X POST -d '{tekst' $B
{"greshka":"Невалиден JSON"}
$ curl -s $B/abc
{"greshka":"Невалиден идентификатор"}
$ curl -si -X DELETE $B | sed -n '1,2p'
HTTP/1.1 405 Method Not Allowed
Allow: GET, POST
```

А тяло от 20 000 байта, изпратено с `--data-binary @файл`, получава `{"greshka":"Тялото е твърде голямо"}`.

Бележка: API-то не проверява заглавието `Content-Type` на заявката. По-строго API би връщало `415 Unsupported Media Type` при нещо различно от `application/json`.

## Пример от практиката

Да кажем, че правиш списък с покупки за семейството. Ресурсът е „покупка“ с полета `ime`, `broi`, `kupena`. Мобилното приложение праща `POST /api/pokupki` за нова покупка и `PATCH /api/pokupki/5` с `{"kupena":true}`, когато я зачертаят. Уеб страницата вика `GET /api/pokupki?kupeni=false`. Три клиента ползват един и същ договор, защото методите и статусите са предвидими.

## Чести грешки

- **Глаголи в адреса** (`/api/iztrii`) – оставяй глагола на метода.
- **Винаги `200`** – дори при грешка. Клиентът не може да разбере какво е станало; връщай `4xx`/`5xx`.
- **`201` без `Location`** – клиентът не знае адреса на новия ресурс.
- **`DELETE` с тяло и `204`** – кодът 204 е без тяло.
- **Доверие на входа** – записване на `req` тялото директно в данните позволява на клиента да подмени `id` и други полета. Взимай само известните полета.
- **Идентификатор като текст** – сравнението `"3" === 3` е `false`; преобразувай и провери.
- **Липсва ограничение на тялото** – една огромна заявка изяжда паметта.

## Упражнение

Направи API за **книги** с полета `zaglavie` (задължително, до 100 знака), `avtor` (задължително) и `prochetena` (булева). Реализирай всичките шест действия, филтър `?prochetena=true`, точни статус кодове и еднакви тела на грешките.

Провери се сам: `POST` връща `201` и `Location`; `PUT` без поле го връща към стойността по подразбиране, а `PATCH` – не; `DELETE` връща `204`; празно заглавие, лош идентификатор, липсваща книга, грешен метод и тяло над ограничението връщат съответно `400`, `400`, `404`, `405` и `413`; сървърът не пада при нито една заявка.

## Бърза справка

| Задача | Правило |
|---|---|
| Прочети | `GET`, без промени |
| Създай | `POST` -> `201` + `Location` |
| Замени / промени част | `PUT` / `PATCH` -> `200` |
| Изтрий | `DELETE` -> `204` |
| Лош вход | `400` със съобщение |
| Липсва ресурс | `404` |
| Грешен метод | `405` + `Allow` |
| Голямо тяло | `413` |
| Неочаквана грешка | `500` без подробности |

## Обобщение

REST API назовава ресурси с адреси, а действията се определят от HTTP метода. Всеки успех и всяка грешка носят точен статус код и еднакво оформено JSON тяло. Входът никога не се приема сляпо: проверяваш тип, дължина и непознати полета, и ограничаваш размера на тялото. Един централен `catch` превръща хвърлените грешки в отговори, така че сървърът не пада. В следващия урок ще разделим този код на модули и ще го подредим със междинен слой.

## Бележки за видеото

Видеото е в терминален вид, със субтитри (сървърът работи в друг терминал):
- Списъкът със задачи се чете с `curl -s $B`.
- `POST` създава нова задача и връща JSON с `id` 3.
- Празен `tekst` връща съобщение за грешка при валидиране.
- `PATCH` отбелязва задачата като готова.
- `DELETE` връща `204`.
