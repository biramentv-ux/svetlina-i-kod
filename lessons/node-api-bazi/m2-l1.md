> **Цел на урока:** да регистрираш потребители с хеширани пароли чрез `node:crypto` и да ги държиш влезли със сесия в бисквитка, като ограничаваш опитите за налучкване.

## Какво ще научиш
- защо паролата никога не се пази в явен вид и защо обикновеният хеш не е достатъчен
- как да хешираш със сол (salt) и да проверяваш парола с `scrypt` и `timingSafeEqual`
- как работи сесията: случаен токен, бисквитка със защитни атрибути и запис в базата
- как да ограничиш опитите за вход и да не издаваш дали потребителят съществува

## Паролата не се пази, а се хешира
Ако базата ти изтече и в нея стоят пароли в явен вид, всеки може да влезе при всички потребители. Хората често използват една парола на много места, така че вредата излиза извън твоето приложение. Затова пазиш не паролата, а нейния хеш (hash): резултат от функция, която не се връща назад.

Обикновените хеш функции като SHA-256 са направени да са бързи, а това е проблем: атакуващият с откраднатата база може да пробва милиарди пароли в секунда. Нужна е функция за пароли (password hashing), която е нарочно бавна и иска памет. В `node:crypto` има такава: `scrypt`. Измерено в тази среда (само ориентир, зависи от машината):

```
sha256                               0.615126 ms
scrypt N=16384 (по подразбиране)     154.839038 ms
scrypt N=32768                       322.792022 ms
```

Около 150 ms е нищожно за един вход на потребител, но прави масовото налучкване стотици пъти по-скъпо. Параметърът `N` е цената: удвояването му удвоява времето. Ако го вдигнеш много, Node може да откаже и да върне `memory limit exceeded`; тогава подаваш по-голям `maxmem`. За начало остави стойностите по подразбиране.

Солта (salt) е случаен низ, различен за всеки потребител и записан до хеша. Той гарантира, че две еднакви пароли дават различни хешове и че готови таблици с предварително изчислени хешове са безполезни. Солта не е тайна.

| Понятие | Какво прави | Къде се пази |
|---|---|---|
| Парола | Тайна на потребителя | Никъде |
| Сол | Прави всеки хеш различен | До хеша, в базата |
| Хеш | Резултат от `scrypt(парола, сол)` | В базата |
| Токен на сесия | Случаен ключ в бисквитката | В браузъра; в базата само хешът му |

## Хеширане и проверка
Събери логиката в един файл `hash.mjs`. Записът е във формат `сол:хеш`, и двете в шестнайсетичен вид (hex).

```js
import { randomBytes, scrypt, timingSafeEqual } from "node:crypto";
import { promisify } from "node:util";

const scryptAsync = promisify(scrypt);

export async function hashPassword(password) {
  const salt = randomBytes(16);
  const hash = await scryptAsync(password, salt, 64);
  return `${salt.toString("hex")}:${hash.toString("hex")}`;
}

export async function verifyPassword(password, stored) {
  const [saltHex, hashHex] = stored.split(":");
  const expected = Buffer.from(hashHex, "hex");
  const actual = await scryptAsync(password, Buffer.from(saltHex, "hex"), expected.length);
  return timingSafeEqual(actual, expected);
}
```

Ползваме асинхронния `scrypt`, за да не блокираме цикъла на събитията за 150 ms при всеки вход. `timingSafeEqual` сравнява два буфера за едно и също време, независимо къде се различават; обикновеното `===` спира при първата разлика и в теория издава информация. Двата буфера трябва да са с еднаква дължина, иначе функцията хвърля `ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH`. Тук дължината е винаги 64 байта.

Опит с две хеширания на една и съща парола (записите са съкратени):

```

6371cc0efdf703d1ebe342f4bd319fa8:8790a2ab1b2adc2ffd40d4f98684c25ad741...
една и съща парола, различен запис: true
вярна парола: true
грешна парола: false
```

## Сесии: как сървърът помни, че си влязъл
HTTP няма памет: всяка заявка е самостоятелна. След успешен вход сървърът създава сесия (session), т.е. запис, че този браузър е доказал кой е. Браузърът носи отметка за него в бисквитка (cookie) и я връща при всяка следваща заявка.

Токенът трябва да е непредвидим, затова се взима от `randomBytes(32)`, а не от час, брояч или `Math.random()`. В базата не пазиш самия токен, а неговия SHA-256 хеш. Тук бързият хеш е подходящ, защото токенът е случаен и дълъг, не е измислен от човек. Ако базата изтече, откраднатите хешове не позволяват влизане.

Атрибутите на бисквитката са част от защитата:

| Атрибут | Ефект |
|---|---|
| `HttpOnly` | JavaScript на страницата не може да чете бисквитката, което ограничава кражбата ѝ при XSS |
| `SameSite=Lax` | Браузърът не я праща при повечето заявки от други сайтове, което ограничава подправени заявки (CSRF) |
| `Path=/` | Важи за целия сайт |
| `Max-Age` | Живот в секунди; `0` я изтрива |
| `Secure` | Праща се само през HTTPS; задължителен в продукция |

В примера по-долу няма `Secure`, защото тестваме по обикновен HTTP на локалния адрес. Когато пуснеш приложението зад HTTPS, добави атрибута.

## Стъпка по стъпка
Създай `server.mjs`. Помощните `send` и `readJson` са познатите от предишните уроци; `send` приема трети параметър с допълнителни заглавия.

1. Таблици и подготвени заявки:

```js
import { createServer } from "node:http";
import { DatabaseSync } from "node:sqlite";
import { createHash, randomBytes } from "node:crypto";
import { hashPassword, verifyPassword } from "./hash.mjs";

const SESSION_SECONDS = 60 * 60;
const MAX_FAILS = 5;
const WINDOW_MS = 60_000;

const db = new DatabaseSync(process.env.DB_FILE ?? ":memory:");
db.exec(`
  CREATE TABLE IF NOT EXISTS users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT NOT NULL UNIQUE,
    password_hash TEXT NOT NULL
  );
  CREATE TABLE IF NOT EXISTS sessions (
    token_hash TEXT PRIMARY KEY,
    user_id INTEGER NOT NULL REFERENCES users(id),
    expires_at INTEGER NOT NULL
  );
`);
const findUser = db.prepare("SELECT id, username, password_hash FROM users WHERE username = ?");
const addUser = db.prepare("INSERT INTO users (username, password_hash) VALUES (?, ?)");
const addSession = db.prepare("INSERT INTO sessions (token_hash, user_id, expires_at) VALUES (?, ?, ?)");
const findSession = db.prepare(`
  SELECT u.id, u.username FROM sessions s JOIN users u ON u.id = s.user_id
  WHERE s.token_hash = ? AND s.expires_at > ?`);
const dropSession = db.prepare("DELETE FROM sessions WHERE token_hash = ?");
const sha256 = (text) => createHash("sha256").update(text).digest("hex");
const DUMMY = await hashPassword("няма-такъв-потребител");
```

2. Регистрация с проверка на входа. Паролата има и горна граница, за да не принуждава сървъра да хешира огромен текст:

```js
if (req.method === "POST" && pathname === "/register") {
  const { username, password } = (await readJson(req)) ?? {};
  if (typeof username !== "string" || !/^[a-z0-9_]{3,20}$/.test(username))
    return send(res, 400, { error: "Потребителското име е 3–20 малки латински букви, цифри или _" });
  if (typeof password !== "string" || password.length < 10 || password.length > 200)
    return send(res, 400, { error: "Паролата трябва да е от 10 до 200 знака" });
  if (findUser.get(username)) return send(res, 409, { error: "Името е заето" });
  addUser.run(username, await hashPassword(password));
  return send(res, 201, { username });
}
```

3. Вход. Ако потребителят не съществува, пак се прави проверка срещу фиктивен хеш (`DUMMY`, изчислен при старт), за да отнема отговорът същото време. Съобщението е едно и също и при грешно име, и при грешна парола:

```js
const { username, password } = (await readJson(req)) ?? {};
const key = `${req.socket.remoteAddress}|${String(username).slice(0, 20)}`;
if (tooMany(key)) return send(res, 429, { error: "Твърде много опити, изчакай малко" }, { "Retry-After": "60" });
const user = typeof username === "string" ? findUser.get(username) : undefined;
const ok = typeof password === "string" &&
  (await verifyPassword(password, user ? user.password_hash : DUMMY)) && Boolean(user);
if (!ok) { noteFail(key); return send(res, 401, { error: "Грешно име или парола" }); }
fails.delete(key);
const token = randomBytes(32).toString("base64url");
addSession.run(sha256(token), user.id, Date.now() + SESSION_SECONDS * 1000);
return send(res, 200, { username }, {
  "Set-Cookie": `sid=${token}; HttpOnly; SameSite=Lax; Path=/; Max-Age=${SESSION_SECONDS}`,
});
```

4. Ограничението на опитите е брояч в паметта: пет неуспеха за минута за двойката адрес и име водят до 429. Ключът включва и името, затова един натрапник не заключва всички потребители от същия адрес.

```js
const fails = new Map();
function tooMany(key) {
  const f = fails.get(key);
  if (!f) return false;
  if (Date.now() - f.since > WINDOW_MS) { fails.delete(key); return false; }
  return f.n >= MAX_FAILS;
}
function noteFail(key) {
  const f = fails.get(key);
  if (!f || Date.now() - f.since > WINDOW_MS) fails.set(key, { n: 1, since: Date.now() });
  else f.n++;
}
```

5. `GET /me` чете бисквитката, хешира я и търси сесия, която още не е изтекла. `POST /logout` изтрива реда в базата и връща `Set-Cookie` с `Max-Age=0`.

Проверка с curl. Опцията `-c` записва бисквитките, `-b` ги връща:


## Пример от практиката
Да кажем, че правиш приложение за записки на участници в работилница. Потребителите се регистрират с име и парола. Един ден ти изпращат копие на базата за диагностика. Какво виждаш? Редове с имена, сол и хеш, и таблица със сесии, в която токените са хешове. Нищо от това не позволява да влезеш като потребител, нито да научиш паролата му. Ако вместо това в базата имаше пароли в явен вид, цялата работилница щеше да е компрометирана с едно копие. Точно срещу това са солта, бавният хеш и хешираните токени.

## Чести грешки
- **Парола в базата или в журнала.** Не записвай паролата никъде, включително в `console.log` при отстраняване на грешки.
- **Бърз хеш (SHA-256, MD5) за пароли.** Такива хешове се налучкват милиарди пъти в секунда.
- **Една сол за всички или сол в кода.** Солта е случайна и различна за всеки потребител.
- **Токен от `Math.random()` или от времето.** Можеш да го предвидиш; ползвай `randomBytes`.
- **Бисквитка без `HttpOnly` и `SameSite`.** Така я чете всеки скрипт на страницата.
- **Различни съобщения за „няма такъв потребител“ и „грешна парола“.** Издават кой има профил.
- **Сравнение с `===`.** За тайни стойности ползвай `timingSafeEqual`.
- **Вечни сесии.** Винаги записвай срок и го проверявай в заявката.
- **Броячът на опитите е само по адрес.** Така един натрапник заключва всички зад същия адрес; комбинирай адрес и име.

Затвори сървъра си, когато свършиш.

## Бърза справка
- `randomBytes(n)`: случайни байтове за сол и токени.
- `scrypt(парола, сол, дължина, колбек)`: бавен хеш за пароли; `promisify` за `await`.
- `timingSafeEqual(a, b)`: сравнение на буфери с равна дължина.
- Запис в базата: `сол:хеш`; токен: само SHA-256 хешът.
- Бисквитка: `HttpOnly; SameSite=Lax; Path=/; Max-Age=...`, плюс `Secure` при HTTPS.
- Кодове: `201` създаден, `401` не си влязъл или грешни данни, `409` заето име, `429` твърде много опити.
- Лимитът в паметта се губи при рестарт; в продукция се добавя още защита (например на ниво прокси).

## Обобщение
Паролата не се пази: пазиш `scrypt` хеш със случайна сол и го проверяваш с `timingSafeEqual`. След вход създаваш непредвидим токен, пазиш само хеша му в базата, а в браузъра го даваш в бисквитка с `HttpOnly`, `SameSite` и срок. Еднакво съобщение за грешка и брояч на опитите затрудняват налучкването. Следващият урок обобщава защитата на целия вход и изход на приложението.

## Бележки за видеото
Не е предвидено видео за този урок. При евентуален запис покажи хеширането на една парола два пъти с различен резултат, вход с `curl -c`, достъп до `/me` с бисквитката и `429` след шестия грешен опит.
