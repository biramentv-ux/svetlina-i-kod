> **Цел на урока:** да познаваш и да затваряш най-честите слабости в API-то: липсващо валидиране, SQL инжекция, XSS и неправилно настроен CORS.

## Какво ще научиш
- как да валидираш входа със списък от разрешеното (allowlist), а не със списък от забраненото
- как се появява SQL инжекцията, как я разпознаваш и защо параметрите я спират
- как XSS се получава от неекраниран изход и как се лекува с екраниране и политика за съдържание
- какво прави CORS, какво не прави и как да го настроиш безопасно
- как да прегледаш цяло API по контролен списък

## Три навика вместо списък от трикове
Сигурността в уеб приложение се свежда до три навика:

1. **Не вярвай на входа.** Всичко от заявката (тяло, адрес, заглавия, бисквитки) идва от непознат. Проверявай тип, дължина и формат.
2. **Екранирай изхода.** Данните, които връщаш в HTML, SQL или команда, се превръщат в безвредни за съответния контекст.
3. **Давай най-малко права.** Съобщенията за грешка не издават вътрешности, CORS допуска само нужното, а потребителят вижда само своето.

Примерите по-долу са собствен учебен код, пуснат на локалния адрес. Всеки показан „уязвим“ вариант е следван от поправка; целта е да разпознаваш проблема в своя код.

## Валидиране на входа
Валидирането отговаря на въпроса „приемлива ли е тази стойност?“. Определи точно какво е позволено и откажи останалото с 400. Проверявай:

- **тип**: `typeof name === "string"`; JSON може да даде число, масив или обект там, където очакваш низ;
- **дължина**: и минимум, и максимум, защото огромен вход товари паметта;
- **формат**: например `/^[a-z0-9_]{3,20}$/` за потребителско име;
- **размер на тялото**: прекъсни четенето над лимит и върни 413;
- **вид на съдържанието**: за JSON API очаквай `Content-Type: application/json`, иначе 415.

```js
class HttpError extends Error {
  constructor(status, message) { super(message); this.status = status; }
}

async function readJson(req) {
  if (!(req.headers["content-type"] ?? "").startsWith("application/json"))
    throw new HttpError(415, "Очаквам application/json");
  let raw = "";
  for await (const chunk of req) {
    raw += chunk;
    if (raw.length > MAX_BODY) throw new HttpError(413, "Тялото е твърде голямо");
  }
  try { return JSON.parse(raw); } catch { throw new HttpError(400, "Невалиден JSON"); }
}

function validateEntry(body) {
  const { name, message } = body ?? {};
  if (typeof name !== "string" || name.trim().length < 1 || name.length > 40)
    throw new HttpError(400, "Името е от 1 до 40 знака");
  if (typeof message !== "string" || message.trim().length < 1 || message.length > 500)
    throw new HttpError(400, "Съобщението е от 1 до 500 знака");
  return { name: name.trim(), message: message.trim() };
}
```

Така отговорите на лошия вход са предвидими. Реални резултати: празно име връща `{"error":"Името е от 1 до 40 знака"}` с 400, число вместо име също 400, заявка без `application/json` дава 415, тяло над 4096 знака дава 413, а счупен JSON дава 400.

Валидирането не замества екранирането. Името „Д'Артанян“ е напълно валидно и ще счупи залепена заявка; затова следват следващите раздели.

## SQL инжекция
Инжекцията (SQL injection) се получава, когато входът на потребителя става част от текста на SQL заявката и променя нейния смисъл. Ето уязвим учебен обработчик за търсене по заглавие. Публичните бележки се показват, а частните трябва да остават скрити:

```js
// УЯЗВИМО: входът се залепя в SQL текста
const q = url.searchParams.get("q") ?? "";
const sql = "SELECT id, title FROM notes WHERE is_private = 0 AND title LIKE '%" + q + "%'";
try {
  return send(res, 200, db.prepare(sql).all());
} catch (e) {
  return send(res, 500, { error: e.message });
}
```

С нормално търсене `q=баница` получаваш `[{"id":1,"title":"Рецепта за баница"}]`. Но входът `zzz' OR 1=1 --` затваря кавичката, добавя условие, което е винаги вярно, и коментира остатъка на заявката. Резултатът в нашата тестова база:

```
[{"id":1,"title":"Рецепта за баница"},{"id":2,"title":"План за пролетта"},{"id":3,"title":"ТАЙНО: код за гаража"}]
```

Частната бележка изтече. Само един апостроф (`q='`) пък връща грешка `unrecognized token: "'"`, която издава, че заявката е залепена, и сама по себе си е сигнал за слабост. Забележка: в тази версия на Node `prepare()` обработва само първата заявка в текста и редът `x'; DROP TABLE notes; --` не изтри таблицата, а `exec()` изпълнява всички заявки. Не разчитай на такива особености за защита.

Поправката е да подадеш стойността като параметър. Тя никога не се разглежда като SQL, независимо какви знаци съдържа:

```js
const searchStmt = db.prepare(
  "SELECT id, title FROM notes WHERE is_private = 0 AND title LIKE ? ESCAPE '\\'"
);
// ...
const q = (url.searchParams.get("q") ?? "").slice(0, 100);
const pattern = "%" + q.replace(/[\\%_]/g, "\\$&") + "%";
return send(res, 200, searchStmt.all(pattern), undefined, headers);
```

Втората част е специфична за `LIKE`: символите `%` и `_` са джокери, затова ги екранираме. След поправката същият вход `zzz' OR 1=1 --` връща `[]`, търсенето `q=%` също връща `[]`, а `q=ТАЙНО` не намира частната бележка, защото `is_private = 0` остава част от заявката. Нормалното търсене `баница` работи както преди.

Две допълнителни правила. Първо, имена на таблици и колони, както и посока на сортиране, не могат да бъдат параметри. Ако са динамични, сравни ги със списък от разрешени стойности. Второ, не връщай `e.message` към клиента: логвай грешката на сървъра, а на клиента върни общо 500.

## XSS: когато данните стават код в страницата
XSS (cross-site scripting) се получава, когато текст на потребител се вмъква в HTML без екраниране и браузърът го изпълнява като скрипт. Уязвим учебен пример: книга за гости.

```js
// УЯЗВИМО: данните отиват в HTML без екраниране
const items = rows.map((r) => `<li><b>${r.name}</b>: ${r.message}</li>`).join("\n");
```

След запис със съобщение `<script>alert(1)</script>` HTML-ът съдържа `<li><b>Хакер</b>: <script>alert(1)</script></li>`. В Chromium, зареден с Playwright, страницата показва диалог: скриптът се е изпълнил. На истински сайт вместо `alert` би могло да е кражба на данни от страницата.

Поправката е екраниране на петте специални знака според контекста HTML:

```js
const escapeHtml = (s) =>
  String(s).replace(/[&<>"']/g, (c) => ({ "&": "&amp;", "<": "&lt;", ">": "&gt;", '"': "&quot;", "'": "&#39;" })[c]);

const items = rows.map((r) => `<li><b>${escapeHtml(r.name)}</b>: ${escapeHtml(r.message)}</li>`).join("\n");
```

Сега HTML-ът съдържа `&lt;script&gt;alert(1)&lt;/script&gt;`, браузърът го показва като текст и диалози няма (`диалози: 0`). Ако API-то ти връща само JSON, а страницата се изгражда с `textContent`, а не с `innerHTML`, проблемът не възниква; опасните места са `innerHTML`, шаблони и всеки HTML, сглобен от потребителски данни.

Втора линия на защита е заглавието `Content-Security-Policy`. С `default-src 'none'` браузърът отказва да изпълнява вградени скриптове. При проверка с изключено екраниране, но с оставена политика, диалогът пак не се появи. Политиката не замества екранирането, а го допълва.

## CORS и заглавия за сигурност
CORS (cross-origin resource sharing) е правило на браузъра: страница от един произход (origin: схема, домейн и порт) не може да чете отговори от друг произход, освен ако сървърът не го разреши със заглавие. Важно е да знаеш какво **не** е CORS: той не пази сървъра от заявки с curl или от друг сървър. Защитава потребителя в браузъра. Затова не го ползвай вместо вход и права.

Настройвай го със списък от разрешени произходи, а не със `*`, особено когато има бисквитки:

```js
const ALLOWED_ORIGINS = new Set(["http://127.0.0.1:5173"]);
// ...
if (origin && ALLOWED_ORIGINS.has(origin)) {
  headers["Access-Control-Allow-Origin"] = origin;
  headers["Vary"] = "Origin";
}
```

Предварителната заявка (preflight, метод `OPTIONS`) от разрешен произход получава `204` със `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods: GET, POST` и `Access-Control-Allow-Headers: Content-Type`. От неразрешен произход (`example.com`) отговорът е `204` без тези заглавия и браузърът блокира заявката.

| Заглавие | Какво прави |
|---|---|
| `Content-Security-Policy` | Ограничава откъде и какъв код може да се изпълнява |
| `X-Content-Type-Options: nosniff` | Забранява на браузъра да налучква типа на съдържанието |
| `Referrer-Policy: no-referrer` | Не изпраща адреса на страницата към други сайтове |
| `Access-Control-Allow-Origin` | Разрешава конкретен произход да чете отговорите |

## Стъпка по стъпка
Прегледай своето API:
1. Намери всяко място, където се чете вход (`req.url`, тяло, заглавия, бисквитки), и добави валидиране с лимити.
2. Потърси `+` или `${` в текст на SQL и ги замени с `?`.
3. Потърси `innerHTML` и HTML, сглобен от данни, и екранирай или ползвай `textContent`.
4. Добави общите заглавия във функцията, през която минават всички отговори.
5. Замени `*` в CORS с явен списък.
6. Провери отговорите за грешки: няма ли вътрешни текстове на изключения?

## Пример от практиката
Да кажем, че колега показва своя сайт за рецепти. Търсачката му връща грешка при апостроф: „Д'Артанян“ дава 500. Това е сигнал за залепена заявка. Преработва я с `?`, добавя лимит от 100 знака, и грешката изчезва заедно със слабостта. После забелязва, че коментарите се вмъкват с `innerHTML`, и ги сменя с `textContent`.

## Чести грешки
- **Черен списък.** Опитът да забраниш „лошите“ знаци винаги пропуска нещо; описвай позволеното.
- **Валидиране само в браузъра.** Всеки може да прати заявка и без твоята страница.
- **Екраниране на неправилното място.** Екранираш при записа, а не при изхода; контекстът решава как.
- **`Access-Control-Allow-Origin: *` с бисквитки или лични данни.**
- **Връщане на `e.message` на клиента.**
- **Доверие на размера и `Content-Type` без проверка.**
- **Динамично име на колона в `ORDER BY` без списък от разрешени.**

## Упражнение
Вземи API-то си и приложи контролния списък.
1. Напиши функция за валидиране на тялото при създаване и промяна на задача.
2. Въведи лимит на тялото и `415` за други типове.
3. Покажи в отделна временна папка уязвим вариант на търсене по заглавие, докажи слабостта на свои тестови данни и покажи поправката.
4. Добави `nosniff`, `Referrer-Policy` и `Content-Security-Policy` към всички отговори и CORS със списък от един произход.

Критерии: никъде няма заявка, сглобена с `+` или `${}`; лошите входове дават 400, 413 или 415, а не 500; текст като `<script>` излиза екраниран; отговор от неразрешен произход няма `Access-Control-Allow-Origin`; грешките не съдържат вътрешни текстове. Затвори сървърите си след проверката.

## Бърза справка
- Валидирай тип, дължина, формат и размер; отказвай с 400, 413 или 415.
- Стойностите в SQL са параметри (`?`); имената са от списък.
- `LIKE`: екранирай `%` и `_`.
- HTML изход: `escapeHtml` или `textContent`; `innerHTML` само със сигурно съдържание.
- Заглавия: `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`.
- CORS: списък от произходи, `Vary: Origin`, без `*` при бисквитки.
- Грешки: подробности в журнала, общо съобщение към клиента.

## Обобщение
Слабостите имат една и съща причина: данни, които се смесват с код. Валидирането ограничава какво влиза, параметрите държат SQL и данните разделени, екранирането прави текста безвреден в HTML, а CORS и заглавията ограничават какво може да прави браузърът. Не са нужни хитрости, а навици, приложени навсякъде. В курса „JavaScript за уеб“ виждаш как `textContent` пази страницата от страната на браузъра. Следва тест, а после проект, в който обединяваш всичко.

Не е предвидено видео за този урок. При запис покажи един и същ вход срещу уязвимия и поправения вариант: изтеклата частна бележка срещу празния резултат и `<script>` срещу екранирания текст.
