> **Цел на урока:** да разделиш API-то на модули с ясна отговорност, да изградиш междинен слой (middleware), да обработваш грешките на едно място и да вземаш настройките от променливи на средата.

## Какво ще научиш
- Защо един голям файл става проблем и как се разделя по отговорности
- Какво е междинен слой (middleware) и как се реализира верига от тях
- Как една централна точка превръща грешките в правилни отговори
- Как се четат и проверяват настройки от `process.env`
- Как се подрежда проектът във файлове

## Защо да разделяме

Кодът от предишния урок работи, но в един файл се смесват настройки, четене на заявката, правила и данни. За да смениш масива с база или да добавиш дневник, трябва да четеш всичко. Затова разделяме по **отговорност**: всеки файл знае за едно нещо.

```text
src/
  server.js      вход: чете настройките, пуска сървъра
  config.js      настройки от променливите на средата
  app.js         верига от междинни слоеве + централна обработка на грешки
  middleware.js  дневник, JSON тяло, помощник за отговор
  routes.js      маршрути: метод и адрес -> действие
  validate.js    проверка на входните данни
  store.js       данните (засега в паметта)
  errors.js      клас HttpGreshka
```

Правилото на посоката: `routes.js` вика `store.js` и `validate.js`, но `store.js` не знае нищо за HTTP. Така по-късно заменяш масива със SQLite, без да пипаш маршрутите (в модул 3).

Проектът има `package.json` със `"type": "module"` и скриптове `start` и `dev`, както в първия урок.

## Междинен слой

Междинният слой (middleware) е функция, която преминава **преди** маршрута и върши обща работа за всички заявки: записва в дневник, чете тялото, проверява вход. Тя получава `req`, `res` и функцията `next`; когато приключи, вика `next()`, за да продължи веригата. Ако хвърли грешка, веригата спира.

```js
import { HttpGreshka } from "./errors.js";

export function otgovori(req, res, next) {
  res.json = (status, data) => {
    res.writeHead(status, { "Content-Type": "application/json; charset=utf-8" });
    res.end(JSON.stringify(data));
  };
  return next();
}

export function dnevnik(req, res, next) {
  const start = performance.now();
  res.on("finish", () => {
    const ms = Math.round(performance.now() - start);
    console.log(`${req.method} ${req.url} ${res.statusCode} ${ms}ms`);
  });
  return next();
}

export function tialoJson(maxBajtove) {
  return async (req, res, next) => {
    if (!["POST", "PUT", "PATCH"].includes(req.method)) return next();
    const chastichki = [];
    let razmer = 0;
    for await (const chast of req) {
      razmer += chast.length;
      if (razmer > maxBajtove) throw new HttpGreshka(413, "Тялото е твърде голямо");
      chastichki.push(chast);
    }
    try {
      req.body = JSON.parse(Buffer.concat(chastichki).toString("utf8"));
    } catch {
      throw new HttpGreshka(400, "Невалиден JSON");
    }
    return next();
  };
}
```

Три слоя, три различни вида работа:
- `otgovori` **добавя** към `res` помощника `res.json(статус, данни)`, така че маршрутите не повтарят `writeHead` и `end`.
- `dnevnik` само **наблюдава**: записва време на началото и печата ред, когато отговорът е приключил (събитие `finish`).
- `tialoJson` е **фабрика**: приема настройка (максимален размер) и връща слой. Чете тялото и го поставя в `req.body`, за да не се занимава с това всеки маршрут.

Веригата се сглобява с малка функция:

```js
function podredi(sloeve, krai) {
  return (req, res) => {
    let i = 0;
    const next = async () => {
      const sloi = sloeve[i++];
      return sloi ? sloi(req, res, next) : krai(req, res);
    };
    return next();
  };
}
```

`next` взема следващия слой от масива; когато слоевете свършат, вика крайния обработчик (`krai`) – маршрутите. Редът в масива **е** редът на изпълнение и има значение: `otgovori` трябва да е първи, защото останалите разчитат на `res.json`. Фреймуъркът Express предлага същата идея наготово, а тук я строим сами, за да я разбереш.

## Централна обработка на грешки

Файлът `errors.js` е кратък:

```js
export class HttpGreshka extends Error {
  constructor(status, saobshtenie) {
    super(saobshtenie);
    this.status = status;
  }
}
```

Сега `app.js` събира всичко и има **единственото** място, където грешките стават отговори:

```js
import { HttpGreshka } from "./errors.js";
import { otgovori, dnevnik, tialoJson } from "./middleware.js";
import { marshruti } from "./routes.js";

// ... функцията podredi от по-горе ...

export function suzdaiPrilozhenie(config) {
  const sloeve = [otgovori, ...(config.dnevnik ? [dnevnik] : []), tialoJson(config.maxTialo)];
  const veriga = podredi(sloeve, marshruti);

  return async (req, res) => {
    try {
      await veriga(req, res);
    } catch (e) {
      if (e instanceof HttpGreshka) return res.json(e.status, { greshka: e.message });
      console.error(e);
      res.json(500, { greshka: "Вътрешна грешка" });
    }
  };
}
```

Логиката е проста. Очакваните грешки (`HttpGreshka`) носят свой статус и съобщение и клиентът ги получава. Всичко останало е **неочаквана грешка**: пишем я подробно в конзолата за себе си, а на клиента казваме само „Вътрешна грешка“. Така не разкриваме стекове и вътрешни пътища, а сървърът не пада.

Маршрутите вече са чисти: когато нещо не е наред, **хвърлят** `HttpGreshka` и не се грижат за формата на отговора. Файлът `routes.js` е същата логика като в предишния урок, но чете `req.body` и вика `store`:

```js
import { HttpGreshka } from "./errors.js";
import { proveriZadacha } from "./validate.js";
import * as store from "./store.js";

export async function marshruti(req, res) {
  const url = new URL(req.url, `http://${req.headers.host}`);
  const [api, resurs, idNiz, ...ostanalo] = url.pathname.split("/").filter(Boolean);
  if (api !== "api" || resurs !== "zadachi" || ostanalo.length > 0) {
    throw new HttpGreshka(404, "Не е намерено");
  }

  if (idNiz === undefined) {
    if (req.method === "GET") {
      const gotovi = url.searchParams.get("gotovi");
      const vsichki = store.spisak();
      return res.json(200, gotovi === null ? vsichki : vsichki.filter((z) => z.gotova === (gotovi === "true")));
    }
    if (req.method === "POST") {
      const nova = store.dobavi(proveriZadacha(req.body));
      res.setHeader("Location", `/api/zadachi/${nova.id}`);
      return res.json(201, nova);
    }
    res.setHeader("Allow", "GET, POST");
    throw new HttpGreshka(405, "Методът не е позволен");
  }

  const zadacha = store.nameri(idNiz);
  if (req.method === "GET") return res.json(200, zadacha);
  if (req.method === "PUT") return res.json(200, Object.assign(zadacha, proveriZadacha(req.body)));
  if (req.method === "PATCH") return res.json(200, Object.assign(zadacha, proveriZadacha(req.body, true)));
  if (req.method === "DELETE") {
    store.premahni(zadacha);
    res.writeHead(204);
    return res.end();
  }
  res.setHeader("Allow", "GET, PUT, PATCH, DELETE");
  throw new HttpGreshka(405, "Методът не е позволен");
}
```

Файлът `validate.js` е функцията `proveriZadacha` от предишния урок, само с `export` и внос на `HttpGreshka`. А `store.js` пази данните и **не знае за HTTP**, освен че хвърля `HttpGreshka` при липсващ запис:

```js
import { HttpGreshka } from "./errors.js";

const zadachi = [
  { id: 1, tekst: "Купи хляб", gotova: false },
  { id: 2, tekst: "Прочети урока", gotova: true },
];
let sledvashtId = 3;

export const spisak = () => zadachi;

export function nameri(idNiz) {
  const id = Number(idNiz);
  if (!Number.isInteger(id) || id < 1) throw new HttpGreshka(400, "Невалиден идентификатор");
  const zadacha = zadachi.find((z) => z.id === id);
  if (!zadacha) throw new HttpGreshka(404, "Задачата не е намерена");
  return zadacha;
}

export function dobavi({ tekst, gotova }) {
  const nova = { id: sledvashtId++, tekst, gotova };
  zadachi.push(nova);
  return nova;
}

export function premahni(zadacha) {
  zadachi.splice(zadachi.indexOf(zadacha), 1);
}
```

## Конфигурация от средата

Номерът на порта, адресът и ограниченията не са за кодиране „на твърдо“: на твоя компютър и на сървъра са различни. Четем ги от `process.env` и ги **проверяваме**:

```js
function chislo(env, ime, rezerva, min, max) {
  const surovo = env[ime];
  if (surovo === undefined) return rezerva;
  const n = Number(surovo);
  if (!Number.isInteger(n) || n < min || n > max) {
    throw new Error(`${ime} трябва да е цяло число между ${min} и ${max}, а е „${surovo}“`);
  }
  return n;
}

export function chetiKonfiguratsia(env = process.env) {
  return {
    port: chislo(env, "PORT", 3000, 1, 65535),
    host: env.HOST ?? "127.0.0.1",
    maxTialo: chislo(env, "MAX_TIALO", 10_000, 1, 1_000_000),
    dnevnik: env.DNEVNIK !== "izkl",
  };
}
```

Функцията приема `env` като параметър със стойност по подразбиране. Това я прави лесна за тестване с подаден обект. Входът на програмата е най-кратката част:

```js
import { createServer } from "node:http";
import { chetiKonfiguratsia } from "./config.js";
import { suzdaiPrilozhenie } from "./app.js";

let config;
try {
  config = chetiKonfiguratsia();
} catch (e) {
  console.error("Грешна настройка:", e.message);
  process.exit(1);
}

const server = createServer(suzdaiPrilozhenie(config));
server.listen(config.port, config.host, () => {
  console.log(`Слушам на http://${config.host}:${config.port}`);
});

process.on("SIGINT", () => server.close());
```

Лоша настройка се хваща още при старт, а не по средата на работа:

```text
$ PORT=abc node src/server.js
Грешна настройка: PORT трябва да е цяло число между 1 и 65535, а е „abc“
$ echo $?
1
```

## Стъпка по стъпка

1. Създай папка `src` и файловете от урока (`validate.js` вземи от предишния урок).
2. Пусни `npm start` и изпробвай с `curl` същите заявки като преди: резултатите трябва да са идентични.
3. Погледни редовете на дневника в конзолата на сървъра.
4. Пусни с `MAX_TIALO=20` и изпрати дълго тяло: очаквай `413`.
5. Пусни с `PORT=abc` и `DNEVNIK=izkl` и виж разликите.
6. За да видиш `500`, добави временно `throw new Error("тест")` в началото на `spisak` и изпрати `GET`. Върни промяната.

С пуснат сървър, пет заявки подред дават дневник като този (милисекундите се различават на всеки компютър):

```text
GET /api/zadachi 200 28ms
POST /api/zadachi 201 10ms
POST /api/zadachi 400 1ms
DELETE /api/zadachi/3 204 0ms
GET /api/zadachi/3 404 1ms
```

А при `MAX_TIALO=20` и тяло над 20 байта клиентът получава `{"greshka":"Тялото е твърде голямо"}`, а дневникът – `POST /api/zadachi 413`. При изкуствената грешка отговорът е `500` с `{"greshka":"Вътрешна грешка"}`, конзолата показва `TypeError: тест за 500`, а следващата заявка пак работи: сървърът не е паднал.

## Пример от практиката

Да кажем, че клуб по настолни игри ползва твоето API за записване на турнири. Един ден искат да знаят кой колко пъти е викал API-то. Добавяш **един** слой `broiach` в `app.js` и всички маршрути получават функцията без промяна. После искат да пазиш данните в база: променяш само `store.js`. Ако бе един голям файл, всяка от двете промени щеше да засегне хиляди редове.

## Чести грешки

- **Забравено `next()`** – заявката увисва, защото веригата не продължава. Слоят трябва да извика `next()` или да отговори.
- **Грешен ред на слоевете** – слой, който ползва `res.json`, преди `otgovori` да го е добавил.
- **`try`/`catch` във всеки маршрут** – повтаряш код, а някой пропуска грешка. Хвърляй и хващай на едно място.
- **Подробности в отговора при `500`** – стекове и пътища помагат на нападателя. Пиши ги само в дневника.
- **Настройки в кода** – пароли и портове в файла не са за хранилището; ползвай средата.
- **Модул, който знае за всичко** – `store.js`, който пише `res.json`, не може да се замени. Пази посоката.
- **Настройка без проверка** – води до необясним срив много по-късно.

## Упражнение

Разшири проекта:
1. Нов слой `broiach`, който брои заявките по метод и ги връща от `GET /api/statistika` (ново маршрутизиране в `routes.js` или отделен слой).
2. Нова настройка `LIMIT_ZADACHI` (цяло число, по подразбиране 100): когато броят на задачите е достигнат, `POST` връща `409` с `{ "greshka": "Достигнат е лимитът" }`.
3. Всички нови грешки да минават през `HttpGreshka`.

Провери се сам: `broiach` е във веригата, а не в маршрутите; лош `LIMIT_ZADACHI=0` спира сървъра при старт с ясно съобщение; никой маршрут не съдържа `try`/`catch`; сървърът не пада при нито една заявка.

## Бърза справка

| Понятие | Как изглежда |
|---|---|
| Междинен слой | `(req, res, next) => { ...; return next(); }` |
| Фабрика за слой | `tialoJson(макс)` връща слой |
| Веригата | масив от слоеве + краен обработчик |
| Очаквана грешка | `throw new HttpGreshka(400, "съобщение")` |
| Неочаквана грешка | `console.error(e)` + `500` без подробности |
| Настройка | `Number(process.env.PORT ?? 3000)` + проверка |
| Спиране | `server.close()` при `SIGINT` |

## Обобщение

Когато кодът расте, го делиш по отговорности: настройки, веригата от слоеве, маршрути, проверка и данни. Междинният слой върши обща работа за всяка заявка и предава управлението с `next()`. Всички грешки се хвърлят и се хващат на едно място, където се превръщат в подходящ статус; неочакваните се пишат в конзолата, а клиентът получава общо съобщение. Настройките идват от средата и се проверяват още при старт. В следващия модул заменяме масива в `store.js` със SQL база, без да пипаме маршрутите.
