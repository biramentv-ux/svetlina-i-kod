> **Цел на урока:** да запазиш задачите от API-то в SQLite файл с вградения модул `node:sqlite`, като използваш подготвени заявки и транзакции.

## Какво ще научиш
- как да отвориш база данни и да създадеш таблица с `CREATE TABLE`
- как да пишеш `INSERT`, `SELECT`, `UPDATE` и `DELETE` и да ги пускаш с `run()`, `get()` и `all()`
- защо стойностите се подават като параметри, а не се залепят в текста на заявката
- какво означава предупреждението за експериментален модул и как да живееш с него
- как транзакцията (transaction) пази данните от половинчати промени

## Защо база данни, а не масив
До сега задачите ти живееха в масив в паметта. Масивът е бърз и прост, но се изчиства при всяко спиране на процеса. Файл с JSON решава проблема наполовина: при всяка промяна пренаписваш целия файл, а при две едновременни заявки можеш да загубиш данни.

Релационната база данни (relational database) пази данните в таблици с редове и колони, гарантира, че промените са цялостни, и умее да търси бързо. SQLite е база, която живее в един обикновен файл и няма отделен сървър за инсталиране. Затова пасва на философията на курса: само вградени модули и нула външни зависимости. За натоварени приложения често се взема отделен сървър за бази данни (PostgreSQL, MySQL), а езикът SQL, който учиш тук, е почти същият.

## Модулът node:sqlite и предупреждението
Node.js 22 носи модула `node:sqlite`. В Node 22.23.4 (с нея са проверени примерите) той се зарежда без никакъв флаг. При пускане обаче Node извежда предупреждение, което отива в потока за грешки (stderr), а не в обикновения изход:

```
(node:12529) ExperimentalWarning: SQLite is an experimental feature and might change at any time
(Use `node --trace-warnings ...` to show where the warning was created)
```

Номерът в скобите е номерът на процеса и при теб ще е различен. Какво значи съобщението: програмният интерфейс на модула още може да се промени в следващи версии. Затова:

- Не го крий и не го забравяй. Фиксирай версията на Node в проекта си и препрочети бележките за модула при всяка смяна на версията.
- Можеш да скриеш всички предупреждения с `node --no-warnings`, но така скриваш и други, полезни съобщения. Ползвай го само в сървърния скрипт, не в тестовете.

Зарежда се с `import { DatabaseSync } from "node:sqlite"`. Името `DatabaseSync` казва, че всички извиквания са синхронни: програмата чака отговора на базата. За учебен API и за малко приложение това е напълно достатъчно, а кодът е по-кратък, защото няма `await`.

## Таблици, типове и четирите основни заявки
Таблицата има колони с имена и типове. SQLite е свободна по отношение на типовете, но препоръката е да пишеш ясни колони и ограничения.

| Колона | Пример | За какво е |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `id` | Уникален пореден номер, който базата дава сама |
| `TEXT NOT NULL` | `title` | Текст, който не може да липсва |
| `INTEGER NOT NULL DEFAULT 0` | `done` | Няма тип „булева стойност“, затова се пази 0 или 1 |
| `CHECK (qty >= 0)` | `qty` | Правило, което базата проверява при всеки запис |
| `UNIQUE` | `username` | Не позволява две еднакви стойности |

Четирите основни заявки: `INSERT` добавя ред, `SELECT` чете, `UPDATE` променя, `DELETE` изтрива. `SELECT` без `WHERE` връща всички редове, а `UPDATE` и `DELETE` без `WHERE` засягат всички редове, така че винаги ги пиши внимателно.

## Подготвени заявки: run, get, all
Подготвената заявка (prepared statement) се създава с `db.prepare(...)`. Текстът ѝ съдържа места за стойности: `?` по позиция или `:име` по име. Стойностите се подават отделно при изпълнение.

- `run(...)` изпълнява `INSERT`, `UPDATE` или `DELETE` и връща обект `{ lastInsertRowid, changes }`.
- `get(...)` връща първия ред или `undefined`, ако няма такъв.
- `all(...)` връща масив с всички редове.

Реален изход от кратък опит с таблица `tasks`:

```
{ lastInsertRowid: 1, changes: 1 }
[Object: null prototype] { id: 2, title: 'Подготви урока', done: 0 }
undefined
{ lastInsertRowid: 2, changes: 1 }
```

Първият ред е резултатът от `insert.run("Купи хляб")`, вторият е `get(2)`, третият е `get(99)` за несъществуващ ред. Последният е `run` на `UPDATE`: `changes` показва колко реда са променени, а при `0` знаеш, че такъв ред няма. Полето `lastInsertRowid` има смисъл само след `INSERT`; след `UPDATE` то просто повтаря последния вмъкнат номер. Точно така в API-то ще разпознаваш отговор 404.

Двете важни причини да подготвяш заявките: параметрите са безопасни (за инжектирането ще говорим подробно в следващите уроци) и заявката се разбира от базата веднъж, а се изпълнява много пъти. Затова ги подготвяй веднъж, извън обработчика.

## Транзакции
Транзакцията групира няколко промени в едно цяло: или се записват всичките, или никоя. Започваш с `BEGIN`, завършваш с `COMMIT` (потвърждение) или `ROLLBACK` (отмяна).

```js
function sell(n) {
  db.exec("BEGIN");
  try {
    db.prepare("UPDATE stock SET qty = qty - ? WHERE item = 'боя'").run(n);
    db.prepare("INSERT INTO log (msg) VALUES (?)").run(`продадени ${n}`);
    db.exec("COMMIT");
  } catch (e) {
    db.exec("ROLLBACK");
    throw e;
  }
}
```

Втората полза е скоростта. Без транзакция всяко записване се потвърждава на диска поотделно. В тази среда 1000 вмъквания един по един отнеха около 2300 ms, а в една транзакция около 2 ms. Числата зависят от машината и диска и са само ориентировъчни, но разликата е огромна.

## Стъпка по стъпка
Вземаме сървъра за задачи от предишните уроци и му слагаме база. Създай празна папка и файл `server.mjs`.

1. Отвори базата и създай таблицата, ако още я няма:

```js
import { createServer } from "node:http";
import { DatabaseSync } from "node:sqlite";

const db = new DatabaseSync(process.env.DB_FILE ?? "zadachi.db");
db.exec(`
  CREATE TABLE IF NOT EXISTS tasks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    title TEXT NOT NULL,
    done INTEGER NOT NULL DEFAULT 0
  )
`);
```

2. Подготви заявките веднъж:

```js
const listAll = db.prepare("SELECT id, title, done FROM tasks ORDER BY id");
const getOne = db.prepare("SELECT id, title, done FROM tasks WHERE id = ?");
const insert = db.prepare("INSERT INTO tasks (title) VALUES (?)");
const markDone = db.prepare("UPDATE tasks SET done = 1 WHERE id = ?");
const remove = db.prepare("DELETE FROM tasks WHERE id = ?");
```

3. Опиши обработчика. Забележи как `changes` разпознава липсващ ред:

```js
function send(res, status, body) {
  res.writeHead(status, { "Content-Type": "application/json; charset=utf-8" });
  res.end(body === undefined ? "" : JSON.stringify(body));
}

async function readJson(req) {
  let raw = "";
  for await (const chunk of req) raw += chunk;
  return JSON.parse(raw);
}

const server = createServer(async (req, res) => {
  try {
    const url = new URL(req.url, "http://127.0.0.1");
    const m = url.pathname.match(/^\/tasks(?:\/(\d+))?$/);
    if (!m) return send(res, 404, { error: "Няма такъв адрес" });
    const id = m[1] ? Number(m[1]) : null;

    if (req.method === "GET" && id === null) return send(res, 200, listAll.all());
    if (req.method === "GET") {
      const row = getOne.get(id);
      return row ? send(res, 200, row) : send(res, 404, { error: "Няма такава задача" });
    }
    if (req.method === "POST" && id === null) {
      const { title } = await readJson(req);
      if (typeof title !== "string" || title.trim() === "") return send(res, 400, { error: "Липсва заглавие" });
      const info = insert.run(title.trim());
      return send(res, 201, getOne.get(Number(info.lastInsertRowid)));
    }
    if (req.method === "PUT" && id !== null) {
      const info = markDone.run(id);
      return info.changes === 0 ? send(res, 404, { error: "Няма такава задача" }) : send(res, 200, getOne.get(id));
    }
    if (req.method === "DELETE" && id !== null) {
      const info = remove.run(id);
      return info.changes === 0 ? send(res, 404, { error: "Няма такава задача" }) : send(res, 204);
    }
    send(res, 405, { error: "Методът не се поддържа" });
  } catch (err) {
    if (err instanceof SyntaxError) return send(res, 400, { error: "Невалиден JSON" });
    console.error(err);
    send(res, 500, { error: "Вътрешна грешка" });
  }
});

server.listen(3000, "127.0.0.1", () => console.log("Слушам на http://127.0.0.1:3000"));
process.on("SIGINT", () => { server.close(); db.close(); });
```

4. Пусни сървъра в един терминал с `node server.mjs`, а в друг опитай с curl:

```
$ curl -i -X POST 127.0.0.1:3000/tasks -d '{"title":"Купи хляб"}'
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
...
{"id":1,"title":"Купи хляб","done":0}

$ curl -X PUT 127.0.0.1:3000/tasks/1
{"id":1,"title":"Купи хляб","done":1}

$ curl -s -w " %{http_code}\n" 127.0.0.1:3000/tasks/2
{"error":"Няма такава задача"} 404

$ curl -s -w " %{http_code}\n" -X POST 127.0.0.1:3000/tasks -d '{"title":"  "}'
{"error":"Липсва заглавие"} 400
```

5. Спри сървъра с Ctrl+C, пусни го отново и поискай `GET /tasks`. Задачата от преди рестарта вече е там:

```
[{"id":1,"title":"Купи хляб","done":1}]
```

Това е разликата спрямо масива: данните живеят във файла, не в процеса.

## Пример от практиката
Да кажем, че правиш малък склад за боя на кооперативно ателие. Таблица `stock` пази количеството, а `log` записва всяка продажба. Продажбата е две стъпки: намаляваш количеството и записваш в дневника. Ако между двете стъпки програмата се счупи, без транзакция дневникът и складът се разминават.

Функцията `sell` от по-горе е пусната три пъти: нормална продажба на 2 броя, продажба на 1 брой с умишлен срив след първата стъпка и продажба на 9 броя, повече от наличното (колоната има `CHECK (qty >= 0)`):

```
{"stock":{"qty":3},"log":{"n":1}}
откат: Сривът е след първата стъпка
{"stock":{"qty":3},"log":{"n":1}}
откат: CHECK constraint failed: qty >= 0
{"stock":{"qty":3},"log":{"n":1}}
```

След срива количеството си остава 3: промяната от първата стъпка е отменена. Същото става и когато самата база откаже записа. Ограниченията в схемата (`NOT NULL`, `CHECK`, `UNIQUE`) са втора линия на защита зад проверките в кода ти.

## Чести грешки
- **Двойни кавички за текст.** В SQL `"x"` е име на колона, а текстът е в единични кавички. Получаваш реалната грешка `no such column: "x" - should this be a string literal in single-quotes?`. Стойностите от потребителя обаче така или иначе се подават като параметри.
- **Подаване на `undefined`.** `run(undefined)` хвърля `Provided value cannot be bound to SQLite parameter 1.`. Първо провери входа, после записвай.
- **Залепване на данни в текста на заявката.** Работи, докато някой не въведе апостроф. Подавай стойностите като параметри.
- **Редове с празен прототип.** Обектите от `get()` и `all()` нямат прототип. `JSON.stringify` работи нормално, но `assert.deepEqual` в строг режим не ги приема за равни на обикновен обект. Разгъни ги с `{ ...row }` преди сравнение.
- **Забравена транзакция при много записи.** Бавно е и при срив остават половин резултати.
- **Липса на `WHERE`.** `DELETE FROM tasks` изтрива всичко.

## Упражнение
Преобразувай своя сървър за задачи така, че да ползва SQLite файл вместо масив.

2. Всички пет операции (списък, една задача, създаване, отбелязване като готова, изтриване) да ползват подготвени заявки, създадени веднъж.
3. Добави `GET /tasks?done=1`, който връща само изпълнените, със стойност, подадена като параметър.

## Бърза справка
- `new DatabaseSync(файл)`: отваря или създава файл; `":memory:"` е база само в паметта.
- `db.exec(sql)`: изпълнява един или няколко реда SQL без параметри (схема, `BEGIN`, `COMMIT`).
- `db.prepare(sql)`: подготвя заявка с `?` или `:име`.
- `stmt.run(...)`: връща `{ lastInsertRowid, changes }`.
- `stmt.get(...)`: един ред или `undefined`; `stmt.all(...)`: масив от редове.
- `BEGIN`, `COMMIT`, `ROLLBACK`: ръчна транзакция; `ROLLBACK` слагай в `catch`.
- `node --no-warnings`: скрива предупрежденията, включително това за SQLite.
- Версията на Node определя точния интерфейс; прочети бележките за модула при смяна.

## Обобщение
SQLite пази данните в един файл и с `node:sqlite` я ползваш без външни пакети. Подготвените заявки със `run`, `get` и `all` покриват всяко действие на API-то, а `changes` и `undefined` ти казват кога отговорът е 404. Транзакцията прави няколко стъпки неделими и силно ускорява масовите записи. Модулът е експериментален: следи версията на Node. С тази база задачите вече преживяват рестарт, а следващата крачка е да защитиш потребителите, които ги пазят.

## Бележки за видеото
Видеото е терминал: показва кратък скрипт, който отваря файл на база, записва ред и го чете. Първото пускане показва реалното предупреждение за експериментален модул, второто доказва, че данните оцеляват между пусканията (два реда). Следва пускане с `--no-warnings` и размерът на файла на базата, до скрипта.
