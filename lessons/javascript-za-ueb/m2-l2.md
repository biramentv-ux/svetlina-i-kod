> **Цел на урока:** да запазваш данни в браузъра със `localStorage` и да откриваш грешките в кода си с конзолата, точките на прекъсване и четене на съобщенията.

## Какво ще научиш
- Как `localStorage` пази данни между две отваряния на страницата и какви са ограниченията му
- Как да записваш и четеш списъци и обекти чрез JSON и как да се пазиш от повредени данни
- Как да ползваш конзолата и инструкцията `debugger`, за да спреш кода и да видиш стойностите
- Как да разчиташ съобщенията за грешки и къде в инструментите за разработчици се виждат запазените данни и мрежовите заявки

## localStorage: малък сейф в браузъра

Променливите в JavaScript живеят, докато страницата е отворена. Презаредиш ли я, всичко изчезва. За малки данни (списък със задачи, избрана тема, последен филтър) браузърът предлага `localStorage`: хранилище от двойки „ключ – стойност“, което остава и след затваряне на браузъра. Основните методи са пет:

| Метод | Какво прави |
|---|---|
| `localStorage.setItem(ключ, стойност)` | записва; ако ключът го има, го презаписва |
| `localStorage.getItem(ключ)` | чете; ако ключът липсва, връща `null` |
| `localStorage.removeItem(ключ)` | трие един ключ |
| `localStorage.clear()` | трие всичко за този произход |
| `localStorage.length`, `localStorage.key(n)` | брой записи и име на n-тия ключ |

Има няколко правила, които е добре да знаеш предварително:

- **Само низове.** Ако запишеш число или обект, браузърът го превръща в текст. Записахме `{a: 1}` и получихме `[object Object]`, а числото `42` се върна като низ. Затова обектите и масивите минават през `JSON.stringify` при запис и `JSON.parse` при четене.
- **Всеки произход има собствено хранилище.** Произходът е схема, адрес и порт. В нашия опит данните, записани на `127.0.0.1:3457`, не се видяха от `localhost:3457`, макар че сочат към същия компютър.
- **`sessionStorage`** има същия интерфейс, но живее само в един раздел: в нов раздел стойността му беше `null`, докато `localStorage` се видя и в двата.
- **Ограничен обем.** Пределът е няколко мегабайта и зависи от браузъра. В Chromium четири реда по милион знака се побраха, а следващият хвърли `QuotaExceededError`. Запис, който може да не успее, винаги се обгражда с `try/catch`.
- **Не е сигурно място.** Потребителят може да види и промени всичко от инструментите за разработчици, а всеки скрипт на страницата чете хранилището. Никога не пази пароли и ключове.
- **Може да е недостъпно.** В някои режими (например частен прозорец с блокирани данни) достъпът хвърля грешка. Приложението трябва да работи и без него.

## Запис и четене на списък

Най-добре е да събереш достъпа до хранилището в една малка двойка функции, които знаят за ключа, JSON-а и повредените данни. Така останалият код не се занимава с тези детайли:

```js
const KEY = "tasks-v1";

export function save(tasks) {
  try {
    localStorage.setItem(KEY, JSON.stringify(tasks));
    return true;
  } catch (err) {
    console.warn("Не мога да запиша:", err.name);
    return false;
  }
}

export function load() {
  let text = null;
  try {
    text = localStorage.getItem(KEY);
  } catch {
    return [];
  }
  if (text === null) return [];
  try {
    const data = JSON.parse(text);
    return Array.isArray(data) ? data : [];
  } catch (err) {
    console.warn("Повредени данни, започвам начисто:", err.name);
    return [];
  }
}
```

Суфиксът `-v1` в ключа е навик, който ще ти спести проблеми: ако един ден смениш формата на данните, използваш `tasks-v2` и старите записи не чупят новата версия. Проверихме функциите в Chromium през страница, сервирана от локален сървър. Ето какво показа проверката (пред всеки ред е етикет на стъпката):

```
записвам:        true
в хранилището:   [{"id":1,"text":"Хляб","done":false}]
след презареждане: Намерени задачи: 1
след повреда ("{не е json"): предупреждение "Повредени данни, започвам начисто: SyntaxError", Намерени задачи: 0
нов чист браузър: Намерени задачи: 0
```

Две неща си струва да забележиш. Данните оцеляха при презареждане, но не и в нов, чист профил на браузъра. Повредената стойност не срина страницата, защото `JSON.parse` е в `try/catch`, а резултатът се проверява с `Array.isArray`. Данните от хранилището са входни данни като всички други и не бива да им вярваш сляпо.

## Конзолата като работен инструмент

Инструментите за разработчици се отварят с F12 или с Ctrl+Shift+I (на Mac с Cmd+Option+I) в Chrome, Edge и Firefox; точните имена на панелите зависят от браузъра и версията. Конзолата е най-често ползваният от тях. Освен `console.log` ще ти трябват още няколко метода:

```js
const tasks = [
  { id: 1, text: "Хляб", done: true },
  { id: 2, text: "Мляко", done: false },
];
console.log("обикновено:", tasks[0]);
console.table(tasks);
console.group("Група");
console.warn("предупреждение");
console.groupEnd();
console.assert(tasks.length === 3, "очаквах 3 задачи, а са", tasks.length);
```

```
обикновено: { id: 1, text: 'Хляб', done: true }
┌─────────┬────┬─────────┬───────┐
│ (index) │ id │ text    │ done  │
├─────────┼────┼─────────┼───────┤
│ 0       │ 1  │ 'Хляб'  │ true  │
│ 1       │ 2  │ 'Мляко' │ false │
└─────────┴────┴─────────┴───────┘
Група
  предупреждение
Assertion failed: очаквах 3 задачи, а са 2
```

Това е изходът в Node; в браузъра `console.table` рисува интерактивна таблица, а предупреждението е оцветено в жълто. `console.assert` пише само когато условието е лъжа, което е удобно за бързи проверки. За да видиш обект по време на изпълнението, понякога е по-добре да не го печаташ, а да спреш кода.

## Точки на прекъсване и debugger

Печатането на стойности е бавно, ако не знаеш къде да гледаш. По-силният начин е да спреш изпълнението в избран ред и да разгледаш всички променливи. Има два начина:

- **Точка на прекъсване (breakpoint):** в панела за изходния код (в Chrome и Edge „Sources“, във Firefox „Debugger“) щракваш върху номера на реда.
- **Инструкция `debugger;`** в самия код. Когато инструментите за разработчици са отворени, кодът спира на този ред; ако са затворени, инструкцията не прави нищо. Не я оставяй в готовия код.

Ето функция с коварна грешка: цикълът ползва `<=` вместо `<`.

```js
function average(prices) {
  let total = 0;
  for (let i = 0; i <= prices.length; i++) {
    debugger;
    total += prices[i];
  }
  return total / prices.length;
}
console.log("среден:", average([3, 5, 8]));
```

Резултатът е `среден: NaN`, а не `5,33`. Пуснахме страницата в Chromium и при всяка пауза прочетохме стойностите (редовете са форматирани от нашия скрипт за проверка):

```
пауза: i=0, prices[i]=3, total=0
пауза: i=1, prices[i]=5, total=3
пауза: i=2, prices[i]=8, total=8
пауза: i=3, prices[i]=undefined, total=16
```

На четвъртата пауза се вижда грешката: масивът има три елемента (индекси 0 до 2), а цикълът поиска и `prices[3]`. Събирането на `undefined` с число дава `NaN`. Поправката е `i < prices.length`. В инструментите ще видиш същото в панелите „Scope“ (променливите на текущата функция) и „Call Stack“ (веригата от извиквания). Можеш да добавиш и изрази за следене („Watch“).

Основните бутони за управление са: продължи до следващата пауза, мини през реда (step over), влез във функцията (step into) и излез от нея (step out). Клавишите за тях зависят от браузъра и са изписани върху бутоните.

## Четене на съобщенията за грешки

Първото правило при грешка е да прочетеш съобщението от начало докрай. То съдържа вид, причина и място. Ето истински съобщения, получени в Chromium:

| Съобщение | Какво означава | Типична причина |
|---|---|---|
| `ReferenceError: brojach is not defined` | името не съществува | печатна грешка, липсва `const` или `import` |
| `TypeError: Cannot read properties of undefined (reading 'name')` | четеш свойство на `undefined` | обектът още не е зареден или липсва поле |
| `TypeError: z.text is not a function` | викаш нещо, което не е функция | бъркаш свойство с метод |
| `TypeError: Assignment to constant variable.` | преприсвояваш `const` | ползвай `let` или не променяй стойността |
| `TypeError: Cannot set properties of null (setting 'textContent')` | `querySelector` не намери елемент | грешен селектор или скриптът върви преди HTML-а |
| `SyntaxError: Unexpected end of input` | липсва затваряща скоба | прегледай скобите и кавичките |
| `SyntaxError: Expected property name or '}' in JSON at position 1 (line 1 column 2)` | невалиден JSON | липсват двойни кавички около ключа |
| `ReferenceError: Cannot access 'x' before initialization` | ползваш `let`/`const` преди декларацията | премести реда |

Под съобщението стои **стекът** (stack trace): редовете са подредени от мястото на грешката към началото на извикванията, а най-горният сочи файла и реда. Щракването върху него отваря кода. Съобщенията се различават между браузърите и версиите (във Firefox и в Node текстът е друг), затова търси смисъла, а не точната формулировка.

## Къде се виждат данните и заявките

- **Мрежата** (раздел „Network“): за всяка заявка се виждат адрес, метод, статус, заглавия, време и отговор. Там първо проверяваш дали заявката изобщо е тръгнала и какъв статус е получила.
- **Хранилището** (в Chrome и Edge „Application“, във Firefox „Storage“): списък на ключовете в `localStorage` и `sessionStorage`. Можеш да ги разглеждаш, да ги редактираш и да ги изтриваш. Така проверяваш дали приложението ти записва правилно и можеш нарочно да повредиш запис, за да изпробваш защитата.
- **Конзолата**: можеш да пишеш код директно в нея, да вземеш елемент и да го разгледаш.

## Пример от практиката

Да кажем, че правиш малко приложение за списък с покупки. Потребителят добавя продукти, затваря страницата и на другия ден очаква да ги намери. След всяка промяна викаш `save`, а при стартиране `load`. Един ден добавяш ново поле „количество“. Старите записи нямат такова поле, затова кодът чете `item.quantity ?? 1`, а ключът минава на `-v2`. Ако потребителят отвори приложението в друг браузър или на друг адрес, списъкът няма да е там. Така разбираш, че `localStorage` пази данни на един браузър и един произход, а не на самия потребител.

## Чести грешки
- **Записване на обект без `JSON.stringify`** – получаваш `[object Object]` и данните се губят.
- **`JSON.parse` без `try/catch`** – един повреден запис спира цялото приложение.
- **Пазене на чувствителни данни** – паролите и ключовете не принадлежат на `localStorage`.
- **Предполагане, че хранилището е безкрайно** – при голям обем или забранен достъп записът хвърля грешка.
- **Оставена `debugger` инструкция** – бъркотия в готовия код.

## Упражнение

Вземи приложението за задачи и добави: (1) запис в `localStorage` след всяка промяна; (2) зареждане при старт; (3) защита срещу повредени данни. После изкуствено повреди записа и провери, че страницата работи. Накрая вмъкни нарочна грешка (например `list.textContent` върху липсващ елемент), намери я със съобщението и с точка на прекъсване и запиши в една бележка какво си видял.

Критерии: (1) данните оцеляват след презареждане; (2) повреден запис не руши страницата; (3) ключът има версия; (4) в кода няма останала `debugger` инструкция; (5) можеш да обясниш на какво отговаря всяка част от съобщението за грешка.

## Бърза справка
- `localStorage.setItem(k, v)`, `getItem(k)`, `removeItem(k)`, `clear()`; стойностите са низове
- Обекти и масиви: `JSON.stringify` при запис, `JSON.parse` в `try/catch` при четене
- Хранилището е отделно за всеки произход; `sessionStorage` е за един раздел
- Запис в `try/catch`: възможен е `QuotaExceededError`
- `console.log`, `console.table`, `console.group`, `console.assert`, `debugger;`
- Четеш: вид на грешката, съобщение, най-горния ред от стека

## Обобщение
`localStorage` пази малки данни между отварянията на страницата, но те са само текст, достъпни са на потребителя и може да липсват или да са повредени. Затова се записват като JSON и се четат със защита. Когато кодът не прави каквото очакваш, спираш го с точка на прекъсване и гледаш стойностите, вместо да гадаеш. Съобщенията за грешки са подробни и се четат отляво надясно. С това завършва модулът, а следващият урок е преговор. Ако работиш с Node.js, същите съобщения и дебъгер ще срещнеш в курса `node-api-bazi`.

- Повреди стойността и покажи как `try/catch` пази страницата
