> **Цел на урока:** да разделяш програма на няколко .c файла със заглавни файлове и да разбираш какво прави компилаторът и какво – свързващият редактор.

## Какво ще научиш
- Каква е разликата между декларация и дефиниция и кога се ползват `extern` и `static`
- Защо заглавните файлове имат предпазители и какво да (не) слагаш в тях
- Как една програма минава през препроцесор, компилатор и свързващ редактор (linker)
- Как да четеш обектни файлове с `nm` и да разпознаваш грешките при свързване
- Как да автоматизираш сглобяването с Makefile

## Единица на транслация

В „Програмиране от нулата“ писа програми в един файл. Реалните проекти са десетки или хиляди файлове. Компилаторът не вижда проекта като цяло: той обработва един `.c` файл наведнъж, след като препроцесорът е вмъкнал в него всички `#include`. Получилият се текст се нарича **единица на транслация** (translation unit).

Резултатът от компилирането на една единица е **обектен файл** (`.o`) с машинен код и таблица на символите. Едва после **свързващият редактор** (linker, `ld`, който се вика през `gcc`) събира обектните файлове в изпълним файл и замества всяко извикване на чужда функция с реалния ѝ адрес.

Помни това разделение, защото то обяснява две различни семейства грешки:

- грешки на компилатора – казват „не познавам това име“ или „типовете не съвпадат“;
- грешки на свързващия редактор – казват „познавам името, но никъде няма код за него“ или „кодът му е на две места“.

## Декларация и дефиниция

**Декларацията** казва на компилатора, че нещо съществува и какъв е типът му. **Дефиницията** създава самото нещо – заделя памет или генерира код.

```c
double stats_mean(const double *a, size_t n);   // декларация
double stats_mean(const double *a, size_t n) {  // дефиниция
    /* ... */
}

extern int stats_calls;   // декларация: променливата е дефинирана другаде
int stats_calls = 0;      // дефиниция: тук се заделя паметта
```

Правилото е просто: всяко нещо се **дефинира точно веднъж** в цялата програма, но може да се **декларира много пъти** – във всяка единица, която го ползва. Ключовата дума `extern` пред променлива означава „това е само декларация“. Функциите са външни по подразбиране, затова пред тях `extern` не се пише.

Обратното на външната видимост е `static` върху глобална променлива или функция. Тя получава **вътрешно свързване** (internal linkage): името е видимо само в тази единица и свързващият редактор не го вижда отвън. Така две библиотеки могат да имат по една помощна функция `note()`, без да се бият.

| Запис | Къде е видимо | Колко пъти се дефинира |
|---|---|---|
| `int x = 0;` (глобално) | цялата програма | веднъж |
| `extern int x;` | декларация, ползва външната `x` | колкото искаш |
| `static int x = 0;` (глобално) | само този .c файл | веднъж във всеки файл (отделни променливи) |
| `static` функция | само този .c файл | веднъж във всеки файл |
| `static` локална променлива | само във функцията, но живее цяла програма | веднъж |

## Заглавни файлове и предпазители

Заглавният файл (`.h`) е **договорът** на модула: съдържа декларациите, които останалите единици трябва да знаят. В него слагаш:

- прототипи на публичните функции;
- `extern` декларации на публичните глобални променливи;
- `typedef`, `struct`, `enum` и константи, които са част от интерфейса.

В заглавния файл **не слагаш** дефиниции на променливи и функции (освен `static inline` – за по-късно). Причината ще видиш след малко.

Същият файл може да бъде включен по два пътя – например `main.c` включва `report.h` и `stats.h`, а `report.h` също включва `stats.h`. Без защита типовете ще се дефинират два пъти:

```text
In file included from t.c:2:
bad.h:1:8: error: redefinition of 'struct P'
    1 | struct P { int x; };
```

Решението е **предпазител** (include guard):

```c
#ifndef STATS_H
#define STATS_H
/* съдържание */
#endif
```

При първото включване `STATS_H` не е дефиниран и съдържанието влиза; при второто условието е лъжа и целият блок се прескача. Много компилатори поддържат и `#pragma once`, но предпазителят е стандартен и работи навсякъде.

## Стъпка по стъпка: програма от три файла

Ще направим малък модул за статистика и модул за отчет. Работи в празна папка.

**1. Модулът `stats`.** Файлът `stats.h`:

```c
#ifndef STATS_H
#define STATS_H
#include <stddef.h>
extern int stats_calls;
double stats_mean(const double *a, size_t n);
double stats_max(const double *a, size_t n);
#endif
```

Файлът `stats.c` дефинира всичко и пази помощна функция `note()` като `static`:

```c
#include "stats.h"
int stats_calls = 0;
static void note(void) { stats_calls++; }
double stats_mean(const double *a, size_t n) {
    double s = 0;
    note();
    for (size_t i = 0; i < n; i++) s += a[i];
    return n ? s / n : 0;
}
double stats_max(const double *a, size_t n) {
    double m = a[0];
    note();
    for (size_t i = 1; i < n; i++) if (a[i] > m) m = a[i];
    return m;
}
```

Забележи, че `stats.c` включва собствения си `stats.h`. Така компилаторът проверява дали дефинициите съвпадат с декларациите.

**2. Модулът `report`.** `report.h` декларира `void report_print(const char *title, const double *a, size_t n);`, а `report.c` го реализира с `printf`, като вика `stats_mean` и `stats_max`.

**3. Главната програма `main.c`** подава четири температури на `report_print` и после печата `stats_calls`.

**4. Компилирай всеки файл поотделно** с `-c` (само компилиране, без свързване):

```text
$ gcc -Wall -Wextra -c stats.c
$ gcc -Wall -Wextra -c report.c
$ gcc -Wall -Wextra -c main.c
```

**5. Свържи обектните файлове:**

```text
$ gcc main.o stats.o report.o -o app
$ ./app
Температури: средно=22.25 макс=25.00
извиквания: 2
```

Препроцесираният `main.c` (опцията `-E`) е около 850 реда, макар сам да има десетина – толкова вкарват заглавните файлове.

## Какво има вътре в един обектен файл

Командата `nm` показва таблицата на символите:

```text
$ nm stats.o
0000000000000000 t note
0000000000000000 B stats_calls
00000000000000c3 T stats_max
000000000000001a T stats_mean

$ nm main.o
                 U __stack_chk_fail
0000000000000000 T main
                 U printf
                 U report_print
                 U stats_calls
```

Буквите значат:

| Буква | Значение |
|---|---|
| `T` / `t` | код (text); главна буква = външен символ, малка = `static` |
| `D` / `d` | инициализирани данни |
| `B` / `b` | неинициализирани данни (bss) |
| `U` | undefined – нужен е, но не е дефиниран тук |

Веднага се вижда, че `note` е малка `t` – скрита за останалите. А `main.o` изброява със `U` всичко, което чака да бъде намерено при свързването. Задачата на linker-а е да събере всички `U` със съответните `T`/`D`/`B`. Точният списък от `U` (например `__stack_chk_fail`) зависи от компилатора и настройките му.

## Грешки при свързването

Ето четирите най-чести, всички истински изходи от `gcc` 13.

**Липсва дефиниция.** Забравяш да подадеш `stats.o`:

```text
$ gcc main.o report.o -o app
main.c:(.text+0x6c): undefined reference to `stats_calls'
report.c:(.text+0x28): undefined reference to `stats_max'
report.c:(.text+0x40): undefined reference to `stats_mean'
collect2: error: ld returned 1 exit status
```

Съобщението идва от `ld`, не от компилатора – затова пише `ld returned 1 exit status`. Лекарството е да добавиш липсващия обектен файл (или библиотека).

**Дефиниция на две места.** Два файла дефинират `int counter = 0;`:

```text
$ gcc dup1.o dup2.o -o dup
dup2.o:(.bss+0x0): multiple definition of `counter'; dup1.o:(.bss+0x0): first defined here
```

**Дефиниция в заглавен файл.** Ако сложиш `int shared = 5;` в `g.h` и го включиш в два `.c` файла, всеки обектен файл получава собствена дефиниция и същата грешка се повтаря:

```text
g2.o:(.data+0x0): multiple definition of `shared'; g1.o:(.data+0x0): first defined here
```

Предпазителят тук не помага – той пази в рамките на една единица, а не между единиците. Затова в `.h` стои `extern int shared;`, а дефиницията отива в един `.c`.

**Опит да ползваш `static` отвън.** Ако `s1.c` има `static int hidden = 1;`, а друг файл пише `extern int hidden;`, `nm` показва `d hidden` (малка буква), а свързването пропада с `undefined reference to 'hidden'`.

**Липсваща декларация.** Ако извикаш `sq(3)` без прототип, GCC 13 (стандарт gnu17) само предупреждава `implicit declaration of function 'sq'`, а грешката идва едва от linker-а: `undefined reference to 'sq'`. Затова винаги компилирай с `-Wall`. В по-новите стандарти на C неявните декларации са недопустими, така че не разчитай на тази леснина.

## Makefile

Ръчното писане на трите команди бързо омръзва. `make` решава задачата: описваш зависимостите, а той прекомпилира само променените файлове.

```make
CC = gcc
CFLAGS = -Wall -Wextra -g
OBJ = main.o stats.o report.o

app: $(OBJ)
	$(CC) $(OBJ) -o $@

%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@

main.o report.o: stats.h report.h

clean:
	rm -f $(OBJ) app
```

Редовете с команди започват с **табулация**, не с интервали. `$@` е целта, `$<` – първата зависимост. Последният шаблон `%.o: %.c` казва как от всеки `.c` се прави `.o`, а редът `main.o report.o: stats.h report.h` добавя зависимост от заглавните файлове, за да се прекомпилират при промяна на интерфейса.

Първото `make` изпълнява всичко. След `touch stats.c` втората команда прекомпилира само `stats.c` и свързва наново:

```text
$ make
gcc -Wall -Wextra -g -c stats.c -o stats.o
gcc main.o stats.o report.o -o app
```

Забележи, че в нашия Makefile `stats.o` не зависи от `stats.h` – ръчното изброяване на заглавните зависимости лесно се забравя.

## Пример от практиката

Да кажем, че пишеш програма за обработка на показания от сензори с три модула: `sensor`, `filter` и `main`. Колегата ти добавя в `filter.h` глобален брояч `int dropped = 0;` и всичко се чупи с `multiple definition`. Правилната поправка е `extern int dropped;` в `filter.h` и `int dropped = 0;` само във `filter.c`. А ако брояча е нужен само вътре във `filter.c`, още по-добре е да стане `static` – тогава изобщо не излиза от модула и никой не го пипа случайно.

Общото правило: показвай в заглавния файл най-малкото възможно.

## Чести грешки

- **Дефиниция на променлива в `.h`** – води до `multiple definition`. Слагай `extern` в `.h` и дефиниция в един `.c`.
- **Липсващ предпазител** – води до `redefinition of 'struct ...'`. Всеки `.h` има предпазител.
- **Заглавният файл не се включва в собствения си `.c`** – компилаторът не открива, ако прототипът и дефиницията се разминават.
- **Забравен обектен файл при свързването** – `undefined reference`. Провери дали всеки `.c` е компилиран и подаден на linker-а.
- **Интервали вместо табулация в Makefile** – `make` се оплаква с `missing separator`.

## Упражнение

Раздели програмата за температури от урока на три `.c` файла с общ заглавен файл (задачата на урока: три файла, `Makefile`).

1. Направи модул `geom` с функции `area_circle` и `perimeter_circle` (константата π – в `geom.h` като `#define`).
2. Направи модул `app_log` с глобален брояч `log_count`, достъпен отвън, и `static` помощна функция за форматиране.
3. Напиши `main.c`, който ползва и двата.
4. Сглоби всичко с `Makefile` със зависимости към заглавните файлове.

Проверка:
- `make` не печата предупреждения при `-Wall -Wextra`;
- `nm app_log.o` показва помощната функция с малка буква, а `log_count` с главна;
- след `touch geom.h` се прекомпилират точно файловете, които го включват;
- умишлено добавена дефиниция в `.h` води до `multiple definition` и ти можеш да обясниш защо.

## Бърза справка

| Нужда | Решение |
|---|---|
| Само компилиране | `gcc -c f.c` |
| Свързване | `gcc a.o b.o -o prog` |
| Само препроцесор | `gcc -E f.c` |
| Символи в обектен файл | `nm f.o` |
| Скрит символ | `static` |
| Споделена променлива | `extern` в `.h`, дефиниция в един `.c` |
| Предпазител | `#ifndef X_H` / `#define X_H` / `#endif` |

## Обобщение

Програмата на C е множество от единици на транслация, всяка компилирана отделно до обектен файл. Заглавните файлове съдържат декларациите – договора между модулите, а дефиницията на всяко нещо живее на точно едно място. `static` скрива имената в рамките на файла, `extern` обещава, че нещо е дефинирано другаде, а linker-ът проверява това обещание. Грешките `undefined reference` и `multiple definition` са именно нарушения на това обещание. `make` пази времето ти, като прекомпилира само променения.
