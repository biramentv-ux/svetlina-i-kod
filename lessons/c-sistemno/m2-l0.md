> **Цел на урока:** да разбереш какво е недефинирано поведение в C, защо компилаторът има право да го използва срещу теб и как да го хванеш с предупреждения и UBSan, преди да е станало авария.

## Какво ще научиш
- Каква е разликата между недефинирано, неуточнено и дефинирано от реализацията поведение
- Кои са най-честите източници на недефинирано поведение: препълване на знаково число, излизане извън граници, неинициализирани променливи, невалидни измествания и указатели
- Защо една и съща програма се държи различно при `-O0` и `-O2` и при GCC и Clang
- Как да включиш UBSan и да четеш съобщенията му
- Как да пишеш код, който не разчита на недефинирано поведение

## Договорът между теб и компилатора

Стандартът на C е договор. Ти обещаваш да не нарушаваш определени правила, а компилаторът обещава да преведе програмата ти правилно. Ако нарушиш правило, договорът се прекратява и стандартът не казва нищо за това, което ще се случи. Това е **недефинирано поведение (undefined behavior, UB)**.

Недефинираното поведение не означава „грешна стойност“. Означава, че цялата програма е без гаранции. Тя може да даде очаквания резултат, да даде странен, да се срути, а може да работи безупречно седмици и да се счупи след смяна на компилатора, на версията му или на ключа за оптимизация.

Трябва да различаваш четири понятия:

| Понятие | Какво казва стандартът | Пример |
|---|---|---|
| Дефинирано поведение | Точно определен резултат | Препълване на `unsigned`: стойността се връща от нула |
| Дефинирано от реализацията | Компилаторът избира и документира | Размерът на `int`, десният shift на отрицателно число |
| Неуточнено | Има няколко допустими резултата, не е нужно да е документиран | Редът на изчисляване на аргументите на функция |
| Недефинирано (UB) | Няма никакви гаранции | Препълване на `int`, `a[5]` на масив с 5 елемента, `*p` при `p == NULL` |

Само последният ред е опасен в смисъл на „всичко е позволено“. Първите три си остават предвидими, ако знаеш правилата.

## Най-честите източници на UB

**Препълване на знаково цяло число.** При `int` събирането на `INT_MAX + 1` е UB. При `unsigned` същото е напълно дефинирано и се „обръща“ от нула. Разликата често изненадва хората, които идват от езици с обвиване.

**Излизане извън граници на масив.** Индексът трябва да е от 0 до размера минус 1. Четенето или писането извън тях е UB, дори адресът да изглежда „близо“ до масива.

**Неинициализирана променлива.** Автоматична променлива без начална стойност съдържа боклук и четенето ѝ е UB. Глобалните и `static` променливите са нулирани, локалните не са.

**Невалидно изместване.** `1 << 33` при 32-битов `int` е UB, както и изместване с отрицателен брой битове.

**Невалиден указател.** Разглеждането на `NULL`, на вече освободена памет или на указател към променлива, чийто живот е свършил (висящ указател).

**Нарушение на правилата за псевдоними (strict aliasing).** Достъп до обект през указател от несъвместим тип. Например четене на `float` през `int *`. За копиране на битове ползвай `memcpy`.

Този списък не е пълен. Приложение J на стандарта изброява много десетки случаи, но шестте горни обясняват огромната част от грешките в реалния код.

## Пример: три програми, които „работят“

Нека видим три малки програми. Компилираме ги с предупреждения и ги пускаме.

```c
/* ub1.c: препълване на знаково число */
#include <stdio.h>
#include <limits.h>

int main(void) {
    int x = INT_MAX;
    int y = x + 1;
    printf("%d\n", y);
    return 0;
}
```

```c
/* ub2.c: четене извън масива (условието е i <= 5, а не i < 5) */
#include <stdio.h>

int main(void) {
    int a[5] = {1, 2, 3, 4, 5};
    int sum = 0;
    for (int i = 0; i <= 5; i++)
        sum += a[i];
    printf("sum=%d\n", sum);
    return 0;
}
```

```c
/* ub3.c: неинициализирана променлива */
#include <stdio.h>

int main(void) {
    int total;
    for (int i = 1; i <= 3; i++)
        total += i;
    printf("total=%d\n", total);
    return 0;
}
```

Компилираме с `gcc -Wall -Wextra -O0` и пускаме:

```
$ ./ub1
-2147483648
$ ./ub2
sum=32781
$ ./ub3
total=-1984069138
```

Никаква грешка и нито едно предупреждение. Първата програма „сработи“ с обвиване, втората прочете случаен байт зад масива (сумата би трябвало да е 15), третата започна от боклук. Стойностите при теб ще са други, защото боклукът зависи от стека.

Ако смениш на `-O2`, GCC вече забелязва проблемите, защото анализът на потока от данни при оптимизация е по-дълбок:

```
ub2.c:7:17: warning: iteration 5 invokes undefined behavior [-Waggressive-loop-optimizations]
ub3.c:6:15: warning: 'total' is used uninitialized [-Wuninitialized]
```

Урокът е: **компилирай с `-Wall -Wextra` и поне веднъж с `-O2`, защото някои предупреждения излизат само при оптимизация**. И не се успокоявай, когато мълчат: предупрежденията хващат малка част от случаите.

## Защо оптимизацията разкрива проблема

Компилаторът има право да приеме, че UB никога не се случва. Това е полезно за скоростта: не е нужно да проверява нещо, което „не може“ да стане. Но води до коварни резултати. Класическият пример е проверка за препълване, написана след самото препълване:

```c
/* ub4.c */
int will_overflow(int x) {
    return x + 1 < x;
}
```

Логиката е ясна: ако `x` е `INT_MAX`, сборът се обръща и става по-малък. Но според стандарта `x + 1` никога не прелива, така че `x + 1 < x` е винаги лъжа и компилаторът може да я замени с `0`. Резултатът при `will_overflow(INT_MAX)` в тази среда (GCC 13 и Clang):

```
gcc   -O0 : 0
gcc   -O2 : 0
clang -O0 : 1
clang -O2 : 0
gcc -O2 -fwrapv : 1
```

Същият код дава различни отговори в зависимост от компилатора и ключа. GCC е свил проверката дори при `-O0`, Clang я е оставил без оптимизация. Ключът `-fwrapv` казва на компилатора да третира знаковото препълване като обвиване, и поведението става определено. Това е помощно средство, но не оправдание да пишеш непреносим код.

Правилната проверка не допуска препълването изобщо:

```c
#include <limits.h>
int will_overflow(int x) {
    return x == INT_MAX;          /* за x + 1 */
}
```

За общия случай `a + b` проверяваш предварително: `b > 0 && a > INT_MAX - b`. GCC и Clang имат и вградени функции като `__builtin_add_overflow`, които правят проверката за теб.

## UBSan: хващаме UB по време на изпълнение

**UndefinedBehaviorSanitizer (UBSan)** е част от GCC и Clang. Включва се с `-fsanitize=undefined` и вмъква проверки в програмата. Когато проверка се провали, се печата съобщение с файл, ред и колона.

```
$ gcc -g -fsanitize=undefined ub1.c -o ub1_u && ./ub1_u
ub1.c:6:9: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
-2147483648

$ gcc -g -fsanitize=undefined ub2.c -o ub2_u && ./ub2_u
ub2.c:7:17: runtime error: index 5 out of bounds for type 'int [5]'
```

Съобщенията казват точно какво е нарушено. Програмата по подразбиране продължава след съобщението. Ако искаш да спре при първата грешка, добави `-fno-sanitize-recover=undefined`.

Още един пример със shift и нулев указател:

```c
/* ub5.c */
#include <stdio.h>
int main(void) {
    int s = 33;
    int v = 1 << s;
    int *p = 0;
    printf("%d\n", v);
    return *p;
}
```

```
ub5.c:4:15: runtime error: shift exponent 33 is too large for 32-bit type 'int'
ub5.c:7:12: runtime error: load of null pointer of type 'int'
```

Обърни внимание на два факта. Първо, UBSan **не хвана** неинициализираната `total` от `ub3.c`: за такива грешки ползваме предупрежденията на компилатора и Valgrind (следващия урок). Второ, UBSan хваща само това, което се случи при конкретното изпълнение. Затова е най-полезен, когато го пускаш върху тестовете си.

## Стъпка по стъпка

1. Компилирай с `-Wall -Wextra -O2` и прочети всяко предупреждение. Не потискай предупреждение, преди да си го разбрал.
2. Пусни тестовете с `-g -fsanitize=undefined` (за повече проверки добави и `address`).
3. Когато UBSan съобщи за ред, отвори го и отговори на въпроса: какво е предположил авторът и кое от правилата на езика е нарушено?
4. Поправи причината: смени типа, добави проверка преди операцията или промени алгоритъма. Не се опитвай да „изтриеш“ съобщението с `-fwrapv`, освен ако не го искаш като съзнателно решение за целия проект.
5. Пусни тестовете отново. Ако са чисти, остави санитайзера в CI конфигурацията.

## Пример от практиката

Да кажем, че пишеш функция за средна яркост на кадър. Пикселите са `unsigned char`, а сумата държиш в `int`:

```c
int sum = 0;
for (int i = 0; i < w * h; i++) sum += pix[i];
```

Тестваш с малки изображения и всичко е наред. При кадър 8192 на 8192 сумата надхвърля `INT_MAX`: `w * h` е 67 108 864 пиксела, а при средна стойност 100 сумата е около 6,7 милиарда. Знаковото препълване е UB и резултатът ще зависи от компилатора. UBSan ще ти покаже реда още при първото изпълнение върху голямо изображение. Поправката е `unsigned long long sum` (или `uint64_t`) и `size_t` за индекса.

## Чести грешки

- **„Работи при мен, значи е вярно.“** – при UB „работи“ означава само „не се е счупило още“. Тествай с различни нива на оптимизация и с UBSan.
- **Проверка за препълване след операцията.** – както в `ub4.c`: компилаторът може да я премахне. Проверявай преди операцията.
- **Смесване на знакови и беззнакови.** – `if (i < strlen(s))` с отрицателно `i` го превръща в огромно число. Ползвай `size_t` за размери и сравнявай внимателно.
- **Индекс до `<= n` вместо `< n`.** – класическата грешка с единица. Пиши цикли по шаблона `for (i = 0; i < n; i++)`.
- **Разчитане на `-fwrapv` без да знаеш.** – кодът ти спира да е преносим стандартен C.
- **Игнориране на предупреждения.** – предупреждението за неинициализирана променлива почти винаги е истинска грешка.

## Упражнение

Получаваш три програми. Във всяка има по едно недефинирано поведение:

1. Средно аритметично на масив от `int`, при което сумата прелива.
2. Функция, която копира низ в буфер от 8 байта, но обхожда `<= 8` елемента.
3. Функция, която връща указател към локална променлива.

За всяка програма: компилирай с `-Wall -Wextra -O0` и с `-O2`, запиши какво казва компилаторът, после пусни с `-fsanitize=undefined,address`. Поправи ги и докажи, че са чисти.

Критерии: (а) за всяка програма имаш записан изход преди и след поправката; (б) никоя поправка не използва `-fwrapv` или потискане на предупреждения; (в) можеш да обясниш с едно изречение кое правило на езика е нарушено; (г) правилното решение за първата програма използва по-широк тип или предварителна проверка.

## Бърза справка

| Ситуация | Какво да правиш |
|---|---|
| Знаково препълване | По-широк тип, `__builtin_add_overflow` или проверка преди операцията |
| Индекс извън масив | Цикли с `< n`, `-fsanitize=address,undefined` |
| Неинициализирана | Инициализирай при декларация; Valgrind |
| `1 << n` | Провери `0 <= n < ширина на типа`, ползвай `1u` |
| Псевдоними | `memcpy` вместо преобразуване на указатели |
| Всеки проект | `-Wall -Wextra`, поне веднъж `-O2`, тестове с UBSan |

## Обобщение

Недефинираното поведение е нарушение на договора с компилатора и след него няма гаранции. Затова една програма може да работи с `-O0` и да се счупи с `-O2`, или да се държи различно в GCC и Clang. Предупрежденията хващат част от случаите, UBSan хваща останалите, които се изпълнят по време на тест. Най-сигурната защита е да пишеш код, който не разчита на нищо, което стандартът не гарантира. Това е основата и за следващия урок, където ще търсим грешките с паметта. Ако някога анализираш чужд бинарен файл (курсът „Reverse Engineering“), ще разпознаваш следите от тези оптимизации в асемблера.
