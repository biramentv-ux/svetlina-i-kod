> **Цел на урока:** да разбереш защо управляваният код (.NET) се анализира съвсем различно от родния – какво има в един .NET файл, как се чете IL, кои декомпилатори го връщат почти до изходния C# и какво променят ReadyToRun и Native AOT. Накрая го сравняваш с Java байткода и с Python `.pyc`.

## Подготовка
Работиш в собствена нова папка. Нужни са .NET SDK (в тази лаборатория е версия 8.0.134), `javac`/`javap` от JDK и Python 3. Примерът е малка C# програма с клас `Stack` и функция `Mul`, която умножава чрез събиране – същата идея като стековата машина `vm.c` от курса, пренесена в C#.

```csharp
using System;
namespace Demo {
  public class Stack {
    private int[] items = new int[8];
    private int sp;
    public void Push(int v) { if (sp >= items.Length) throw new InvalidOperationException("overflow"); items[sp++] = v; }
    public int Pop() { if (sp == 0) throw new InvalidOperationException("underflow"); return items[--sp]; }
  }
  public static class Program {
    public static int Mul(int a, int b) { int r = 0; for (int i = 0; i < b; i++) r += a; return r; }
    public static void Main() {
      var s = new Stack(); s.Push(6); s.Push(7);
      int y = s.Pop(), x = s.Pop();
      Console.WriteLine("6 * 7 = " + Mul(x, y));
    }
  }
}
```

Нормалният път е `dotnet build -c Release`. В изолираната среда възстановяването на пакети беше блокирано (`api.nuget.org`), затова компилирах директно с Roslyn (`csc.dll` от SDK-то) срещу референтните библиотеки на `net8.0`, с ръчно добавен `app.runtimeconfig.json`.

```
$ dotnet app.dll
6 * 7 = 42
$ ls -l app.dll
-rw-r--r-- 1 root root 4096 app.dll
```

## Какво е управляван код
В родния код (курсът по Ghidra) компилаторът превежда C директно в инструкции за конкретен процесор. Загубата на информация е огромна: няма типове, няма имена на локални променливи, функциите са просто адреси.

.NET работи на два етапа. Компилаторът (`csc`, Roslyn) превежда C#, F# или Visual Basic не в машинен код, а в **междинен език** – IL, наричан още CIL или MSIL. Резултатът е сглобка (assembly), файл `.dll` или `.exe`. Когато стартираш програмата, **CLR** (Common Language Runtime) зарежда сглобката, проверява я и **JIT компилаторът** превежда IL на парчета в машинен код за твоя процесор, точно преди да се изпълни. Затова такъв код се нарича „управляван“: средата следи типовете, паметта (сметосъбирач) и изключенията.

За анализатора следствието е голямо. IL е на нивото на езика, а не на процесора. Сглобката носи **пълни метаданни**: имена на типове, методи, полета и параметри, сигнатури, наследяване, атрибути. Нищо от това не се губи при компилация. Затова декомпилаторът за .NET връща код, който често е много близо до оригинала, с истинските имена на класовете и методите. Загубата се ограничава до коментарите, имената на локалните променливи (освен ако има символен файл `.pdb`), форматирането и някои конструкции, които компилаторът е превърнал в други (`foreach`, `using`, `async`, `lambda`, интерполирани низове).

Ако в декомпилирания код видиш класове с имена като `a`, `b`, значи авторът е преименувал символите (обфускация). Урокът не разглежда как се сваля такава защита от чужд софтуер; важното е, че метаданните вече не помагат и ще четеш повече IL и поведение.

## Как е устроен .NET файл
Сглобката е обикновен **PE файл**, същият контейнер като при родните Windows програми (урокът за формати на изпълними файлове). Започва с `MZ`, на отместване 0x3c има указател към заглавието `PE\0\0`. Разликата е в една от директориите на данните – **CLI заглавието**. То сочи към блока с метаданни и към IL кода. Старият вход `_CorExeMain` от `mscoree.dll`, който се вижда в импортите, е следа от времената, когато Windows зареждаше управлявани програми през този модул.

Проверих структурата на `app.dll` с кратък Python скрипт, който чете байтовете:

```
PE at 0x80 b'PE\x00\x00'
BSJB at 0x34c
b'v4.0.30319'
#~ 428
#Strings 356
#US 60
#GUID 16
#Blob 140
```

`BSJB` е магическият подпис на блока с метаданни (инициалите на четиримата създатели). Низът `v4.0.30319` е версията на метаданните, не версията на .NET: тя е една и съща за целия .NET Framework 4.x, .NET Core и .NET 5 и по-нови. След нея следват **потоците**:

| Поток | Съдържание | Какво търсиш в него |
|---|---|---|
| `#~` | Компресирани таблици с метаданни: TypeDef, MethodDef, Field, Param, MemberRef, TypeRef, CustomAttribute и др. | Структурата на програмата: кои типове има, кой метод на кой тип принадлежи, къде е IL кодът |
| `#Strings` | Идентификатори: имена на типове, методи, полета | Истинските имена (`Push`, `Pop`, `Mul`) или следите от обфускация |
| `#US` | Низовете от кода (User Strings) в UTF-16 | `overflow`, `underflow`, `6 * 7 = ` – текстове, URL адреси, пътища |
| `#Blob` | Двоични данни: сигнатури на методи и полета, константи | Типове на параметрите и връщаните стойности |
| `#GUID` | Идентификатори (MVID на модула) | Уникален идентификатор на конкретната компилация |

Важен детайл: низовете, които програмата показва, са в `#US` като UTF-16, затова `strings` без допълнителен параметър ги пропуска. Нужен е `strings -el`, който чете 16-битови малки-endian низове. Тук `strings -a` показа имената (`Push` и т.н.), а `strings -el -n 4` показа `overflow`, `underflow` и `6 * 7 = `.

Всеки елемент в метаданните има **маркер (token)** – 32-битово число: старшият байт е таблицата, останалите три са редът. Токенът `0x06000004` е ред 4 в таблицата `MethodDef` (0x06), т.е. четвъртият метод в сглобката. `0x04000002` е второто поле (таблица `Field`, 0x04), `0x0a000005` е външна препратка `MemberRef` (0x0a), `0x70000013` е низ от `#US` на отместване 0x13 (старшият байт 0x70 означава „потребителски низ“). Тези числа стоят в IL кода вместо имена, затова декомпилаторът трябва да ги разреши през таблиците.

## Четене на IL
IL е **стекова** машина, подобна на стековата ни `vm.c`: инструкциите вземат аргументи от стека на изчисленията (evaluation stack) и оставят резултата там. Локалните променливи и аргументите са в номерирани слотове. Нямам инсталиран `ildasm` или `ilspycmd` в тази лаборатория (пакетите се теглят от NuGet, а той е недостъпен), затова написах кратък C# разглобител със `System.Reflection`, който взема тялото на метода с `GetMethodBody().GetILAsByteArray()` и превежда байтовете по таблицата `System.Reflection.Emit.OpCodes`. Ето резултатът за `Mul`:

```
method Mul (token 0x06000004, IL 20 bytes, maxstack 2)
    IL_0000: ldc.i4.0
    IL_0001: stloc.0          // r = 0
    IL_0002: ldc.i4.0
    IL_0003: stloc.1          // i = 0
    IL_0004: br.s IL_000e     // към проверката на условието
    IL_0006: ldloc.0
    IL_0007: ldarg.0
    IL_0008: add
    IL_0009: stloc.0          // r += a
    IL_000a: ldloc.1
    IL_000b: ldc.i4.1
    IL_000c: add
    IL_000d: stloc.1          // i++
    IL_000e: ldloc.1
    IL_000f: ldarg.1
    IL_0010: blt.s IL_0006    // ако i < b, обратно в тялото
    IL_0012: ldloc.0
    IL_0013: ret              // върни r
```

Прочети го като програма: `ldc.i4.0` слага константата 0 на стека, `stloc.0` я сваля в локалната променлива 0. Цикълът е класическата форма на Release компилацията: безусловен скок към проверката в края, а тялото е отгоре. Въпреки че работим с 20 байта IL, `maxstack 2` казва, че изчисленията никога не държат повече от две стойности.

| Инструкция | Какво прави |
|---|---|
| `ldarg.N`, `ldarg.s` | зарежда аргумент N на стека (при инстанционен метод `ldarg.0` е `this`) |
| `ldloc.N`, `stloc.N` | зарежда или сваля в локална променлива N |
| `ldc.i4.N`, `ldc.i4.s` | константа от тип int32 |
| `ldstr` | зарежда низ по токен от `#US` |
| `ldfld`, `stfld` | чете или записва поле на обект |
| `ldelem.i4`, `stelem.i4` | чете или записва елемент на масив от int32 |
| `add`, `sub`, `mul` | аритметика върху двете горни стойности |
| `br.s`, `brtrue.s`, `blt.s` | условни и безусловни скокове (кратка форма с 1 байт отместване) |
| `call`, `callvirt`, `newobj` | извикване на метод, виртуално извикване, създаване на обект |
| `throw`, `ret` | хвърля изключение, връща от метода |

Същото важи за `Pop`. Ето началото му:

```
IL_0000: ldarg.0
IL_0001: ldfld 0x04000002        // this.sp
IL_0006: brtrue.s IL_0013        // ако sp != 0, прескочи
IL_0008: ldstr 0x70000013        // "underflow"
IL_000d: newobj 0x0a000005       // new InvalidOperationException(...)
IL_0012: throw
```

Това е точно проверката `if (sp == 0) throw ...` от изходния код, в обърната логика: компилаторът скача над хвърлянето, когато стойността е различна от нула. Така се вижда как се мисли в IL: върни условието в оригиналния вид и прочети токените.

## Декомпилатори за .NET
Тъй като IL запазва толкова информация, декомпилаторите са зрели и точни. Те не „откриват“ типове, а ги четат, и възстановяват управляващите конструкции (`for`, `while`, `foreach`, `switch`, `try/catch`) от скоковете.

| Инструмент | Лиценз | Платформа | Забележки |
|---|---|---|---|
| **ILSpy** (icsharpcode) | MIT, свободен | Графичният интерфейс (Avalonia) работи на Windows, Linux и macOS; `ilspycmd` като `dotnet tool` – на трите | Декомпилира до C#, цели проекти, търси типове и методи, показва метаданните; поддържа ReadyToRun файлове; има разширения.  |
| **dnSpyEx** (поддържана разклонена версия на dnSpy) | GPL-3.0, свободен | Изграждането е през .NET и PowerShell, главно Windows | Освен декомпилатор има **дебъгер** (точки на прекъсване, локални променливи, стек) и **редактор на сглобки** (метаданни, C#/VB, IL). Оригиналният dnSpy е спрян и архивиран |
| **dotPeek** (JetBrains) | Безплатен за ползване; затворен код | Windows | Декомпилатор и браузър на сглобки; може да служи като символен сървър. Проверявай на официалната страница на JetBrains актуалните условия |

Проверих в страницата на ILSpy: MIT, интерфейс на Avalonia за трите системи и `ilspycmd`. В страницата на dnSpyEx: GPL-3.0, дебъгер и редактор на сглобки, хранилището не е архивирано. За dotPeek не прочетох точната страница с условията, затова фактите за него са общи – провери ги. Не пуснах нито един от тези инструменти, защото NuGet и изтеглянията бяха блокирани.

Практически съвет: започни с ILSpy, защото е свободен и работи навсякъде. dnSpyEx ползвай само за дебъгване на **собствена** сглобка; редактирането на IL на чужда програма е извън границите на курса.

Декомпилираният C# е добра хипотеза, не гаранция: `async` методите стават машини на състоянията, а променливите се преизползват. Когато резултатът изглежда странно, върни се към IL – той е истината.

## ReadyToRun и Native AOT
Класическата сглобка съдържа само IL и JIT я компилира при всеки старт. За по-бърз старт има два начина да предкомпилираш.

**ReadyToRun (R2R)** добавя към сглобката предварително компилиран машинен код, но запазва IL и метаданните. Включва се с `<PublishReadyToRun>true</PublishReadyToRun>` при публикуване за конкретна платформа (runtime identifier). Файлът става по-голям, но CLR още може да върне към JIT. За анализа това е добра новина: IL е на мястото си и ILSpy чете такива файлове (в описанието му са посочени ReadyToRun сглобки за .NET Core), като показва IL и C#. Родният код вътре е допълнение, което обикновено не те интересува.

**Native AOT** е друго нещо. С `<PublishAot>true</PublishAot>` и `dotnet publish -r linux-x64 -c Release` целият код се компилира предварително до **родна** програма. Според документацията на Microsoft резултатът е самостоятелно приложение за конкретна платформа, с по-бърз старт и по-малко памет, което върви и без инсталиран .NET, а ограниченията включват липса на динамично зареждане (`Assembly.LoadFile`), липса на `System.Reflection.Emit` и задължително подрязване (trimming). Директорията съдържа и орязан CLR.

За анализатора изводът е решаващ: Native AOT файл **не е .NET сглобка**. В него няма IL и няма таблици с метаданни от разгледания тип, а обикновен ELF или PE файл. Отваряш го в Ghidra, а не в ILSpy; методите са родни функции, а имената се губят като при C++ (освен ако символите не са оставени). Остават следи, по които разпознаваш произхода: низове и структури на runtime-а, типични идентификатори и данни за сметосъбирача. Практиката от курса по родния код – триаж, низове, графове на извикванията – е точно инструментът тук. | Формат на разпространение | Съдържа IL и метаданни | Инструмент за анализ |
|---|---|---|
| Обикновена сглобка | да | ILSpy, dnSpyEx, dotPeek |
| ReadyToRun | да, плюс машинен код | ILSpy (чете IL), по желание Ghidra за родната част |
| Самостоятелен файл (single-file) | да, пакетиран с runtime | първо извличане на сглобките, после ILSpy |
| Native AOT | не | Ghidra, IDA, Binary Ninja, radare2 |

## Java байткод и Python `.pyc` за сравнение
Идеята „междинен език плюс виртуална машина“ не е само на .NET. Същата функция `mul` в Java, компилирана с `javac` и показана с `javap -c -p`:

```
static int mul(int, int);
  Code:
     0: iconst_0
     1: istore_2
     2: iconst_0
     3: istore_3
     4: iload_3
     5: iload_1
     6: if_icmpge     19
     9: iload_2
    10: iload_0
    11: iadd
    12: istore_2
    13: iinc          3, 1
    16: goto          4
    19: iload_2
    20: ireturn
```

Прилича на IL: стек, локални слотове, скокове. Разликите са дребни. В Java цикълът е с проверка отгоре и `goto` в края, в IL (на C# компилатора) е обратното. Java има специална `iinc` за увеличаване на локална променлива, а IL смята `ldloc`, `ldc.i4.1`, `add`, `stloc`. В Java слотовете на аргументите и локалните са общо номерирани (аргументи 0 и 1, локални 2 и 3), в IL имат отделни пространства (`ldarg` и `ldloc`). Java класовете носят същото богато описание на типове, затова `jadx` и други декомпилатори работят добре.

Python пази байткод в `.pyc` файлове. Със Python 3.13 `dis.dis` дава за същата функция:

```
LOAD_CONST          1 (0)
STORE_FAST          2 (r)
LOAD_GLOBAL         1 (range + NULL)
LOAD_FAST           1 (b)
CALL                1
GET_ITER
FOR_ITER            7 (to L2)
STORE_FAST          3 (i)
LOAD_FAST_LOAD_FAST 32 (r, a)
BINARY_OP           13 (+=)
```

Файлът `m.pyc` започва с „магическо число“ (`f3 0d 0d 0a`), което зависи от версията на интерпретатора. Различията от IL и Java са по-големи, защото Python е динамичен: няма типове на променливите (`LOAD_FAST`, а не `iload`), няма `iadd` – операторът `+=` е общият `BINARY_OP`, и видът му се решава в изпълнение. Байткодът на Python се променя често между версиите (във 3.13 има и комбинирани инструкции като `LOAD_FAST_LOAD_FAST`), затова декомпилаторите за `.pyc` са обвързани с конкретна версия.

| Свойство | .NET (IL) | Java (байткод) | Python (`.pyc`) |
|---|---|---|---|
| Контейнер | PE с CLI заглавие | `.class`, пакетирани в `.jar` | `.pyc` (маршализиран код) |
| Типове в кода | статични, в метаданните | статични, в дескрипторите | динамични |
| Идентификатори | пълни, в `#Strings` | пълни, в константния пул | имена на променливи и функции |
| Компилиране в машинен код | JIT, ReadyToRun, Native AOT | JIT, GraalVM Native Image | обикновено не (интерпретатор) |
| Качество на декомпилация | много високо | много високо | зависи от версията |
| Основни инструменти | ILSpy, dnSpyEx, dotPeek | `javap`, jadx, CFR | `dis`, декомпилатори по версия |

## Чести грешки
- **Низове само с `strings`.** Низовете на .NET са в UTF-16; ползвай `strings -el`.
- **Версията на метаданните не е версията на .NET.** `v4.0.30319` стои във всички съвременни сглобки.
- **Декомпилираният C# не е изходният код.** `async` и `foreach` са възстановени по догадка.
- **Native AOT файл в ILSpy.** Няма IL; ползвай родните инструменти.

## Упражнение
1. Компилирай програмата от урока и намери `BSJB` и петте потока със скрипт.
2. Разгледай IL на `Push` и обясни как се компилира `items[sp++] = v`.
3. Сравни IL на `Mul` при `-optimize-` и `-optimize+`.
4. Напиши `Mul` на Java и Python и сравни разглобяванията.

## Бърза справка
- Тип файл: `file app.dll` показва PE32 с CLI заглавие (Mono/.Net assembly).
- Низове в UTF-16: `strings -el -n 4 app.dll`.
- Подпис на метаданните: байтовете `42 53 4A 42` (`BSJB`).
- Командата за разглобяване на Java: `javap -c -p M`.
- Командата за Python: `python3 -c "import dis; dis.dis(f)"`.
- Native AOT: `dotnet publish -r linux-x64 -c Release` с `<PublishAot>true</PublishAot>`.
- ReadyToRun: `<PublishReadyToRun>true</PublishReadyToRun>`.

## Речник
- **Управляван код (managed code)** – код, който се изпълнява под надзора на CLR: със следене на типове, сметосъбирач и изключения.
- **CLR (Common Language Runtime)** – изпълнителната среда на .NET, която зарежда сглобки и ги компилира до машинен код.
- **IL / CIL (Intermediate Language)** – стековият междинен език, в който компилаторите на .NET записват програмата.
- **Сглобка (assembly)** – .NET файлът `.dll` или `.exe` с IL, метаданни и ресурси.
- **Метаданни (metadata)** – таблици и потоци, които описват типовете, методите, полетата и сигнатурите в сглобката.
- **Маркер (metadata token)** – 32-битово число, което посочва ред в таблица на метаданните (например `0x06000004` е методът `Mul`).
- **JIT компилатор (just-in-time compiler)** – превежда IL в машинен код по време на изпълнение.
- **ReadyToRun (R2R)** – режим, при който сглобката носи и предкомпилиран машинен код, без да губи IL.
- **Native AOT (ahead-of-time)** – пълна предварителна компилация до родна програма, без IL и без JIT.
- **Обфускация (obfuscation)** – преименуване и преобразуване на кода, за да е по-труден за четене; тук само я разпознаваш.

## Обобщение
.NET файлът е PE контейнер с IL и пълни метаданни, затова декомпилаторите като ILSpy го връщат близо до оригиналния C#, а IL остава крайният източник на истина. Потоците `#Strings` и `#US` и таблиците с маркери ти дават имената и текстовете, а IL се чете като стекова програма. ReadyToRun запазва IL, докато Native AOT го премахва и връща анализа към родните инструменти. Java байткодът и Python `.pyc` са близки роднини със същата идея, но с различно богатство на типовете и стабилност на формата.
