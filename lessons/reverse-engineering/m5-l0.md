## Подготовка: собствено учебно приложение
Не ти трябва Android Studio. Нужни са JDK, `android.jar` на една платформа и инструментите за изграждане (`dx` или `d8`, `aapt2`, `zipalign`, `apksigner`). Във Debian/Ubuntu те идват от пакетите `android-sdk-build-tools`, `android-sdk-platform-23`, `apktool`, `smali` и `dexdump`. Приложението е малко: една активност и метод `score`, който смята сума по низ.

```
package bg.lab.hello;
public class MainActivity extends Activity {
    private static final String GREETING = "Здравей от собствено приложение";
    static int score(String name, int level) {
        int s = 0;
        for (int i = 0; i < name.length(); i++) s += name.charAt(i) * (i + 1);
        return level > 3 ? s * 2 : s;
    }
    protected void onCreate(Bundle b) { /* показва GREETING + score("lab", 5) */ }
}
```

Веригата за изграждане е същата, която прави Gradle, само че ръчно:

```
javac --release 8 -cp android.jar -d cls src/.../MainActivity.java
dx --dex --output=classes.dex cls
aapt2 compile --dir res -o res.zip
aapt2 link -o base.apk -I android.jar --manifest AndroidManifest.xml res.zip
zip base.apk classes.dex ; zipalign -f 4 base.apk al.apk
keytool -genkeypair -keystore lab.jks -alias lab -keyalg RSA -keysize 2048 -validity 365 -dname "CN=Lab"
apksigner sign --ks lab.jks --out lab.apk al.apk
```

`javac` дава `.class`, `dx` ги превръща в DEX, `aapt2` кодира манифеста и ресурсите в двоичен вид, `zipalign` подравнява записите, а `apksigner` слага подпис. В реален проект това върши Android Gradle Plugin с D8 и R8.

## Какво е APK и какво е AAB
**APK** (Android Package) е обикновен ZIP архив. Ето истинският списък на нашия пакет:

```
$ unzip -l lab.apk
  Length   Name
    1712   AndroidManifest.xml
      40   resources.arsc
    1544   classes.dex
     412   META-INF/LAB.SF
    1098   META-INF/LAB.RSA
     285   META-INF/MANIFEST.MF
```

**AAB** (Android App Bundle) е формат за **публикуване**, не за инсталиране. Разработчикът качва `.aab` в магазина, а магазинът генерира от него APK файлове за конкретното устройство. Затова на телефона често има **разделени APK** (split APKs): основен `base.apk` плюс отделни пакети за архитектура (`arm64_v8a`), плътност на екрана и език. Ако ти трябва пълно приложение за анализ, отнасяш се към всички части, а не само към `base.apk`. Собствен `.aab` се превръща в APK с инструмента `bundletool`.

| Елемент | Съдържание | Какво търсиш |
|---|---|---|
| `AndroidManifest.xml` | Двоичен XML: пакет, разрешения, компоненти | Разрешения, експортирани компоненти, `debuggable` |
| `classes.dex`, `classes2.dex` | Изпълним код за ART | Класове, методи, низове |
| `resources.arsc` | Компилирана таблица на ресурсите | Имена, низове, оформления |
| `res/` | Компилирани XML оформления и изображения | Идентификатори на екрани |
| `lib/<abi>/*.so` | Роден код (JNI) за всяка архитектура | Анализ с Ghidra |
| `META-INF/` | Подписи (схема v1) | Сертификат, хешове |

APK е ZIP, затова `unzip` вече дава първия триаж.

## Манифестът: първото, което четеш
В пакета манифестът е двоичен (AXML) и не се чете с `cat`. Инструментът `aapt` го показва:

```
$ aapt dump badging lab.apk
package: name='bg.lab.hello' versionCode='1' versionName='1.0'
sdkVersion:'23'
targetSdkVersion:'23'
uses-permission: name='android.permission.INTERNET'
application-debuggable
launchable-activity: name='bg.lab.hello.MainActivity'
```

Пълното дърво е с `aapt dump xmltree lab.apk AndroidManifest.xml`. Два реда са сигнал: `uses-permission` (какво иска приложението от системата) и `application-debuggable`. Флагът `debuggable` позволява закачане на дебъгер към приложението. При издание той трябва да е изключен; затова в нашето учебно приложение го виждаме нарочно.

Още четеш компонентите (`activity`, `service`, `receiver`, `provider`), `android:exported` (достъпен ли е отвън), `intent-filter`, `allowBackup` и `usesCleartextTraffic`.

В анализа на собствено приложение това е и одит: компонент с `exported="true"`, който не трябва да е такъв, е грешка, която поправяш.

## От Java към DEX: какво се случва с кода
Android не изпълнява Java байткод (`.class`) направо. D8 (по-рано `dx`) обединява всички класове в един или няколко **DEX** файла (Dalvik Executable). Разликата е важна за разбирането:

- Java VM е **стекова** машина: операндите са на стек, както във виртуалната машина `vm` от курса.
- DEX е **регистрова** машина: инструкциите работят с виртуални регистри `v0`, `v1`, ... и параметри `p0`, `p1`, ...
- Един `.class` файл има собствен пул от константи; DEX обединява низовете, типовете и методите на целия пакет в общи таблици. Така файлът е по-компактен.

Първо Java байткодът на нашия `score`, реален изход на `javap -c -p`:

```
static int score(java.lang.String, int);
   0: iconst_0
   1: istore_2
   4: iload_3
   6: invokevirtual #7    // Method java/lang/String.length:()I
   9: if_icmpge     30
  15: invokevirtual #13   // Method java/lang/String.charAt:(I)C
  21: imul
  22: iadd
  32: if_icmple     41
  37: imul
  42: ireturn
```

А това е същият метод в DEX, преведен до smali с `baksmali d classes.dex -o smali`:

```
.method static score(Ljava/lang/String;I)I
    .registers 6
    const/4 v1, 0x0
    move v0, v1
    move v2, v1
    :goto_3
    invoke-virtual {p0}, Ljava/lang/String;->length()I
    move-result v1
    if-ge v0, v1, :cond_15
    invoke-virtual {p0, v0}, Ljava/lang/String;->charAt(I)C
    move-result v1
    add-int/lit8 v3, v0, 0x1
    mul-int/2addr v1, v3
    add-int/2addr v1, v2
    add-int/lit8 v0, v0, 0x1
    move v2, v1
    goto :goto_3
    :cond_15
    const/4 v0, 0x3
    if-le p1, v0, :cond_1a
    mul-int/lit8 v2, v2, 0x2
    :cond_1a
    return v2
.end method
```

(Редовете `.line` и празните са махнати; в изхода на javap са оставени само ключовите инструкции.) Сравни двата списъка. Стековите `iload`/`istore` изчезнаха: сумата `s` е в `v2`, индексът `i` в `v0`, параметърът `name` е `p0`, а `level` е `p1`. `.registers 6` значи шест регистъра общо: `v0`–`v3` са локални, а `p0`/`p1` са последните два (`v4`, `v5`). Резултатът от извикването се взема отделна инструкция `move-result`, докато в JVM той остава на стека. Същата функция през `dexdump -d` показва суровите байтове, а числата от вида `method@0009` са индекси в таблиците на DEX, не адреси.

### Нотация на типовете в smali
| Запис | Значение |
|---|---|
| `V`, `Z`, `B`, `S`, `C`, `I`, `J`, `F`, `D` | void, boolean, byte, short, char, int, long, float, double |
| `Ljava/lang/String;` | Клас `java.lang.String` |
| `[I` | Масив от `int` |
| `->` | Достъп до член: `Lклас;->метод(параметри)връщане` |
| `v0..vN`, `p0..pN` | Локални регистри и параметри |
| `.registers`, `.locals` | Общ брой регистри или само локалните |
| `:cond_N`, `:goto_N` | Етикети за преходи |

Най-честите инструкции са `const`, `move`, `invoke-*` (virtual, static, direct, interface), `iget`/`iput`/`sget`/`sput` за полета, `if-*` за преходи и `add-int`, `mul-int` за аритметика.

Заглавието на DEX файла също се чете. `dexdump -f` показва: `magic: 'dex\n035\0'`, `file_size: 1544`, `header_size: 112`, `string_ids_size: 32`, `type_ids_size: 12`. Магията `dex\n035\0` казва версията на формата; контролната сума и подписът (SHA-1) покриват останалото.

## ART: кой изпълнява DEX
Първоначално DEX се изпълняваше в **Dalvik**; от Android 5.0 заместител е **ART** (Android Runtime), който първоначално компилираше всичко при инсталиране (AOT), а след Android 7.0 комбинира интерпретатор, JIT и AOT по профил: горещите методи се компилират по-късно, докато устройството е свободно. Следствията за теб:

- Файловете в `/data/app/.../oat/` като `.odex`, `.vdex` и `.art` са **кеш на устройството**, получен от DEX. Те не са оригиналният код и не са това, което разработчикът е пратил.
- За статичен анализ работиш с `classes.dex` от самия пакет, а не с оптимизирания роден код.
- Рефлексията, `DexClassLoader` и JNI скриват повиквания от статичния анализ; решава се с динамичен анализ на собствено приложение.

## jadx: от DEX към четим Java
**jadx** (Apache-2.0, проект с отворен код) декомпилира DEX до Java. Има команден вариант `jadx` и графичен `jadx-gui`. Основните употреби:

```
jadx -d out lab.apk          # изходни файлове и ресурси в out/
jadx-gui lab.apk             # навигация, търсене, преименуване
jadx --show-bad-code -d out lab.apk   # показва и кода, който не може да се възстанови напълно
```

Няма jadx в средата, в която е писан този урок, затова командите по-горе са по документацията му, а не от реален изход. Ето какво да очакваш за `score`: четим цикъл `for` с `charAt`, но с имена на променливи като `i2`, `i3`, ако няма отладъчна информация. Ако пакетът е компилиран с `-g` (или `debuggable`), jadx може да вземе имената от `.local`/`.line` метаданните.

Силните страни на jadx са: бърз преглед на структурата, търсене по низове и по класове, навигация „кой извиква този метод“ и преименуване, което се помни в проекта. Слабите: при оптимизиран, обфусциран или нестандартен байткод някои методи излизат като коментар `Code restructure failed` или като `/* JADX WARN */`. В такъв случай не вярвай на Java изхода, а слез на smali. Това е същото правило като в курса за Ghidra: декомпилаторът е хипотеза, дизасемблерът е истина.

## Apktool: разопаковане с ресурси и smali
**Apktool** (Apache-2.0) разопакова ресурсите до четим вид и превежда DEX в smali чрез smali/baksmali. Върху нашия пакет:

```
$ apktool d lab.apk -o apk_out
I: Loading resource table...
Exception in thread "main" brut.androlib.AndrolibException:
  arsc files with zero packages or no arsc file found.
```

Това е реален изход и нещо поучително: нашият учебен пакет няма собствени ресурси, а таблицата `resources.arsc` е празна (40 байта). Apktool 2.7 не знае какво да прави с таблица без пакети. Заобикаляме с `-r` (не декодирай ресурсите):

```
$ apktool d -r lab.apk -o apk_r
I: Copying raw resources...
I: Baksmaling classes.dex...
$ ls apk_r
AndroidManifest.xml  apktool.yml  original  resources.arsc  smali
$ ls apk_r/smali/bg/lab/hello
MainActivity.smali
```

Файлът `apktool.yml` пази метаданните, нужни за сглобяване: `minSdkVersion: '23'`, `compressionType: false`, `doNotCompress: [resources.arsc]`. В реален проект с ресурси `apktool d` дава и `res/` с четим XML, и манифест като обикновен текст. Сглобяването със `apktool b` е удобно за **собствено** приложение, например когато искаш да добавиш логване на свой build. Подпис след промяна е винаги нужен, защото старият вече не съвпада.

| Задача | jadx | Apktool | baksmali/smali | dexdump |
|---|---|---|---|---|
| Четим Java | да | не | не | не |
| smali | не | да | да | не (суров дизасемблер) |
| Декодиране на ресурси и манифест | да | да | не | не |
| Сглобяване обратно | не | да | да (smali) | не |
| Лиценз | Apache-2.0 | Apache-2.0 | BSD | част от Android SDK |

Препоръчан ред на работа: триаж с `unzip` и `aapt`, преглед с jadx, а когато декомпилаторът се провали или трябва точен поглед върху поведението, smali от Apktool. Алтернативи на jadx са Bytecode Viewer и Ghidra (зарежда DEX и APK).

## Подписване на общо ниво
Android не инсталира неподписан пакет. Подписът служи за две неща: **цялост** (пакетът не е променян) и **идентичност** (същият издател, при обновяване). Версиите на схемата са няколко: v1 (подписан JAR, файловете в `META-INF/`), v2 (подпис над целия ZIP от Android 7.0), v3 (с ротация на ключове, Android 9) и v4 (допълнителен файл за поточно инсталиране). Така `apksigner` отчита за нашия пакет:

```
$ apksigner verify --verbose lab.apk
Verifies
Verified using v1 scheme (JAR signing): true
Verified using v2 scheme (APK Signature Scheme v2): true
Verified using v3 scheme (APK Signature Scheme v3): true
Verified using v4 scheme (APK Signature Scheme v4): false
Number of signers: 1
```

Следствие, което обяснява много от анализа: **промяна в пакета чупи подписа**. Затова сменен пакет е друг пакет от гледна точка на системата, с друг ключ. Подписването на собствено приложение със собствен ключ е нормално. Промяна на чужд подпис, подправяне на сертификат и заобикаляне на проверки са извън курса.

## R8, ProGuard и обфускацията
При издание Android Gradle Plugin пуска **R8**: компилатор, който **смалява** кода (премахва неизползвано), **оптимизира** (вмъква методи, опростява потока) и **преименува** (obfuscation) класове, методи и полета. Правилата идват от файл `proguard-rules.pro`. R8 е по подразбиране от Android Gradle Plugin 3.4; преди това се ползваше **ProGuard** и форматът на правилата остава същият. Тези преименувания са обратими само ако пазиш файла `mapping.txt`, който генерира сборката.

| Признак в jadx/smali | Какво означава |
|---|---|
| Класове `a.a.a`, методи `a()`, `b()` | Преименуване от R8 или ProGuard |
| Липсващи `.line` и имена на локални променливи | Без отладъчна информация |
| Низове, декодирани по време на изпълнение | Допълнителна защита на низове, не е част от R8 |
| Само няколко класа и огромен роден код | Логиката е в `lib/*.so` |

Какво се запазва и при R8: **имената на системните класове** (`android.*`, `java.*`), низовите константи, структурата на разрешенията и компонентите (те са в манифеста, а R8 не пипа имената на компонентите, регистрирани там). Затова навигацията от манифеста към входните точки работи и в обфусциран пакет. 

## Kotlin в байткода
Повечето съвременни приложения са на Kotlin. В байткода това личи по няколко признака:

- Анотация `kotlin.Metadata` на всеки клас и пакети `kotlin.*` и `kotlin.jvm.internal.*`.
- Извиквания на `Intrinsics.checkNotNullParameter(...)` в началото на методи с ненулеви параметри (при R8 те често се премахват).
- Корутини: методи с параметър `Continuation`, и клас-автомат с поле `label` и метод `invokeSuspend`. В jadx това са сложни `switch` по `label`; реалната логика е между преходите на състояния.

Jadx понякога връща Kotlin като Java, която не би се компилирала. Това не е грешка в приложението, а ограничение на превода от автомати към `switch`.

## JNI: когато логиката е в роден код
**JNI** (Java Native Interface) свързва Java/Kotlin с C/C++. В кода се вижда деклариран метод `native`, и `System.loadLibrary("име")`. Самата библиотека лежи в `lib/<abi>/libиме.so`, например `arm64-v8a` или `x86_64`. Как намираш роден метод:

1. В jadx: метод с модификатор `native` без тяло.
2. В `.so`: функции с имена `Java_<пакет>_<клас>_<метод>`, например `Java_bg_lab_hello_Native_check`, ако са регистрирани статично. При `RegisterNatives` в `JNI_OnLoad` връзката се прави по таблица и името на функцията е произволно.
3. Първите два параметъра на роден метод са `JNIEnv*` и `jobject` (или `jclass` при статичен); останалите са параметрите от Java.
4. `.so` файловете са ELF и се анализират като всеки ELF: `readelf`, `nm -D`, Ghidra (виж курса за Ghidra и модул 3 на този курс). В Ghidra има типови файлове за JNI (`jni_all.h`), които правят извикванията през `JNIEnv` четими.


## Стъпка по стъпка
1. Триаж: `unzip -l`, брой `classes*.dex`, наличие на `lib/` и `assets/`.
2. Манифест с `aapt dump badging`: разрешения, компоненти, `exported`, `debuggable`.
3. Подпис с `apksigner verify --verbose`.
4. jadx: тръгни от входните точки от манифеста и следвай данните.
5. При `JADX WARN` слез на smali; при `native` продължи в Ghidra върху `.so`.
6. Провери хипотезите динамично върху собственото приложение.

## Чести грешки
- Четеш `.odex`/`.vdex` от устройство вместо `classes.dex` от пакета.
- Вярваш на jadx при метод с `JADX WARN`, без да провериш smali.
- Търсиш логиката в Java, а тя е в `lib/*.so`.

3. С `dexdump -f` сравни `string_ids_size` преди и след добавяне на низ.
4. Напиши метод с `switch` над три стойности. Сравни `javap -c` (`tableswitch`/`lookupswitch`) със smali (`packed-switch`/`sparse-switch`).
6. Ако имаш проект с отворен код на Android (например малко приложение от F-Droid), отвори го в jadx и проследи една активност от манифеста до ресурс.

## Бърза справка
| Задача | Команда |
|---|---|
| Съдържание на пакета | `unzip -l app.apk` |
| Манифест и разрешения | `aapt dump badging app.apk` |
| Дърво на манифеста | `aapt dump xmltree app.apk AndroidManifest.xml` |
| Проверка на подписа | `apksigner verify --verbose app.apk` |
| Заглавие на DEX | `dexdump -f app.apk` |
| Дизасемблиране на DEX | `dexdump -d app.apk` |
| DEX към smali | `baksmali d classes.dex -o smali` |
| smali към DEX | `smali a smali -o classes.dex` |
| Разопаковане | `apktool d app.apk -o out` (`-r` без ресурси) |
| Декомпилация | `jadx -d out app.apk` |
| Байткод на Java клас | `javap -c -p -cp cls име.на.Клас` |
| Подравняване | `zipalign -f 4 in.apk out.apk` |
| Подпис със собствен ключ | `apksigner sign --ks ключ.jks --out app.apk in.apk` |

## Речник
- **APK** (Android Package) – ZIP пакет с код, ресурси и подпис, който се инсталира на устройство.
- **AAB** (Android App Bundle) – формат за публикуване, от който магазинът генерира APK за конкретно устройство.
- **DEX** (Dalvik Executable) – формат на регистров байткод за Android, обединяващ класовете на пакета.
- **smali** (smali) – четим текстов запис на DEX инструкции, получен с baksmali.
- **ART** (Android Runtime) – средата, която изпълнява DEX с интерпретатор, JIT и AOT компилация.
- **Манифест** (manifest) – двоичен XML файл с пакета, разрешенията и компонентите на приложението.
- **R8** (R8) – компилаторът на Google, който смалява, оптимизира и преименува кода при издание.
- **ProGuard** (ProGuard) – по-старият оптимизатор и обфускатор, чийто формат на правила R8 използва.
- **JNI** (Java Native Interface) – интерфейс за извикване на роден C/C++ код от Java или Kotlin.
- **Подпис на APK** (APK signing) – криптографски подпис на пакета, който доказва цялост и идентичност на издателя.
- **Разделени APK** (split APKs) – набор от пакети (основен плюс по архитектура, език и плътност), инсталирани заедно.
- **apktool** (Apktool) – инструмент за разопаковане на ресурси и превод на DEX в smali и обратно.

## Обобщение
APK е ZIP; манифестът ти казва какво има и къде да започнеш; DEX е регистров байткод, който се чете като smali; jadx дава бърз Java изглед, а Apktool дава точния smali и ресурси. R8 преименува, но не променя структурата на манифеста, а Kotlin и JNI имат ясни следи. Подписът прави всяка промяна на пакета нова идентичност. Всичко това е за собствени приложения и отворен код.
