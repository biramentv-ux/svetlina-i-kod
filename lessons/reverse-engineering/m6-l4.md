### Етап 1: обхват и лаборатория
Отвори чиста виртуална машина със снимка на състоянието. Запиши петте неща от урока за методиката: обект, основание, въпрос, граници, бюджет. Добър въпрос за проекта, който пасва на всяка програма с вход: „Какъв е форматът на входа, как се валидира и може ли неочакван вход да наруши паметта на програмата?“. Компилирай програмата в три варианта и ги пази отделно:

```
$ gcc -O0 -g -o vm vm.c          # с отладъчна информация, за сравнение
$ gcc -O2 -s -o vm_o2 vm.c       # оптимизиран и без символи: това анализираш
$ sha256sum vm vm_o2 | cut -c1-16
6da9c9b68525d7f8
...
```

Анализираш първо варианта `-O2 -s`: той е най-близо до реалността; `-O0 -g` служи само за проверка в етап 5.

### Етап 2: триаж
Тук прилагаш урока за триажа. Събираш факти, без да правиш изводи:

```
$ file vm
vm: ELF 64-bit LSB pie executable, x86-64, dynamically linked
$ readelf -h vm | grep -E 'Type|Entry'
  Type:                              DYN (Position-Independent Executable file)
  Entry point address:               0x1140
$ readelf -lW vm | grep -E 'GNU_STACK|GNU_RELRO'
  GNU_STACK      ... RW  0x10
  GNU_RELRO      ... R   0x1
$ readelf -d vm | grep -E 'BIND_NOW'
 0x000000006ffffffb (FLAGS_1)            Flags: NOW PIE
$ strings -e S -n 4 vm | grep -i 'PV\|ползв'
ползване: %s файл.prog
```

Факти: 64-битов PIE, стекът не е изпълним, RELRO е пълен. Капан: обикновеният `strings` не показва кирилица без `-e S`. Низът „ползване“ подсказва, че програмата иска файл като аргумент.

### Етап 3: статичен анализ
Изгради карта на функциите. В обикновения `-O0` вариант `nm` показва имената; в stripped вариантът ги няма и ти ги именуваш сам.

```
$ nm vm | grep -E ' [tT] '
000000000000145a T main
0000000000001229 t run
$ objdump -d vm --no-show-raw-insn | awk '/<run>:/,/ret/' | grep -E 'jmp.*\*|ja '
    12b6:	ja     13fa <run+0x1d1>
    12dc:	notrack jmp *%rax
```

Двойката `ja` + `jmp *%rax` е типичният отпечатък на `switch`, компилиран като таблица за преход: `ja` проверява дали стойността е в границите, `jmp *%rax` скача през таблицата. Така разпознаваш диспечер на инструкции: функция с голям `switch` над байт, прочетен от входа, е почти сигурно интерпретатор. Това е **хипотеза**, а не факт, и влиза в протокола с ниска увереност до потвърждение.

Задачи: намери къде се чете и проверява входът (магия, дължина, контролна сума), опиши формата поле по поле, именувай функциите със записана увереност и състави въпроси за динамичния етап.

### Етап 4: динамичен анализ
Потвърждавай всяка хипотеза с наблюдение. С GDB спираш на функцията и гледаш аргументите:

```
$ gdb -q -batch -ex 'break run' -ex 'run ok.prog' -ex 'info args' ./vm
Breakpoint 1, run (code=0x7fffffff5f95 "\001\002\001\003\002", n=6) at vm.c:10
code = 0x7fffffff5f95 "\001\002\001\003\002"
n = 6
```

Стойността `n = 6` съвпада с шестте инструкции във входния файл: хипотезата „петият байт е брой инструкции“ е потвърдена. Подобно, `strace` и `ltrace` показват кои файлове се отварят и какви библиотечни функции се викат; за една програма като тази достатъчен е кратък списък от `openat` и `read`. Всяка проверка се записва като ред: хипотеза, как е проверена, резултат, увереност (ниска, средна, висока), както в таблицата от урока за методиката.

Тестовите входове генерирай със скрипт, не на ръка. Входът `ok.prog` изчислява (2+3)·4 и програмата отпечатва `20`. Шестнадесетичното представяне потвърждава описанието на формата:

```
$ xxd ok.prog
00000000: 5056 3031 0601 0201 0302 0001 0403 0005  PV01............
00000010: 0001                                     ..
```

### Етап 6: грешки и поправка
Всяка програма с вход от външния свят заслужава въпроса „какво става при невярен вход?“. Компилирай с проверки по време на изпълнение:

```
$ gcc -g -O0 -fsanitize=address,undefined -o vm_asan vm.c
$ ./vm_asan over.prog
vm.c:15:32: runtime error: index 64 out of bounds for type 'int [64]'
ERROR: AddressSanitizer: stack-buffer-overflow ... WRITE of size 4
$ ./vm_asan under.prog
vm.c:16:46: runtime error: index -2 out of bounds for type 'int [64]'
ERROR: AddressSanitizer: stack-buffer-underflow ... READ of size 4
```

Двата входа са валидни за формата (верни магия и контролна сума): 80 инструкции `PUSH`, съответно три `ADD` без операнди. Контрастът е поучителен: `./vm over.prog` завършва със `*** stack smashing detected ***` и код 134 (защита на компилатора), а `./vm under.prog` завършва с код 0 без предупреждение: мълчаливо неопределено поведение. Заключение за отчета: защитите на компилатора намират част от проблема, не цялото; причината е липсата на проверка на `sp` в интерпретатора, а не във формата.

Поправката е локална: проверка преди изпълнение на всяка инструкция и проверка, че броят инструкции се побира във файла.

```
if ((op == OP_PUSH && sp >= 64) ||
    ((op == OP_ADD || op == OP_MUL || op == OP_SUB) && sp < 2) ||
    (op == OP_PRINT && sp < 1)) {
    fprintf(stderr, "грешка на стека при инструкция %d\n", i); return 1;
}
```

плюс в `main`: `if (5 + (size_t)n*2 + 1 > len)` отказ със „съкратен файл“. Проверка с поправената версия под санитайзери:

```
$ for p in ok under over big; do ./vm_fixed $p.prog; echo "$p rc=$?"; done
20
ok rc=0
грешка на стека при инструкция 0
under rc=1
грешка на стека при инструкция 64
over rc=1
грешка на стека при инструкция 64
big rc=1
```

Доказателството: старите входи, които сриваха програмата, вече завършват с контролиран отказ, а нормалният вход дава пак `20`. Добави регресионен тест, сравни версиите с `radiff2` или `objdump` плюс `diff` (урока за сравняване) и по желание пусни фъзер върху **собствената** програма; целта е поправка, не експлойт.

## Чести грешки
- **Започваш със сорса** – тогава няма какво да проверяваш. Запечатай го.
- **Анализираш `-O0 -g`** – така пропускаш реалната трудност. Основният двоичен файл е без символи.
- **Отчет без доказателства** – „изглежда като интерпретатор“ не е резултат. Покажи команда и изход.
- **Поправка без тест** – „поправих го“ не се приема; нужни са вход, който сриваше, и същият вход след поправката.
- **Излизане от границите** – анализ на чужд софтуер или превръщане на срив в атака не са част от проекта.

## Речник
- **Основание (authorization basis)** – записаното право да анализираш обекта: собствен код, отворен код, CTF или разрешение.
- **Хипотеза (hypothesis)** – твърдение за програмата, което може да се окаже грешно и има метод за проверка.
- **Увереност (confidence)** – оценка колко добре е подкрепена хипотезата с доказателства.
- **Запечатан сорс (sealed source)** – изходният код, който не отваряш, докато анализът е в ход.
- **Санитайзер (sanitizer)** – вграден в компилатора контрол, който улавя грешки по време на изпълнение.
- **Регресионен тест (regression test)** – вход, който доказва, че поправката не разваля старото поведение.
- **Възпроизводимост (reproducibility)** – възможност друг човек да получи същия резултат по описанието.
- **Преглед от колега (peer review)** – проверка на отчета от друг човек преди предаване.
- **Калибрация (calibration)** – съответствие между казаната увереност и реалния дял верни твърдения.
- **Диспечер (dispatcher)** – код, избиращ действие по код на инструкция, обикновено `switch`.
