## Защо ВМ и какво значи „изолирана“
Анализаторът пуска програми, на които не е сигурен как ще се държат. Дори собствената ти програма може да има грешка, която изтрива файлове или зарежда процесора. Затова работата се върши в **виртуална машина (virtual machine, ВМ)**: компютър, емулиран от програма, който можеш да върнеш към предишно състояние с един клик.

Изолацията има три слоя. Първият е самата ВМ с отделен диск. Вторият е мрежата: за курса използвай режим „само за домакина“ (host-only) или напълно изключена мрежа, а връзка към интернет включвай само докато инсталираш пакети. Третият е споделянето: изключи споделените папки, споделения клипборд и плъзгането на файлове, докато работиш с подозрителни мостри. Тези три настройки пречат на програмата да излезе от машината, дори да е зловредна.

Контейнерът (например Docker) **не е** заместител на ВМ за този курс. Той споделя ядрото със системата-домакин, а за дебъгване с `ptrace`, за `strace` и за зареждане на модули често му трябват отслабени защити. За работа със зловреден код ВМ с отделно ядро е минималното разумно ниво. Контейнерът става за бързо компилиране и за пускане на инструмент, на който нямаш доверие в основната си система.

Препоръчителна конфигурация: Ubuntu 24.04 LTS (64-битова), 4 ядра, 8 GB памет (4 GB е минимум), диск 60 GB. Ако домакинът е Apple Silicon или ARM, ВМ ще е AArch64 и част от примерите в курса ще дават различен асемблер. За x86-64 примерите ползвай емулация (QEMU) или компютър с x86-64.

Правилото за снимките (snapshots) е просто: направи **чиста снимка** веднага след инсталацията („lab-clean“) и втора преди всеки експеримент с мостра. След експеримента се връщаш назад, вместо да „чистиш“ ръчно.

## Какво идва от дистрибуцията и какво се сваля ръчно
В Ubuntu 24.04 повечето нужни неща са пакети. Не е така за Ghidra, jadx, ImHex, Cutter, Rizin и ILSpy: те се свалят от страниците на проектите. Пакетът `radare2` в хранилището на Ubuntu 24.04 е стара версия (5.5.0 към момента на писането), затова за актуална версия ползвай изданията на проекта. Командите в курса работят и със старата, но изходът може да се различава леко.

За свалените ръчно програми важи правило: **проверявай хеша**. Страницата с изданието обикновено публикува SHA-256. Ако не съвпада, не отваряй файла.

## Стъпка по стъпка: инсталиране в Ubuntu 24.04
1. **Създай ВМ**, инсталирай Ubuntu 24.04 и обнови системата. Направи снимка „lab-base“.

```
sudo apt update && sudo apt full-upgrade -y
```

2. **Компилатори и системни помощни програми.**

```
sudo apt install -y build-essential gcc-multilib clang llvm libfuzzer-18-dev \
  gcc-aarch64-linux-gnu binutils-aarch64-linux-gnu gcc-mingw-w64-x86-64 \
  git cmake unzip p7zip-full cpio patchelf elfutils checksec
```

3. **Триаж, дебъгване и трасиране.**

```
sudo apt install -y file xxd hexedit vbindiff ssdeep yara gdb gdbserver \
  gdb-multiarch libc6-dbg strace ltrace valgrind bpftrace
```

4. **Емулация, мрежа, фъзинг, фърмуер.**

```
sudo apt install -y qemu-user qemu-system-x86 qemu-system-arm tshark afl++ \
  upx-ucl binwalk squashfs-tools
```

Инсталаторът на `tshark` може да попита дали обикновени потребители да прихващат пакети. Отговори „не“ и работи с `sudo`, когато ти трябва.

5. **Java и .NET** (нужни за jadx, Apktool, Ghidra и ILSpy).

```
sudo apt install -y openjdk-21-jdk-headless apktool dotnet-sdk-8.0
```

Ghidra изисква 64-битов JDK, като минималната версия зависи от изданието: според файловете README на изданията 12.0 и 12.1 искат JDK 21, а 12.2 иска JDK 25. Затова прочети README на изданието, което свалиш, и инсталирай JDK, който то посочва.

6. **Python среда за библиотеките.** Отделна виртуална среда не замърсява системния Python.

```
sudo apt install -y python3-pip python3-venv
python3 -m venv ~/venv/re && . ~/venv/re/bin/activate
pip install capstone keystone-engine unicorn pefile pyelftools lief yara-python \
  angr frida-tools r2pipe z3-solver kaitaistruct oletools
```

Резултатът от `pip install --dry-run` върху тези имена потвърждава, че всички пакети съществуват в индекса: например capstone 5.0.9, unicorn, lief 1.0.0, frida-tools 14.13.1 и kaitaistruct 0.11.

7. **Ръчно свалени програми:** Ghidra, jadx, ImHex, Detect It Easy, Cutter, а при желание Wireshark (графичен), ILSpy и актуалният radare2. Свали, свер*/SHA-256 и разархивирай в `~/tools`.

```
cd ~/tools && sha256sum -c ghidra.sha256   # или сравни ръчно с публикувания хеш
```

8. **Направи снимка „lab-clean“**, изключи мрежата (или я сложи на host-only) и започни работа.

Ядрото на скрипта е една функция. Останалото са редове `check команда аргумент`.

```bash
#!/usr/bin/env bash
check() {  # $1=команда  $2=аргумент за версия
  if command -v "$1" >/dev/null 2>&1; then
    v=$("$1" $2 2>&1 | grep -v -i -e "picked up" -e "dangerous" \
        | sed 's/\x1b\[[0-9;]*m//g' | grep -m1 -E '[0-9]')
    printf "  [OK]  %-12s %s\n" "$1" "$v"
  else
    printf "  [--]  %-12s липсва\n" "$1"
  fi
}
check gcc --version
check gdb --version
check radare2 -v
```

Две дребни подробности, които се видяха при писането му: `binwalk --help` започва с празен ред, затова търсим първия ред с цифра; а `afl-fuzz` и `tshark` печатят предупреждения и цветови кодове, които скриптът изчиства. Така „работи ли инструментът“ е различен въпрос от „какво печата“.

## Тест на лабораторията с учебната програма
Лабораторията не е готова, докато не компилира и не пусне `vm.c`. Копирай файла в работна папка (в курса: `lessons/_src/vm.c`), компилирай го и направи малък `.prog` файл. Форматът е: магия `PV01`, брой инструкции, двойки (код, операнд) и контролна сума XOR.

```
$ gcc -O0 -g -o vm vm.c
$ python3 - <<'E'
prog=[(1,2),(1,3),(2,0),(1,4),(3,0),(5,0)]   # (2+3)*4, после печат
b=b"PV01"+bytes([len(prog)])+b"".join(bytes(p) for p in prog)
c=0
for x in b: c^=x
open("demo.prog","wb").write(b+bytes([c]))
E
$ ./vm demo.prog
20
$ file vm
vm: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV), dynamically linked,
    interpreter /lib64/ld-linux-x86-64.so.2 ...
$ readelf -h vm | grep -E "Class|Entry"
  Class:                             ELF64
  Entry point address:               0x1140
```

Програмата смята (2+3)*4 и печата 20. Ако видиш това, компилаторът, Python и основните помощни програми работят. Забележка: входната точка 0x1140 е от нашата машина; при друг компилатор адресът може да е различен.

Още един малък урок от същата проверка. Низовете в `vm.c` са на български, записани в UTF-8, а `strings` по подразбиране търси само ASCII:

```
$ strings -n 4 vm | grep -c "лоша"
0
$ strings -e S -n 4 vm | grep -c "лоша"
3
```

Със `-e S` (еднобайтови символи, 8 бита) трите съобщения се появяват. Такива несъответствия на кодировката са честа причина „да не намериш“ низ, който е във файла.

## Мрежова изолация и безопасност
- За обикновени уроци е достатъчна ВМ с NAT и изключени споделени папки.
- За всичко с мостра, която не си писал ти: мрежа „само за домакина“ или без мрежа, снимка преди старта, и **отделна** ВМ за работа с такива файлове.
- Никога не поставяй в лабораторията реални пароли, ключове за облачни услуги или лични документи.
- Файлове между домакин и ВМ прехвърляй в архив с парола, а не чрез споделена папка, ако съдържанието е подозрително.
- Не пускай чужд зловреден код извън изолирана ВМ. Курсът работи със собствени програми и безвредни тестови файлове.

## Пример от практиката
Да кажем, че Мартин инсталира всичко в основната си система „за по-бързо“. На третия урок пуска програма с грешка, която записва в неправилна папка и презаписва конфигурационен файл на приложение, което ползва всеки ден. Връщане няма: нямал е снимка. Ако беше работил във ВМ, щеше да върне снимката „lab-clean“ за минута и да продължи. Урокът не е „пази се от зловреден код“, а „експериментите имат цена и снимката я намалява почти до нула“.

## Чести грешки
- **Работа в основната система** – всяка собствена грешка става реален проблем. Решение: ВМ и снимка „lab-clean“.
- **Включена мрежа и споделени папки при чужда мостра** – премахва смисъла на изолацията. Решение: host-only и отделна ВМ.
- **Сваляне от случайни сайтове с „кракнати“ копия на платени инструменти** – така често се разпространява зловреден код. Решение: безплатните и отворените алтернативи от таблиците са напълно достатъчни за курса.
- **Игнориране на хеша** – повреден или подменен архив се открива късно. Решение: `sha256sum` за всичко ръчно свалено.
- **Смесване на версии на Java** – Ghidra не стартира с по-стар JDK. Решение: прочети README на изданието и провери `java -version`.
- **Инсталиране на Python пакети в системния Python** – чупи системни инструменти. Решение: `python3 -m venv`.
- **Очакване, че `apt` ще даде най-новото** – версиите в Ubuntu 24.04 изостават (например radare2 5.5.0). Решение: за актуален инструмент ползвай изданията на проекта.

## Речник
- **Виртуална машина (virtual machine, ВМ)** – емулиран компютър, който работи като програма и може да се връща към запазено състояние.
- **Хипервизор (hypervisor)** – програмата, която създава и управлява виртуалните машини.
- **Снимка (snapshot)** – запазено състояние на диска и паметта на ВМ, към което можеш да се върнеш.
- **Host-only мрежа** – мрежов режим, в който ВМ комуникира само със системата-домакин, но не с интернет.
- **Хеш (hash)** – фиксирана контролна стойност на файл, която се променя при всяка промяна на съдържанието.
- **Размит хеш (fuzzy hash)** – хеш, който дава близки стойности за сходни файлове (ssdeep, TLSH).
- **Дистрибуция (distribution)** – набор от операционна система и пакети с общ мениджър на пакетите, например Ubuntu.
- **Виртуална среда (virtual environment, venv)** – отделна папка с Python пакети, която не засяга системния Python.
- **Крос-компилатор (cross-compiler)** – компилатор, който създава код за друга архитектура от тази на машината.
- **Лиценз с копилефт (copyleft)** – лиценз, който изисква производните работи да се разпространяват под същите условия (например GPL).
