> **Цел на урока:** да пишеш автоматични тестове с `pytest`, които проверяват функциите ти, включително граничните случаи, и да ги ползваш като мрежа за сигурност при промени.

## Какво ще научиш
- Защо ръчната проверка не е достатъчна и какво е автоматичен тест
- Как се пише тест с обикновен `assert` и как се пуска с `pytest`
- Как да четеш изхода на пропаднал тест
- Какво са гранични случаи и как да ги избираш
- Как да пишеш много проверки с `parametrize`, да проверяваш грешки с `pytest.raises` и да ползваш временни файлове с `tmp_path`

## Защо ти трябват тестове

Да кажем, че си написал функция за броене на думи и си я пробвал с два текста. Работи. След седмица добавяш поддръжка на нещо ново и променяш един ред. Как знаеш, че старото още работи? Можеш да пуснеш отново двата текста на ръка, но ще го направиш веднъж, после ще се откажеш.

**Автоматичният тест (automated test)** е малка програма, която вика твоята функция с известен вход и сравнява резултата с очаквания. Пускаш всичко с една команда и за секунда знаеш дали нещо се е счупило. Аналогия: преди излитане пилотът минава през контролен списък. Не го прави, защото не вярва на самолета, а защото паметта греши, а списъкът – не.

Тестовете имат и втора полза: те документират какво обещава функцията. Като четеш `test_empty_text`, разбираш какво се случва с празен текст, без да четеш кода.

## Първият тест

За обучението ползваме `pytest`, най-разпространената библиотека за тестове в Python. Ако още нямаш инсталиран, влез във виртуалната си среда от предишните уроци и пусни `python3 -m pip install pytest`. Ако на системата ти вече е налична, не е нужно нищо повече. Версиите в изходите по-долу са тези, с които пуснах примерите; твоята може да е по-нова.

Ето функциите, които ще тестваме, във файла `words.py`:

```python
import re

def count_words(text):
    """Връща речник дума -> брой, без значение от регистъра."""
    words = re.findall(r"\w+", text.lower())
    result = {}
    for w in words:
        result[w] = result.get(w, 0) + 1
    return result

def top_words(text, n=3):
    """Най-честите n думи като списък от двойки."""
    if n < 1:
        raise ValueError("n трябва да е поне 1")
    counts = count_words(text)
    return sorted(counts.items(), key=lambda p: (-p[1], p[0]))[:n]
```

Първият тест е във файл `test_words.py`:

```python
from words import count_words

def test_simple_count():
    assert count_words("а б а") == {"а": 2, "б": 1}
```

Правилата са три:
- Файлът започва с `test_` (или завършва с `_test`).
- Функцията започва с `test_`.
- Проверката е обикновен `assert`: „твърдя, че това е вярно“. Ако е невярно, тестът пропада.

Пускаш с:

```
$ python3 -m pytest
```

`pytest` сам намира файловете и функциите по имената им. Не е нужно да ги викаш ти.

## Пълният набор от тестове

Нека напишем няколко теста, които покриват различни ситуации:

```python
import pytest
from words import count_words, top_words

def test_simple_count():
    assert count_words("а б а") == {"а": 2, "б": 1}

def test_case_does_not_matter():
    assert count_words("София софия СОФИЯ") == {"софия": 3}

def test_empty_text():
    assert count_words("") == {}

def test_punctuation_is_ignored():
    assert count_words("Здравей, свят! Здравей.") == {"здравей": 2, "свят": 1}

def test_digits_count_as_words():
    assert count_words("2 пъти 2") == {"2": 2, "пъти": 1}
```

Пускаме и виждаме:

```
collected 10 items

test_words.py ..........                                                 [100%]

============================== 10 passed in 0.02s ==============================
```

Всяка точка е един успешен тест. Тук са 10, защото добавихме още тестове по-долу. С `-v` получаваш име на всеки:

```
test_words.py::test_simple_count PASSED                                  [ 10%]
test_words.py::test_case_does_not_matter PASSED                          [ 20%]
test_words.py::test_empty_text PASSED                                    [ 30%]
```

## Как изглежда пропаднал тест

Тестът, който никога не пропада, не е доказал нищо. Нека нарочно счупим функцията. Заменяме регулярния израз `\w+` с `[a-zа-я]+`, който забравя цифрите. Пускаме тестовете:

```
....F.....                                                               [100%]
=================================== FAILURES ===================================
__________________________ test_digits_count_as_words __________________________

    def test_digits_count_as_words():
>       assert count_words("2 пъти 2") == {"2": 2, "пъти": 1}
E       AssertionError: assert {'пъти': 1} == {'2': 2, 'пъти': 1}
E
E         Omitting 1 identical items, use -vv to show
E         Right contains 1 more item:
E         {'2': 2}
E         Use -v to get more diff

test_words.py:17: AssertionError
=========================== short test summary info ============================
FAILED test_words.py::test_digits_count_as_words - AssertionError: assert {'п...
1 failed, 9 passed in 0.02s
```

Чети го така:
1. **Буквата `F`** в реда с точките показва кой по ред тест е паднал.
2. **Знакът `>`** сочи реда с `assert`, който не е минал.
3. **Редовете с `E`** обясняват разликата: вляво е това, което върна функцията (`{'пъти': 1}`), а вдясно очакваното. `pytest` дори казва, че в очакваното има един елемент повече: `{'2': 2}`.
4. **Последният ред** е кратко резюме: 1 пропаднал, 9 минали.

Когато върнем `\w+`, всички тестове пак минават. Този цикъл – счупване, прочитане на съобщението, поправка – е целият смисъл. Тестът ни каза точно какво е изгубено.

## Гранични случаи

**Граничен случай (edge case)** е вход в края на допустимото или необичаен вход, при който програмите най-често се чупят. Ето какво да питаш за всяка функция:

| Въпрос | Пример за `count_words` |
|---|---|
| Какво става при празен вход? | `""` |
| Какво при един елемент? | `"а"` |
| Какво при повторения? | `"а а а"` |
| Има ли значение регистърът? | `"София СОФИЯ"` |
| Какво става със символи, които не са букви? | `"да, не!"` |
| Какво при числа? | `"2 пъти 2"` |
| Какво при невалидна стойност на параметър? | `top_words("а", 0)` |

Не е нужно да мислиш за милион случая. Достатъчни са 5–8 добре подбрани, за да хванеш повечето грешки. Практичното правило: един „нормален“ случай, празният, най-малкият, най-големият и поне един неправилен вход.

## Много случаи наведнъж: `parametrize`

Когато тестовете се различават само по данните, не пиши десет еднакви функции. Ползвай `parametrize`:

```python
@pytest.mark.parametrize("text, n, expected", [
    ("а а б", 1, [("а", 2)]),
    ("б а", 2, [("а", 1), ("б", 1)]),
    ("", 3, []),
])
def test_top_words(text, n, expected):
    assert top_words(text, n) == expected
```

Декораторът `@pytest.mark.parametrize` пуска функцията по веднъж за всеки ред от списъка. В изхода с `-v` виждаш три отделни теста:

```
test_words.py::test_top_words[а а б-1-expected0] PASSED   [ 60%]
test_words.py::test_top_words[б а-2-expected1] PASSED          [ 70%]
test_words.py::test_top_words[-3-expected2] PASSED                       [ 80%]
```

Кирилицата в имената на тестовете `pytest` показва като `а` – това е нормално и не е грешка. Ако един ред пропадне, ще знаеш точно кой.

## Проверка на грешки: `pytest.raises`

Функцията `top_words` обещава да откаже `n` по-малко от 1. Това обещание също се тества:

```python
def test_top_words_rejects_zero():
    with pytest.raises(ValueError, match="поне 1"):
        top_words("а б", 0)
```

Тестът минава само ако блокът вдигне `ValueError`, чието съобщение съдържа „поне 1“. Ако функцията не вдигне нищо, тестът пропада. Параметърът `match` не е задължителен, но не позволява да минеш с погрешна грешка.

## Временни файлове: `tmp_path`

Понякога функцията работи с файлове. Не искаш тестът да чете и пише в реалните ти папки. `pytest` ти дава готова временна папка, ако добавиш параметър `tmp_path`:

```python
def test_reads_from_file(tmp_path):
    f = tmp_path / "text.txt"
    f.write_text("да да не", encoding="utf-8")
    assert count_words(f.read_text(encoding="utf-8")) == {"да": 2, "не": 1}
```

Не викаш `tmp_path` сам: `pytest` го разпознава по името и го подава. Такива готови помощници се наричат **fixtures**. Папката се създава за теста, а старите временни папки pytest изтрива сам след време. Забележи `encoding="utf-8"` – без него на някои системи кирилицата може да се запише с друга кодировка.

## Стъпка по стъпка

Ето работния ред, когато пишеш функция с тестове:

1. **Опиши с едно изречение какво прави функцията.** Ако не можеш, още не знаеш какво пишеш.
2. **Напиши един прост тест** за нормалния случай. Пусни го и го остави да пропадне, докато няма функция.
3. **Напиши функцията**, докато тестът мине.
4. **Добави граничните случаи**, един по един. Всеки нов тест пускай веднага.
5. **Когато намериш бъг, първо напиши тест, който го показва.** Виж го как пропада. После поправи кода. Така бъгът не може да се върне незабелязано.
6. **Пускай целия набор преди всеки къмит.** Ако нещо пропадне, поправи го, преди да продължиш.

Полезни варианти на командата:

```
$ python3 -m pytest -x           # спри при първия пропаднал тест
$ python3 -m pytest -k top       # само тестове, чието име съдържа „top“
$ python3 -m pytest -v           # подробен списък
$ python3 -m pytest --collect-only -q   # покажи какво ще се пусне
```

Пример с `-k top`: на нашия набор избира само тестовете на `top_words` (4 от 10):

```
4 passed, 6 deselected in 0.01s
```

## Пример от практиката

Да кажем, че имаш програма за обработка на разходи с функция, която изчиства сумите: превръща `"7,30"` в `7.30`. Работи при теб, защото пишеш с точка. Приятел ти праща файл от български Excel, където десетичният знак е запетая. Програмата се чупи.

Правилният ход не е да поправиш и да забравиш. Първо пишеш тест:

```python
def test_comma_decimal():
    assert parse_amount("7,30") == 7.30
```

Пускаш го, виждаш, че пропада, поправяш функцията и тестът минава. Остава завинаги в набора. Ако някой следващата година „почисти“ кода и счупи запетаята, тестът ще го каже веднага. В следващия урок ще направим точно това за истински инструмент.

За ИИ-пътеките тестовете са още по-важни. Когато ИИ асистент ти пише или променя код, набор от тестове е най-надеждният начин да провериш дали резултатът прави каквото трябва. Изходът на модел е хипотеза, а тестът е проверката.

## Чести грешки

- **Тест без `assert`.** Функцията се изпълнява, но нищо не се проверява и тестът винаги „минава“. Всеки тест трябва да завършва с проверка.
- **Тест, който никога не си виждал да пропада.** Не знаеш дали наистина проверява нещо. Счупи кода нарочно, поне веднъж.
- **Файл или функция без `test_` в името.** `pytest` ги пропуска и не казва нищо. Виж броя на събраните тестове в `collected N items`.
- **Тест, зависещ от друг тест.** Всеки тест трябва да работи сам, в произволен ред.
- **Сравняване на числа с десетични дроби с `==`.** Сумите като `0.1 + 0.2` не дават точно `0.3`. Закръгляй с `round(...)` или ползвай `pytest.approx(0.3)`.
- **Тестване на прекалено много наведнъж.** Тест с десет `assert` спира на първия и крие останалите. По-добре са малки и именувани.
- **Пишеш в реални файлове.** Ползвай `tmp_path`.
- **Бездействие при `ModuleNotFoundError` в теста.** Ако `pytest` не намира твоя модул, най-често стартираш от грешна папка. Двата варианта са: пусни `python3 -m pytest` от папката на проекта, или добави настройка за пътя (следващият урок показва как).

## Упражнение

Напиши пет теста (или повече) за функцията за броене на думи от по-ранен урок или за `count_words` от този.

1. Създай папка с `words.py` и `test_words.py`.
2. Напиши най-малко пет теста: нормален случай, празен текст, регистър, пунктуация и един неправилен вход (например `top_words` с `n=0`).
3. Поне един от тях да е с `parametrize` (поне три реда данни).
4. Поне един да ползва `pytest.raises`.
5. Счупи функцията нарочно (например промени регулярния израз) и убеди се, че поне един тест пропада. После я поправи.
6. Намери един бъг или необичаен вход, който не си помислил (например текст само от интервали), добави тест за него и реши какво трябва да върне функцията.

Критерии за проверка:
- `python3 -m pytest` показва всички тестове като минали.
- След умишленото счупване поне един тест пропада и съобщението ти показва защо.
- Не се повтарят почти еднакви тестове, където е удобен `parametrize`.
- Всеки тест има име, което казва какво проверява.
- Тестовете не пишат извън временна папка.

## Бърза справка

| Нужда | Запис |
|---|---|
| Проверка | `assert резултат == очаквано` |
| Пускане на всички | `python3 -m pytest` |
| Подробно | `python3 -m pytest -v` |
| Спри при първия провал | `python3 -m pytest -x` |
| По част от името | `python3 -m pytest -k дума` |
| Един тест | `python3 -m pytest файл.py::име_на_теста` |
| Много случаи | `@pytest.mark.parametrize("a, b", [...])` |
| Очаквана грешка | `with pytest.raises(ValueError, match="...")` |
| Временна папка | параметър `tmp_path` |
| Дробни числа | `assert x == pytest.approx(0.3)` |

## Обобщение

Автоматичният тест вика функцията с известен вход и проверява резултата с `assert`, а `pytest` намира и пуска тестовете сам. Пропаднал тест показва разликата между получено и очаквано, така че знаеш какво да поправиш. Подбираш гранични случаи: празен вход, повторения, регистър, невалидни стойности. С `parametrize`, `pytest.raises` и `tmp_path` пишеш компактни тестове за много данни, за грешки и за файлове. Когато намериш бъг, първо го хващаш с тест и чак тогава го поправяш.

## Бележки за видеото
- Покажи `words.py` и първия тест, после пусни `python3 -m pytest` и посочи точките и резюмето.
- Счупи регулярния израз и покажи изхода с `F`, `>`, редовете с `E`; прочети ги на глас.
- Върни кода и пусни отново, за да се видят всички тестове зелени.
- Покажи `parametrize` и изхода с `-v`, в който има три отделни теста.
- Покажи `pytest.raises` и `tmp_path` с кратко обяснение.
- Покажи `-x`, `-k top` и `--collect-only -q`.
