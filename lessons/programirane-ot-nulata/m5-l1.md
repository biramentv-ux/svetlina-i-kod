> **Цел на урока:** да пишеш програми, които не вярват сляпо на входа, не държат тайни в изходния код и следят зависимостите си за известни проблеми.

## Какво ще научиш
- защо всеки вход (от потребител, файл или мрежа) е „непроверен“, докато не го провериш;
- как да валидираш вход в Python и как да пазиш границите в C;
- как да държиш ключове и пароли извън кода: променливи на средата и `.gitignore`;
- какво да направиш, ако тайна вече е попаднала в Git;
- как да проверяваш и обновяваш зависимостите с `pip list --outdated` и `pip-audit`.

## Принцип първи: входът не е надежден
Представи си портиер на сграда. Добрият портиер не пуска човек само защото казва „аз съм от етаж 5“. Проверява. Програмата е същата: всичко, което идва **отвън**, е непроверено. Отвън е: написаното от потребителя, съдържанието на файл, отговорът на мрежова заявка, аргументите от командния ред, дори името на файл.

Проверката не е недоверие към хората. Обикновен потребител пише „двайсет“ вместо „20“, копира интервал, натиска Enter на празно. Програма, която пада при такъв вход, е крехка, а при определени грешки (особено в C) и опасна. Затова валидираме **по правило, което казва какво е допустимо**, не по списък на „лошото“: по-лесно е да опишеш какво е валидно, отколкото да изброиш всичко невалидно.

Ето функция, която чете възраст. Правилото е ясно: цяло неотрицателно число до 120.

```python
def read_age(text):
    """Превръща низ във възраст; вдига ValueError с ясно съобщение."""
    text = text.strip()
    if not text.isdigit():
        raise ValueError(f"възрастта трябва да е цяло число, получих „{text}“")
    age = int(text)
    if not 0 <= age <= 120:
        raise ValueError(f"възрастта е извън 0-120: {age}")
    return age
```

Пуснах я с шест входа. Реалният изход:

```
'25' -> 25
' 7 ' -> 7
'abc' -> грешка: възрастта трябва да е цяло число, получих „abc“
'-3' -> грешка: възрастта трябва да е цяло число, получих „-3“
'150' -> грешка: възрастта е извън 0-120: 150
'' -> грешка: възрастта трябва да е цяло число, получих „“
```

Три етапа винаги се повтарят: **тип** (дали е число), **форма** (без излишни интервали) и **граници** (дали е в разумния диапазон). Съобщението казва какво се очаква и какво е получено.

## Валидиране на вход: пътища, текст и C
**Имена на файлове.** Ако програмата ти приема име на файл и го слага в определена папка, провери, че резултатът наистина остава в нея. Имена с `..` могат да „излязат“ от папката. Python помага с `pathlib`:

```python
from pathlib import Path
BASE = Path("uploads").resolve()
def safe_path(name):
    p = (BASE / name).resolve()
    if BASE not in p.parents:
        raise ValueError(f"недопустим път: {name}")
    return p
```

Опитах `doc.txt` и `../secret.txt`:

```
doc.txt -> uploads/doc.txt
../secret.txt -> грешка: недопустим път: ../secret.txt
```

Първото е в папката, второто се отхвърля. Идеята е отбранителна: програмата отказва да излиза извън своята зона.

**Текст в команди и заявки.** Никога не залепвай вход на потребителя в команда или SQL заявка като обикновен низ. Използвай средствата на езика, които отделят данните от инструкциите: списък от аргументи за `subprocess.run([...])` (без `shell=True`), параметризирани заявки в модулите за бази данни. Подробностите са тема на отделни курсове; тук запомни правилото: **данните остават данни**.

**Размери и граници в C.** В C най-честата грешка с входа е запис над границата на масива. Не използвай `gets` (премахната е от езика) и бъди внимателен с `scanf("%s", ...)` без ограничение на дължината. Пиши така:

```c
char name[32];
if (fgets(name, sizeof name, stdin) == NULL) { /* няма вход */ }
```

`fgets` чете най-много `sizeof name - 1` знака и винаги слага краен нулев знак, така че масивът не се препълва. След това провери дали е прочетен целият ред (има ли `\n`), а при числа използвай `strtol` или `strtoll` и погледни дали е изядена цялата стойност. По същия начин в проекта с виртуалната машина всеки ред се проверява, преди да бъде използван.

| Вход идва от | Какво проверяваш |
|---|---|
| `input()`, `fgets` | тип, дължина, граници, празен вход |
| командния ред | брой и вид на аргументите |
| файл | дали съществува, дали форматът е очаквания, дали е прекалено голям |
| име на файл | дали остава в позволената папка |
| мрежа, JSON | задължителни полета, типове, размери |

Валидирането не е спиране на грешки при писане, то е проектиране на **ясен отговор**: какво прави програмата при лош вход. Добрият отговор е съобщение и код за изход, не срив.

## Тайни: ключове и пароли извън кода
**Тайна** е всичко, което дава достъп: парола, API ключ, токен, частен ключ. Основното правило: **тайната никога не е в изходния код и никога не се качва в Git**.

Причината е проста: Git пази историята. Щом веднъж е записана тайна, тя остава в по-старите коммити, дори да я изтриеш в най-новия. Ако хранилището стане публично или го споделиш, тайната е достъпна. Ключовете се търсят автоматично, така че публикувана тайна трябва да се счита за **разкрита**.

Най-прост правилен подход: **променлива на средата** (environment variable). Това е настройка, която операционната система дава на програмата, без да е записана в кода.

```python
import os, sys
key = os.environ.get("MY_API_KEY")
if not key:
    sys.exit("липсва променливата MY_API_KEY (виж README)")
print("ключът е зареден, дължина", len(key))
```

Без променливата реалният изход е `липсва променливата MY_API_KEY (виж README)` и код 1. Със зададена (`MY_API_KEY=demo-not-a-real-key python3 cfg.py` на Linux и macOS) програмата печата `ключът е зареден, дължина 19`. Забележи, че **не печатаме самия ключ**: тайните не влизат в логове и съобщения.

Как се задава променлива зависи от системата:

| Система | Само за една команда | За текущия терминал |
|---|---|---|
| Linux / macOS (bash, zsh) | `MY_API_KEY=стойност python3 cfg.py` | `export MY_API_KEY=стойност` |
| Windows PowerShell | – | `$env:MY_API_KEY = "стойност"` |
| Windows cmd | – | `set MY_API_KEY=стойност` |

Често пазим локалните настройки във файл `.env` (всеки ред е `ИМЕ=стойност`), който **не** влиза в Git. Четенето му изисква малка библиотека (например `python-dotenv`) или няколко реда собствен код. Не е част от самия Python.

### `.gitignore`
Файлът `.gitignore` казва на Git кои файлове да пренебрегва. Работи само за файлове, които още **не са проследявани**. Пример:

```
.env
*.key
__pycache__/
.venv/
```

Създадох тези редове в нова папка заедно с файловете `.env`, `x.key` и `main.py`. `git status --short` показа само `.gitignore`, `main.py` и другите програмни файлове; `.env` и `x.key` не се появиха. Командата `git check-ignore -v .env x.key` го потвърди:

```
.gitignore:1:.env	.env
.gitignore:2:*.key	x.key
```

Добра практика е да добавиш в хранилището `.env.example` с имената на променливите и **фалшиви** стойности, за да знае всеки какво трябва да зададе.

### Ако тайната вече е изтекла
1. **Смени (revoke) тайната веднага** в услугата, която я е издала. Това е най-важната стъпка.
2. Махни я от кода, премести я в променлива на средата.
3. Почистването на Git историята е по избор и е по-трудно; без стъпка 1 то не помага, защото някой може вече да я е копирал.

## Зависимости: обновяване и проверка
Всяка библиотека, която ползваш, е чужд код, който работи с твоите права. Старите версии могат да имат **известни** проблеми със сигурността, оповестени и поправени от авторите. Затова:

- **Фиксирай версиите** в `requirements.txt` (`requests==2.34.2`), за да е възпроизводимо;
- **проверявай за по-нови версии** редовно;
- **проверявай за известни уязвимости**;
- обновявай внимателно: пускай тестовете след обновяването.

Работи във виртуална среда, както се учи по-рано в курса, за да не пипаш системния Python. В такава среда пуснах `pip list --outdated`. Реален (съкратен) изход за пакети, които нарочно инсталирах със стари версии:

```
Package  Version Latest Type
-------- ------- ------ -----
chardet  3.0.4   7.7.0  wheel
idna     2.7     3.20   wheel
pip      26.2.2  26.3   wheel
requests 2.19.0  2.34.2 wheel
urllib3  1.23    2.8.0  wheel
```

Колоната „Latest“ показва последната версия по момента на пускането. Номерата ще са други при теб.

За проверка за известни уязвимости има инструмент `pip-audit`, който се инсталира с `pip install pip-audit` и търси в публична база. Пуснах го върху файл с един ред `requests==2.19.0`:

```
Found 37 known vulnerabilities in 3 packages
Name     Version ID              Fix Versions
-------- ------- --------------- -------------
requests 2.19.0  PYSEC-2018-28   2.20.0
requests 2.19.0  PYSEC-2018-28   2.20.0
requests 2.19.0  PYSEC-2023-74   2.31.0
```

(показани са първите редове). Изходният код е 1: така инструментът може да „скъса“ автоматична проверка. Колоната „Fix Versions“ казва от коя версия е поправено. След това пуснах същата команда за `requests==2.34.2` и получих `No known vulnerabilities found` с код 0. Инструментът изисква достъп до интернет; ако мрежата е ограничена, ще получиш грешка за връзката, а не резултат, и тогава не можеш да направиш извод, че всичко е чисто.

Две честни уточнения. Липсата на съобщение не означава „напълно безопасно“, а само „няма известни проблеми в тази база“. И `pip-audit` гледа само Python пакети, не и C библиотеките в системата ти.

## Стъпка по стъпка
1. Прегледай проекта и намери всички входове: `input`, аргументи, файлове, мрежа.
2. За всеки вход напиши правило: тип, форма, граници. Реализирай го в една малка функция.
3. Реши какво прави програмата при лош вход: съобщение и код за изход, не срив.
4. Търси тайни в кода (`grep -rn "password\|key\|token" .`) и преглед на Git историята (`git log -p`).
5. Премести всяка тайна в променлива на средата; добави `.env` към `.gitignore`; създай `.env.example`.
6. Ако намериш тайна в историята, смени я при издателя.
7. Създай `requirements.txt` с фиксирани версии (`pip freeze`), пусни `pip list --outdated` и `pip-audit -r requirements.txt`.
8. Обнови, пусни тестовете, направи коммит.

## Пример от практиката
Да кажем, че Силвия е написала малък Telegram бот. В файла `bot.py` има ред `TOKEN = "..."`, а проектът е в публично хранилище. Тя забелязва, че токенът е в кода, и вижда, че вече е видим в историята. Първото, което прави, е да поиска нов токен от услугата и да обезсили стария. После променя кода да чете `os.environ.get("BOT_TOKEN")`, добавя `.env` в `.gitignore` и пише `.env.example`. Накрая пуска `pip-audit` и вижда, че една библиотека е остаряла; обновява я и пуска тестовете.

## Чести грешки
- **Проверка само при потребителския интерфейс.** Ако данните идват и от файл, проверката трябва да е в самата функция, не само във формата.
- **Тайна във `.gitignore`, но вече коммитната.** Игнорирането не изтрива вече проследени файлове и не пипа историята. Смени тайната.
- **Печатане на тайната в лог или съобщение за грешка.** Печатай дължина или маска, не стойността.
- **Прекалено „умна“ проверка.** Сложен регулярен израз за всяка възможна форма често пропуска нещо. По-добре е проста, ясна проверка.
- **Игнориране на кода за изход от инструментите.** `pip-audit` връща 1, когато намери проблеми; не го „прекъсвай“ мълчаливо.
- **Обновяване на всичко наведнъж без тестове.** Обновявай поетапно и проверявай.
- **Тайни в C програми като низове в изходния код.** Те са видими и в компилирания файл. Чети ги от средата (`getenv`) или от файл извън хранилището.

## Упражнение
Вземи проект от курса (например инструмента за командния ред от модул 3).

1. Намери всички входове и за всеки напиши функция за проверка с ясно съобщение.
2. Добави най-малко 6 теста с pytest: валидни и невалидни входове, празен вход, граници.
3. Ако в кода има парола, ключ или пътека към лична папка, премести го в променлива на средата.
4. Добави `.gitignore` (`.env`, `__pycache__/`, `.venv/`) и `.env.example`. Провери с `git check-ignore -v`.
5. Във виртуална среда инсталирай зависимостите, пусни `pip list --outdated` и (ако имаш интернет) `pip-audit`. Запиши резултата.
6. Опиши в `README.md` кои променливи са нужни и как се задават.

Критерии: никакъв низ с тайна в кода; `git status` не показва `.env`; програмата не се срива при празен или груб вход; тестовете минават; в README има инструкция за променливите.

## Бърза справка
- Прочитане на променлива: `os.environ.get("ИМЕ")`; в C: `getenv("ИМЕ")`.
- Задаване (Linux/macOS): `export ИМЕ=стойност`; PowerShell: `$env:ИМЕ = "стойност"`.
- `.gitignore`: един шаблон на ред; проверка с `git check-ignore -v файл`.
- Сигурно четене в C: `fgets(буфер, sizeof буфер, stdin)`, `strtol`/`strtoll` за числа.
- Остарели пакети: `pip list --outdated`; известни проблеми: `pip-audit -r requirements.txt`.
- Фиксиране: `pip freeze > requirements.txt`.

## Обобщение
Вход отвън е непроверен, докато не го провериш по ясно правило за тип, форма и граници. Тайните живеят извън кода: в променливи на средата, а файловете с тях са в `.gitignore`; ако тайна изтече, първо я сменяш. Зависимостите са чужд код, затова ги фиксираш, проверяваш с `pip list --outdated` и `pip-audit` и обновяваш с тестове. Ще го видиш пак в курсовете за работа с ИИ, където ключовете към услугите са точно такива тайни.

- Покажи `cfg.py` без променливата и с нея (на Linux/macOS и в PowerShell).
- Създай `.gitignore`, покажи `git status` преди и след и `git check-ignore -v`.
- Покажи виртуална среда, `pip list --outdated` и `pip-audit` върху стара версия, после върху нова.
