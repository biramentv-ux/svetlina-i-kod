> **Цел на урока:** да автоматизираш компилирането с Makefile, да избираш подходящи флагове на компилатора и да намираш нарочно вкарани грешки с паметта чрез AddressSanitizer и UBSan.

## Какво ще научиш
- Как е устроен Makefile: цели, зависимости, правила и променливи
- Какво правят флаговете `-Wall`, `-Wextra`, `-g`, `-O0` и `-O2` и кога се ползва кой
- Как да включваш AddressSanitizer и UndefinedBehaviorSanitizer в отделна „debug“ цел
- Как да четеш отчетите за грешки в стека, в глобална памет и за препълване на цяло число
- Как да проверяваш поправката си, вместо да вярваш, че „сега работи“

## Защо ни трябва make

Досега компилираше с една команда: `gcc main.c -o prog`. Щом проектът има три файла, командата става дълга, а ти компилираш и трите при всяка промяна, дори да си пипнал само един. Представи си готвач, който при всяка поръчка пече всички хлябове наново, вместо само този, който е свършил.

**make** е програма, която прави точно това: помни кои файлове зависят от кои и прекомпилира само нужното. Инструкциите ѝ са във файл с име `Makefile`. Принципът е прост: за всеки резултат (**цел, target**) описваш от какво зависи и с коя команда се получава. Когато поне една зависимост е по-нова от целта, командата се изпълнява.

В този урок работиш по упражнение: първо ще направиш Makefile за малък проект, после ще го използваш, за да търсиш грешки. Всичко се пуска на Linux или macOS в терминал. На Windows работи същото в WSL или в MSYS2/MinGW; там командите са същите, но името на изпълнимия файл може да завършва на `.exe`.

## Малкият проект

Създай празна папка и в нея три файла. Заглавният файл `stats.h` описва какво предлага модулът:

```c
#ifndef STATS_H
#define STATS_H
#include <stddef.h>
int sum(const int *a, size_t n);
double average(const int *a, size_t n);
#endif
```

Реализацията е в `stats.c`:

```c
#include "stats.h"

int sum(const int *a, size_t n) {
    int s = 0;
    for (size_t i = 0; i < n; i++) s += a[i];
    return s;
}

double average(const int *a, size_t n) {
    return (double)sum(a, n) / n;
}
```

А `main.c` ги използва:

```c
#include <stdio.h>
#include "stats.h"

int main(void) {
    int data[5] = {4, 8, 15, 16, 23};
    printf("sum=%d average=%.2f\n", sum(data, 5), average(data, 5));
    return 0;
}
```

## Makefile стъпка по стъпка

1. В същата папка създай файл с точно име `Makefile` (с главна буква, без разширение).
2. Започни с променливи. Те намаляват повторенията:

```make
CC      = gcc
CFLAGS  = -std=c11 -Wall -Wextra -g
TARGET  = stats

OBJS = main.o stats.o
```

3. Добави главното правило. Първата цел във файла е тази, която `make` строи, когато го пуснеш без аргумент:

```make
$(TARGET): $(OBJS)
	$(CC) $(CFLAGS) -o $@ $(OBJS)
```

Формулата е: `цел: зависимости`, а отдолу команда. `$@` означава „името на целта“, тук `stats`.

4. За всеки `.o` файл опиши от какво зависи. Не забравяй заглавния файл: ако `stats.h` се промени, и двата модула трябва да се прекомпилират.

```make
main.o: main.c stats.h
	$(CC) $(CFLAGS) -c main.c

stats.o: stats.c stats.h
	$(CC) $(CFLAGS) -c stats.c
```

5. Добави цел за изчистване и две варианта на сглобяване:

```make
debug: CFLAGS += -O0 -fsanitize=address,undefined
debug: clean $(TARGET)

release: CFLAGS = -std=c11 -Wall -Wextra -O2
release: clean $(TARGET)

clean:
	rm -f $(OBJS) $(TARGET)

.PHONY: clean debug release
```

`.PHONY` казва на make, че `clean`, `debug` и `release` не са имена на файлове, а действия. Без него, ако случайно има файл с име `clean`, целта никога няма да се изпълни.

**Внимание: командите под всяко правило започват с табулатор (Tab), не с интервали.** Много редактори сами заменят табулатора с интервали. Ако това се случи, получаваш:

```
Bad.mk:8: *** missing separator (did you mean TAB instead of 8 spaces?).  Stop.
```

Това съобщение е истинско, получих го, като нарочно заместих табулатора с 8 интервала. Поправката е да върнеш Tab в началото на реда с командата.

Сега пусни:

```
$ make
gcc -std=c11 -Wall -Wextra -g -c main.c
gcc -std=c11 -Wall -Wextra -g -c stats.c
gcc -std=c11 -Wall -Wextra -g -o stats main.o stats.o
$ ./stats
sum=66 average=13.20
```

Втори път `make` не прави нищо:

```
$ make
make: 'stats' is up to date.
```

А ако „докоснеш“ заглавния файл с `touch stats.h`, make прекомпилира и двата модула, защото и двата зависят от него. Ако промениш само `main.c`, ще се прекомпилира само той. Така се прекомпилира само нужното.

С `make -n clean` само виждаш командите, без да ги изпълняваш.

## Флаговете на компилатора

Флаговете са инструкции към gcc или clang. Най-нужните за начало:

| Флаг | За какво служи | Кога се ползва |
|---|---|---|
| `-Wall` | включва основен набор предупреждения | винаги |
| `-Wextra` | допълнителни предупреждения | винаги |
| `-std=c11` | избира версията на езика | за предсказуемост |
| `-g` | добавя информация за дебъгване (имена, редове) | докато разработваш |
| `-O0` | без оптимизации | дебъгване |
| `-O2` | силни оптимизации | готова версия |
| `-fsanitize=address` | AddressSanitizer: следи достъпа до памет | тестване |
| `-fsanitize=undefined` | UBSan: хваща неопределено поведение | тестване |

Предупрежденията не са украса: повечето сочат реални грешки. Компилирай с `-Wall -Wextra` и ги чети.

**Оптимизациите променят какво виждаш.** При `-O0` компилаторът превежда кода почти буквално, затова дебъгерът показва точно това, което си написал. При `-O2` променливи изчезват, цикли се разгъват, функции се вграждат. Кодът прави същото (когато е коректен), но по различен начин. А когато кодът не е коректен, при различни нива на оптимизация грешката може да се прояви различно, както ще видиш по-долу. Затова разработвай с `-O0 -g`, а оптимизираната версия проверявай отделно.

**Санитайзерите** са междинният инструмент: програмата се компилира с допълнителни проверки, които забавят изпълнението (обикновено няколко пъти), и затова ги ползваш при тестване, не в готовата версия.

Целта `debug` вече ги включва:

```
$ make debug
rm -f main.o stats.o stats
gcc -std=c11 -Wall -Wextra -g -O0 -fsanitize=address,undefined -c main.c
gcc -std=c11 -Wall -Wextra -g -O0 -fsanitize=address,undefined -c stats.c
gcc -std=c11 -Wall -Wextra -g -O0 -fsanitize=address,undefined -o stats main.o stats.o
$ ./stats
sum=66 average=13.20
```

Линкването също получава флага: санитайзерът трябва да е и при компилиране, и при свързване. Забележи как `debug` първо изпълнява `clean`, за да не остане в папката стар `.o` файл, компилиран без санитайзер.

## Упражнение: лов на грешки

Сега идва същинската част. Ето програма `trap.c`, която съдържа три нарочно вкарани грешки, избирани по аргумент. Прочети я внимателно **преди** да я пуснеш и се опитай да познаеш къде са проблемите.

```c
#include <stdio.h>
#include <limits.h>
#include <stdlib.h>

int counts[5];

void stack_bug(void) {
    int arr[4] = {1, 2, 3, 4};
    int total = 0;
    for (int i = 0; i <= 4; i++) total += arr[i];
    printf("total=%d\n", total);
}

void global_bug(void) {
    for (int i = 0; i <= 5; i++) counts[i] = i;
    printf("counts ok\n");
}

void overflow_bug(void) {
    int x = INT_MAX;
    x = x + 1;
    printf("x=%d\n", x);
}

int main(int argc, char **argv) {
    int w = argc > 1 ? atoi(argv[1]) : 0;
    if (w == 1) stack_bug();
    if (w == 2) global_bug();
    if (w == 3) overflow_bug();
    return 0;
}
```

Първо компилирай без санитайзери и пусни трите случая:

```
$ gcc -g -O0 trap.c -o t0
$ ./t0 1
total=-1381305494
$ ./t0 2
counts ok
$ ./t0 3
x=-2147483648
```

Нито един от тях не се срина. Първият дава безсмислена сума, а числото е различно при всяко пускане, защото чете чужда памет. Вторият „работи“, но пише извън масива. Третият преминава през границата на `int` и се връща към отрицателно. Всичко изглежда нормално. Ето защо „пуснах го и работи“ не е доказателство.

Сега компилирай със санитайзери: `gcc -g -O0 -fsanitize=address,undefined trap.c -o trap`.

**Случай 1** (`./trap 1`), съкратен:

```
trap.c:10:46: runtime error: index 4 out of bounds for type 'int [4]'
==4891==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7f77c1b00030
READ of size 4 at 0x7f77c1b00030 thread T0
    #0 0x561d0c5165d6 in stack_bug /tmp/tmp.TJnP7QjovY/trap.c:10
    #1 0x561d0c5169a6 in main /tmp/tmp.TJnP7QjovY/trap.c:33

Address 0x7f77c1b00030 is located in stack of thread T0 at offset 48 in frame
    #0 0x561d0c516358 in stack_bug /tmp/tmp.TJnP7QjovY/trap.c:7
```

Два инструмента са реагирали. UBSan пише „index 4 out of bounds for type 'int [4]'“ с точния ред и колона. ASan съобщава `stack-buffer-overflow`, тоест излизане извън масив в стека, четене (`READ`) от размер 4 байта. Първият ред от стека сочи `trap.c:10`, а `stack_bug` започва на ред 7. Цикълът е `i <= 4` при масив с четири елемента.

**Случай 2** (`./trap 2`):

```
trap.c:15:40: runtime error: index 5 out of bounds for type 'int [5]'
==4894==ERROR: AddressSanitizer: global-buffer-overflow on address 0x55c2812dbd94
WRITE of size 4 at 0x55c2812dbd94 thread T0
    #0 0x55c2812d87ed in global_bug /tmp/tmp.TJnP7QjovY/trap.c:15
0x55c2812dbd94 is located 0 bytes after global variable 'counts' defined in 'trap.c:5:5' (0x55c2812dbd80) of size 20
```

Този път е `global-buffer-overflow` (глобална променлива) и операцията е запис. ASan дори назовава променливата: `counts`, с размер 20 байта (пет `int` по четири). Пишеш на индекс 5, един елемент след края.

**Случай 3** (`./trap 3`):

```
trap.c:21:7: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
x=-2147483648
```

Тук ASan няма какво да каже: няма достъп до памет. Но UBSan хваща препълването на цяло число със знак, което в C е неопределено поведение, и програмата продължава, затова виждаш и изхода. Това е пример защо двата флага се ползват заедно.

**Valgrind** върху `t0` за случай 1 съобщава `Conditional jump or move depends on uninitialised value(s)` с ред `trap.c:11`: същата грешка, видяна от друг ъгъл. Затова не разчитай на един инструмент.

**Какво прави оптимизаторът.** Опитай и `gcc -Wall -Wextra -O2 -c trap.c`. При `-O0` компилаторът мълчи, а при `-O2` пише:

```
trap.c:10:46: warning: iteration 4 invokes undefined behavior [-Waggressive-loop-optimizations]
trap.c:15:44: warning: iteration 5 invokes undefined behavior [-Waggressive-loop-optimizations]
trap.c:15:40: warning: array subscript 5 is above array bounds of 'int[5]' [-Warray-bounds=]
```

Оптимизаторът анализира кода по-дълбоко и открива част от проблемите. Но не разчитай на това: предупрежденията са бонус, не гаранция. Санитайзерът е надеждният проверител, защото гледа какво става наистина по време на работа.

## Пример от практиката

Да кажем, че колега ти праща програма за обработка на списък с оценки и пише: „На моя компютър работи, а при теб дава странни числа“. Ти не гадаеш, а правиш три стъпки.

Пускаш `make debug`, пускаш програмата с входа, който дава проблема, и четеш първия ред на отчета: вид на грешката и ред във файла. Ако е `heap-buffer-overflow` на `grades.c:42`, отваряш този ред и търсиш индекс извън заделеното. След поправката пускаш същия вход и санитайзерът трябва да мълчи.

## Чести грешки
- **Интервали вместо Tab в Makefile** – давам `missing separator`. Върни табулатор в началото на командите.
- **Липсва заглавен файл в зависимостите** – промениш `stats.h`, а make не прекомпилира; резултатът е програма с разминаващи се версии. Изброявай всички `#include` на твои файлове.
- **Забравен `.PHONY`** – ако има файл `clean` или `debug`, целта се пропуска.
- **Санитайзер само при компилиране, не и при линкване** – получаваш грешки за липсващи символи или санитайзерът не се зарежда. Слагай флага и в двата случая (в урока `CFLAGS` се ползва и на двете места).
- **Ползване на `-O2` при дебъгване** – променливите изчезват, редовете „прескачат“. Дебъгвай с `-O0 -g`.
- **Игнориране на предупреждения** – „то се компилира“ не значи „то е вярно“.
- **Пускане на ASan и Valgrind върху една и съща програма** – двата инструмента си пречат; използвай единия за пускане.

## Бърза справка

| Нужда | Команда |
|---|---|
| Сглоби проекта | `make` |
| Само покажи какво ще изпълни | `make -n` |
| Изчисти | `make clean` |
| Версия за дебъгване | `make debug` |
| Оптимизирана версия | `make release` |
| Компилация с предупреждения | `gcc -std=c11 -Wall -Wextra -g f.c` |
| Със санитайзери | `gcc -g -O0 -fsanitize=address,undefined f.c` |
| Предупреждения от оптимизатора | `gcc -Wall -Wextra -O2 -c f.c` |
| Проверка с Valgrind | `valgrind --leak-check=full ./prog` |
| Правило в Makefile | `цел: зависимости` и под него команда с Tab |
| Автоматични променливи | `$@` (целта), `$<` (първата зависимост) |

## Задачи за самостоятелна работа

Изпълни по ред. Всяка стъпка има проверка.

1. **Направи проекта.** Създай трите файла и Makefile и пусни `make`. Проверка: програмата отпечатва `sum=66 average=13.20`, а при втория `make` виждаш съобщението, че всичко е актуално.
2. **Докажи зависимостите.** Промени `stats.h` (например добави празен ред) и пусни `make`. Проверка: прекомпилират се и двата `.c` файла. После промени само `main.c`: прекомпилира ли се само той?
3. **Добави цел `run`**, която сглобява и пуска проекта (включи я в `.PHONY`).
4. **Ловна обиколка.** Компилирай `trap.c` със санитайзери и намери трите проблема. За всеки запиши: вид на грешката, ред, и коя е причината с една дума (например „<= вместо <“).
5. **Поправи ги** и пусни отново. Проверка: нито ASan, нито UBSan пишат нищо.
6. **Най-важното.** Разбий нарочно нещо ново: заделяй с `malloc` масив от 10 елемента и пиши на индекс 10. Прогнозирай какво ще напише ASan преди да пуснеш, после сравни.

**Критерии за самопроверка:**
- Makefile използва променливи и поне две зависимости от заглавен файл;
- имаш цели `debug` и `release` и `.PHONY`;
- можеш да обясниш разликата между `-O0` и `-O2` с твои думи;
- за всеки отчет посочваш първо вида на грешката, после реда;
- знаеш защо санитайзер във финалната версия не е добра идея.

## Обобщение
Makefile описва кои файлове от кои зависят и така прекомпилира само нужното. Флаговете `-Wall -Wextra -g` са минимумът за всеки проект, `-O0` е за дебъгване, а `-O2` за готовата версия. Санитайзерите хващат грешки, които при обикновено пускане изглеждат като „работи“: излизане от масив в стека и в глобална памет, и препълване на цяло число. Правилният навик е да имаш готова цел `make debug`, която ги включва, и да пускаш тестовете през нея.

За курсовете за ИИ и reverse engineering това е ценно по две причини. Когато ИИ асистент ти генерира C код, `make debug` е най-бързата проверка дали не крие такива грешки. А при анализ на програми ще срещаш същите шаблони, видими в машинния код, и вече ще знаеш откъде идват.

## Бележки за видеото
- Покажи структурата на папката и трите файла, после напиши Makefile ред по ред.
- Нарочно сложи интервали вместо Tab и покажи съобщението `missing separator`.
- Пусни `make` два пъти, после `touch stats.h` и сравни кои команди се изпълняват.
- Покажи `make -n clean` преди истинското изчистване.
- Пусни `trap` без санитайзер и със санитайзер за трите случая; в отчетите подчертай вида на грешката и реда.
- Покажи предупрежденията при `-O2` и обясни, че са бонус, а не гаранция.
