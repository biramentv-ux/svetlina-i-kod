> **Цел на урока:** да започнеш да ползваш Git от първия си проект: да записваш история на промените, да се връщаш към стари версии, да експериментираш в клонове и да не качваш в хранилището файлове, които не му принадлежат.

## Какво ще научиш
- Какво е система за контрол на версиите и защо „final_v2_НОВО.py“ не е решение
- Работния цикъл: промяна, `add`, `commit`
- Как да разглеждаш история и разлики с `log` и `diff`
- Как да връщаш файл или цял проект към по-стара версия
- Какво са клонове, отдалечено хранилище и файлът `.gitignore`

## Проблемът, който Git решава

Нека си представим, че пишеш курсова работа. В понеделник я записваш като `rabota.docx`. Във вторник правиш големи промени и я запазваш като `rabota_final.docx`. В сряда добавяш поправки в `rabota_final_2.docx`, а в четвъртък откриваш, че вторничната версия е била по-добра. Не помниш какво точно си променил.

При кода е още по-лошо, защото един счупен ред може да спре цялата програма. **Git** е програма, която пази историята на папката ти като поредица от снимки (подобно на запазени точки в игра). Всяка снимка се нарича **къмит** (commit) и носи кратко описание, автор и дата. Можеш да видиш какво е различно между две снимки, да се върнеш към стара и да пробваш нещо рисковано, без да рискуваш работещата версия.

Git работи локално, на твоя компютър, и не изисква интернет. Той е отделен от сайтове като GitHub, GitLab или Codeberg, които са места за съхранение на хранилища онлайн. Тях ще споменем накрая.

## Основни понятия

| Понятие | Ежедневна аналогия | Какво значи в Git |
|---|---|---|
| Хранилище (repository) | Папка с цялата история | Проектната папка заедно със скритата папка `.git` |
| Работна папка | Бюрото, където пишеш | Файловете, както ги виждаш сега |
| Индекс (staging area) | Кутия, в която слагаш нещата за снимка | Промените, подбрани за следващия къмит |
| Къмит (commit) | Снимка с етикет | Записано състояние с описание |
| Клон (branch) | Паралелна чернова | Отделна линия на историята |
| Отдалечено хранилище (remote) | Копие на сървър или у приятел | Друго хранилище, с което си обменяш къмити |

Най-важното да разбереш е индексът. Файловете минават през три състояния: променени в работната папка, подбрани в индекса и записани в къмит. Това ти позволява да направиш десет промени, но да запишеш в един къмит само логически свързаните.

## Първи настройки

Преди първия си къмит кажи на Git кой си. Това име и поща се записват във всеки твой къмит:

```
git config --global user.name "Твоето Име"
git config --global user.email "ти@пример.bg"
```

Пощата не се проверява. Не е нужно да е истинска, но ако по-късно качиш проекта онлайн, използваният адрес може да стане публичен, така че помисли какво въвеждаш. Ако искаш настройката само за един проект, пусни същите команди без `--global`, докато си в папката на проекта (така направих и аз за примерите по-долу).

Как се инсталира Git: в Linux през пакетния мениджър, в macOS обикновено с инструментите за разработчици, в Windows от официалния сайт на проекта. Проверка: `git --version`. Примерите са пускани с версия 2.43.0; командите `switch` и `restore` са по-нови (около версия 2.23), а в по-стари се ползва `checkout`. Ако получиш „неизвестна команда“, обнови Git.

## Работният цикъл: init, add, commit

Създаваме папка и хранилище. Имената на клона и потребителя са за примера:

```
$ mkdir proekt && cd proekt
$ git init -b main .
$ echo 'print("Здравей!")' > programa.py
$ git status -s
?? programa.py
```

`??` значи „Git не следи този файл“. Добавяме го към индекса и записваме първия къмит:

```
$ git add programa.py
$ git status -s
A  programa.py
$ git commit -m "Първа версия на програмата"
```

Сега променяме файла и гледаме какво точно е различно:

```
$ echo 'print("Здравей, свят!")' > programa.py
$ git diff
--- a/programa.py
+++ b/programa.py
@@ -1 +1 @@
-print("Здравей!")
+print("Здравей, свят!")
```

Редът с `-` е старият, с `+` – новият. Това е най-бързият начин да прегледаш собствената си работа преди къмит. Записваме го, като добавяме ключа `-a`, който включва всички вече следени променени файлове (нови файлове все пак изискват `git add`):

```
$ git commit -am "Добавям „свят“ в поздрава"
```

Правим и трета промяна: програмата вече пита за име.

```
$ git commit -am "Поздрав по име"
$ git log --oneline
c973e8b Поздрав по име
cc619d8 Добавям „свят“ в поздрава
7dc617b Първа версия на програмата
```

Първата колона е част от идентификатора на къмита. При теб ще е различен, защото зависи от съдържанието, автора и времето. Описанията се четат от най-новото към най-старото.

### Как се пише добро съобщение

- Кратко, ясно и в сегашно или минало време, избери един стил и го следвай.
- Казва **какво и защо**, а не „промени“ или „поправка 2“.
- Един къмит прави едно логическо нещо. Ако описанието изисква „и“, вероятно са две неща.

## Връщане назад

Това е причината да ползваш Git. Има няколко ситуации.

**Развалил си файла и още не си записал.** Файлът е променен в работната папка, но не си го добавил:

```
$ echo 'счупен код (' > programa.py
$ git status -s
 M programa.py
$ git restore programa.py
$ cat programa.py
name = input("Име: ")
print("Здравей,", name)
```

`git restore` връща файла към последния къмит. Внимание: незаписаните промени се губят окончателно, защото Git не ги е виждал. Затова къмитвай често.

**Искаш стара версия на файл от историята.** Ползваш `--source` с адрес на къмит. `HEAD` е последният, `HEAD~2` е два къмита назад:

```
$ git restore --source=HEAD~2 programa.py
$ cat programa.py
print("Здравей!")
$ git status -s
 M programa.py
```

Старата версия е върната като нова непотвърдена промяна. Можеш да я запишеш с къмит или да я върнеш обратно с `git restore programa.py`. Историята не е изтрита.

**Искаш да отмениш цял къмит, без да пипаш историята.** `git revert` създава нов къмит, който прави обратното на избрания:

```
$ git revert --no-edit HEAD~1
$ git log --oneline | head -3
a69c9ea Revert "Опит с нова функция"
17daa80 Добавям .gitignore
65e5469 Опит с нова функция
```

Това е безопасният начин, защото не пренаписва миналото. Има и команди като `git reset --hard`, които унищожават промени; не ги пускай, докато не си сигурен какво правят.

## Клонове: безопасни експерименти

**Клонът** е отделна линия на историята. Основният се нарича обикновено `main`. Искаш да пробваш нещо рисковано? Правиш клон, работиш в него и ако не се получи, просто го изоставяш. Основният остава недокоснат.

```
$ git switch -c eksperiment
$ echo 'print("експеримент")' >> programa.py
$ git commit -am "Опит с нова функция"
$ git switch main
$ git merge eksperiment
$ git branch
  eksperiment
* main
```

Звездичката показва текущия клон. `git merge` слива промените на `eksperiment` в `main`. В този пример `main` не е получил нови къмити, затова Git просто „премества“ клона напред. Когато и двата клона имат различни промени в една и съща част на файла, настъпва **конфликт на сливане** и трябва да избереш ръчно коя версия остава. С това ще се занимаваме при по-големи проекти.

## .gitignore: какво не бива да влиза в историята

Не всичко в папката е за запазване. Автоматично генерираните файлове (като папката `__pycache__`, която Python създава), временните файлове и най-вече **тайните** (пароли, ключове, файлове за настройки със секрети) не трябва да се записват в къмит. Щом веднъж са в историята, смятай ги за разкрити, дори да ги изтриеш по-късно.

```
$ mkdir __pycache__ && echo x > __pycache__/a.pyc
$ echo 'тайна=1' > .env
$ git status -s
?? .env
?? __pycache__/
$ printf '__pycache__/\n.env\n' > .gitignore
$ git status -s
?? .gitignore
$ git add .gitignore && git commit -m "Добавям .gitignore"
```

След създаването на `.gitignore` двата файла изчезват от списъка на неследените. Самият `.gitignore` се записва в къмит, за да го има и всеки, който копира проекта. Шаблоните използват пътища и звездички, например `*.log` за всички файлове с такова разширение. Файл, който вече е бил в къмит, не се скрива с `.gitignore`: първо трябва да се махне от следенето, а ако в него е имало тайна, да се смени самата тайна. В реалния живот тайните се държат извън кода (ще го разгледаме в модул за сигурност).

## Отдалечено хранилище

Локалното хранилище е само на твоя диск. Ако дискът се повреди, историята изчезва. Затова добавяш отдалечено хранилище (remote). То може да е в услуга като GitHub, GitLab, Codeberg, на собствен сървър или дори в друга папка. За упражнение ще направим „сървър“ в съседна папка:

```
$ git init --bare -b main ../server.git
$ git remote add origin ../server.git
$ git push -u origin main
To ../server.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
$ git status -sb | head -1
## main...origin/main
```

`push` изпраща къмитите към `origin` (стандартно име за основното отдалечено хранилище). `-u` запомня връзката, така че следващият път е достатъчно `git push`, а `git pull` ще дръпне чужди промени. Друг човек (или ти на друг компютър) получава проекта с клониране:

```
$ git clone server.git kopie
$ ls -A kopie
.git  .gitignore  programa.py
```

Забележи, че в копието **няма** `.env` и `__pycache__`: `.gitignore` е свършил работата си. За онлайн услугите ще ти трябва акаунт и начин за удостоверяване, който зависи от услугата и често се променя, затова го потърси в нейната помощ. Никога не записвай паролите и токените си във файлове, които Git следи.

## Стъпка по стъпка

1. Създай папка `moy-proekt` и влез в нея.
2. Пусни `git init -b main` и настрой `user.name` и `user.email` (без `--global`, ако искаш само за този проект).
3. Напиши прост скрипт, добави го с `git add` и направи първия къмит.
4. Промени скрипта, прегледай с `git diff`, къмитни с описание.
5. Повтори още веднъж, за да имаш три къмита, и виж `git log --oneline`.
6. Развали умишлено файла и го върни с `git restore`.
7. Върни файла към версия от два къмита назад с `git restore --source=HEAD~2`.
8. Направи клон за експеримент, къмитни в него и го слей в `main`.
9. Създай файл `.env` и добави правило в `.gitignore`.

## Пример от практиката

Да кажем, че пишеш програма, която брои думите в текст. Тя работи и ти я къмитваш. После решаваш да добавиш сортиране по честота и променяш три файла. След час програмата вече не работи и не помниш коя от трите промени е причината. Без Git тръгваш да гадаеш. С Git пускаш `git diff` и виждаш точно какво си променил, а най-лошото, което може да се случи, е `git restore .`, с което се връщаш към последната работеща версия. Ако си работил в клон `sortirane`, `main` никога не е бил счупен.

Връзка с другите пътеки: курсовете за работа с ИИ и агенти често започват с хранилище, а когато агент редактира код, `git diff` е най-бързият начин да провериш какво е променил. При reverse engineering пък се сравняват версии на един и същ бинарен файл. Идеята е еднаква: разлика между две състояния.

## Чести грешки

- **Редки и огромни къмити** – „Работа за седмица“ не помага при търсене на проблем. Къмитвай на малки логически стъпки.
- **Неясни съобщения** – „fix“, „промени“, „123“ няма да ти кажат нищо след месец.
- **Тайни в хранилището** – пароли, ключове и токени в къмит се считат за разкрити, дори след изтриване. Не ги записвай.
- **`git add .` без проверка** – добавя всичко, включително файлове, които не искаш. Първо `git status`.
- **Работа в грешния клон** – провери с `git branch`, преди да започнеш.
- **Не пазиш копие извън компютъра** – хранилище само на един диск не е резервно копие.

## Упражнение

Създай хранилище за малък проект, например скрипт за пресмятане на сметка с пица от първия урок.

1. Направи поне **три къмита** с различни и ясни описания.
2. Развали един файл умишлено и го върни с `git restore`.
3. Върни един файл към версия от два къмита назад, после го върни към последната.
4. Направи клон `eksperiment`, добави нещо и го слей в `main`.
5. Създай `.env` с измислена стойност и се увери, че `git status` не го показва след добавяне в `.gitignore`.
6. Създай локално „отдалечено“ хранилище, изпрати къмитите и го клонирай в нова папка.

Критерии: `git log --oneline` показва поне три смислени съобщения; `git status` е чист; `.env` не се появява в клонираното копие; можеш да обясниш на глас разликата между работна папка, индекс и къмит; можеш да върнеш файл от историята, без да губиш нищо.

## Бърза справка

| Задача | Команда |
|---|---|
| Ново хранилище | `git init -b main` |
| Състояние (кратко) | `git status -s` |
| Добавяне в индекса | `git add файл` |
| Запис на къмит | `git commit -m "описание"` |
| Къмит на следени промени | `git commit -am "описание"` |
| Разлика | `git diff` |
| История | `git log --oneline` |
| Връщане на файл към последния къмит | `git restore файл` |
| Файл от по-стара версия | `git restore --source=HEAD~2 файл` |
| Отмяна на къмит чрез нов | `git revert --no-edit къмит` |
| Нов клон / смяна | `git switch -c име` / `git switch име` |
| Сливане | `git merge име` |
| Добавяне на remote | `git remote add origin адрес` |
| Изпращане / клониране | `git push -u origin main` / `git clone адрес` |

Командите са едни и същи в Windows, macOS и Linux. Разликите са само в инсталирането и в обвивката (пътищата в Windows могат да изискват кавички при интервали).

## Обобщение

Git пази историята на проекта като къмити: записани снимки с описание. Работният цикъл е промяна, `git add`, `git commit`, а `git diff` и `git log` ти показват какво се е случило. Можеш да върнеш файл или да отмениш къмит, без да губиш историята, а клоновете ти дават безопасно място за експерименти. С `.gitignore` държиш тайните и генерираните файлове извън хранилището, а отдалеченото хранилище те пази от загуба на данни. Така завършва първият модул: имаш среда, терминал и история на кода и си готов да пишеш Python в следващия модул.

- Покажи `git diff` с червени и зелени редове и `git log --oneline` след три къмита.
- Развали файл и го върни с `git restore`, после върни стара версия с `--source`.
