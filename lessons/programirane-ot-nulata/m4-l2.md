> **Цел на урока:** да разбереш как е подредена паметта на работеща програма и да докажеш с реални адреси къде живеят код, данни, стек и купчина.

## Какво ще научиш
- Какво е процес и защо всяка програма вярва, че паметта е само нейна
- Кои са основните области: код, данни, стек и купчина (heap)
- Как се строи стекова рамка при извикване на функция и какво е адрес за връщане
- Как да гледаш рамките с GDB (`bt`, `info frame`, `x`) и картата на паметта с `/proc/self/maps`
- Защо препълването на стека е грешка и как се проявява

## Процесът е програма в движение
Файлът на диска е като рецепта в книга. Когато го пуснеш, операционната система го зарежда и започва готвенето: това е **процес (process)**. Един и същ файл може да е няколко процеса едновременно, всеки със собствена памет и собствено състояние.

Всеки процес вижда така наречената **виртуална памет**: голямо непрекъснато поле от адреси, което за програмата е изцяло нейно. Реално системата превежда тези адреси към истинската памет и пази различните процеси един от друг. Затова адресът `0x7ffe...` в твоята програма и същият адрес в моя означават различни неща.

Виртуалното поле не е равна пустиня. То е разделено на области с различни правила: къде може да се чете, пише или изпълнява.

| Област | Какво съдържа | Права | Кога се създава |
|---|---|---|---|
| Код (`.text`) | инструкциите на програмата | четене и изпълнение | при зареждане |
| Само за четене (`.rodata`) | низове като „Здравей“ | само четене | при зареждане |
| Данни (`.data`) | глобални с начална стойност | четене и запис | при зареждане |
| Нулирани (`.bss`) | глобални без начална стойност | четене и запис | при зареждане, нули |
| Стек (stack) | локални променливи и връзки между извикванията | четене и запис | расте и намалява сам |
| Купчина (heap) | паметта от `malloc` | четене и запис | по заявка |

Имената `.text`, `.data` и `.bss` са традиционни. Първото е кодът, второто и третото са глобалните данни, като `.bss` не заема място във файла, защото е само нули.

## Експериментът: къде е всичко
Ето програма, която печата адреса на различни неща:

```c
#include <stdio.h>
#include <stdlib.h>

int counter = 7;              /* глобална, с начална стойност */
int empty;                    /* глобална, без начална стойност */
const char *greeting = "Здравей";

void show(const char *label, void *p) {
    printf("%-14s %p\n", label, p);
}

int level2(int x) {
    int local2 = x * 2;
    show("local2 (стек)", &local2);
    return local2;
}

int level1(int x) {
    int local1 = x + 1;
    show("local1 (стек)", &local1);
    return level2(local1);
}

int main(void) {
    int local = 42;
    int *heap = malloc(sizeof *heap);
    *heap = 5;
    show("код: main", (void *)main);
    show("литерал", (void *)greeting);
    show("counter", &counter);
    show("empty", &empty);
    show("local (стек)", &local);
    show("heap", heap);
    int r = level1(3);
    printf("r=%d\n", r);
    free(heap);
    return 0;
}
```

Компилираме с `gcc -g -O0 -Wall -o mem mem.c`. Системата е Linux, затова по подразбиране адресите се разбъркват при всяко пускане (виж по-долу). За първия опит ги „замразяваме“ с `setarch -R`:

```
$ setarch -R ./mem
код: main   0x5555555552d1
литерал 0x555555556008
counter        0x555555558010
empty          0x555555558024
local (стек) 0x7fffffff6030
heap           0x5555555592a0
local1 (стек) 0x7fffffff6014
local2 (стек) 0x7fffffff5fe4
r=8
```

(Колоните не са подравнени, защото `%-14s` брои байтове, а българските букви са по два байта. Това е хубав пример как кирилицата в UTF-8 е различна от броя на символите.)

Прочети числата:
- Кодът (`main`) е в `0x5555555552d1`, а литералът „Здравей“, `counter` и `empty` са в същата група адреси `0x5555555...`. Това е самата програма, заредена в паметта.
- Купчината (`heap`) е веднага след нея: `0x5555555592a0`.
- Стекът е съвсем другаде: `0x7fffffff....`, в най-високите адреси.

И още нещо, което е лесно да пропуснеш: `local` е на `...6030`, `local1` е на `...6014`, а `local2` е на `...5fe4`. Всяко ново извикване отива **на по-нисък адрес**. Стекът расте надолу.

## Картата на паметта
Линукс показва регионите на живия процес във файла `/proc/self/maps` (за друг процес вместо `self` се слага номерът му). Програма, която чете собствената си карта, е най-лесният начин да я видиш:

```
$ setarch -R ./maps | cut -c1-110 | head -12
local=0x7fffffff5f6c heap=0x5555555592a0 main=0x555555555229
555555554000-555555555000 r--p 00000000 fe:00 1656050   /tmp/.../maps
555555555000-555555556000 r-xp 00001000 fe:00 1656050   /tmp/.../maps
555555556000-555555557000 r--p 00002000 fe:00 1656050   /tmp/.../maps
555555557000-555555558000 r--p 00002000 fe:00 1656050   /tmp/.../maps
555555558000-555555559000 rw-p 00003000 fe:00 1656050   /tmp/.../maps
555555559000-55555557a000 rw-p 00000000 00:00 0         [heap]
7ffff7c00000-7ffff7c28000 r--p 00000000 fe:00 12321271  /usr/lib/x86_64-linux-gnu/libc.so.6
7ffff7c28000-7ffff7db1000 r-xp 00028000 fe:00 12321271  /usr/lib/x86_64-linux-gnu/libc.so.6
...
7ffffffd6000-7ffffffff000 rw-p 00000000 00:00 0         [stack]
```

(Съкратен изход; пътят и колоната за файла са орязани.) Нашият код `main` (`...5229`) е в реда с права `r-xp`: четене и изпълнение, но не запис. Променливата `local` (`...5f6c`) е в реда `[stack]`, в областта `7ffffffd6000-7ffffffff000` с права `rw-p`. Купчината е в `[heap]`. Освен това виждаш и стандартната библиотека `libc.so.6`, заредена в паметта на същия процес.

Ако имаш инсталиран `pmap`, командата `pmap <номер>` показва подобна, по-кратка карта на живия процес.

Колоната с буквите значи: `r` четене, `w` запис, `x` изпълнение, `p` частна област. Забележи, че областта на кода не е за запис, а областта на данните не е за изпълнение. Това е важна защита: данните не могат да се вземат за код.

## Защо адресите се менят: ASLR
Ако пуснеш `./mem` без `setarch`, адресите са други при всяко пускане. Ето две пускания, само реда за `local` и `heap`:

```
local (стек) 0x7ffec22e05a0      heap 0x56459cc8d2a0
local (стек) 0x7ffc18000f90      heap 0x55ae194332a0
```

Това се нарича **ASLR** (разбъркване на адресното пространство). Системата нарочно мести стека, купчината и библиотеките, за да не може злонамерен код да разчита на твърди адреси. Окончанието `...2a0` на купчината остава същото, защото се мести цяла страница, а не отделни байтове. За нас от това следва важен практически извод: **никога не записвай адреси от един пуск като константи** и когато сравняваш изходи, ползвай `setarch -R` или GDB, който ASLR го изключва.

## Купчината: паметта по заявка
Стекът се управлява сам. Купчината е различна: ти искаш парче с `malloc`, а когато свършиш, го връщаш с `free`. Процесът не вижда нищо между тези две команди; грижата е твоя.

```
$ setarch -R ./grow
x=0x5555555592a0 y=0x5555555592c0
```

Две поредни `malloc(4)` дават адреси на 32 байта един от друг, макар да искаме по 4. Всяко парче носи служебна информация и се подравнява. Не разчитай на точните числа, а на идеята: купчината расте нагоре към по-високите адреси, а стекът надолу. Между тях има много празно място.

Размерите на `.text`, `.data` и `.bss` на готов файл се виждат с командата `size`:

```
$ size mem
   text	   data	    bss	    dec	    hex	filename
   2421	    640	      8	   3069	    bfd	mem
```

`bss` е 8 байта: двете глобални променливи (`empty`, и още една, която е вътрешна за програмата). Командата `nm mem` потвърждава: `counter` е с буква `D` (данни), а `empty` е с `B` (bss). Това е връзката с променливите, които зададе в C.

## Стекова рамка: какво става при извикване
Когато една функция вика друга, процесорът трябва да запомни къде да се върне. Представи си, че четеш книга, и те прекъсват: слагаш тетрадка с номера на страницата. Този номер е **адресът за връщане (return address)**.

Инструкцията `call` слага адреса за връщане в стека и скача във функцията. Функцията си подрежда **рамка (stack frame)**: запазва стария `rbp`, прави нов и заделя място за локалните променливи. Накрая `ret` взема адреса от стека и се връща.

Нека видим това на живо с GDB в пакетен режим. Поставяме спиране в `level2` и пускаме:

```
$ gdb -q -batch -ex 'break level2' -ex run -ex bt -ex 'info frame' ./mem
Breakpoint 1, level2 (x=4) at mem.c:12
#0  level2 (x=4) at mem.c:12
#1  0x000055555555527b in level1 (x=3) at mem.c:21
#2  0x0000555555555365 in main () at mem.c:34
Stack level 0, frame at 0x7fffffff6000:
 rip = 0x5555555551ee in level2 (mem.c:12); saved rip = 0x55555555527b
 called by frame at 0x7fffffff6030
 Arglist at 0x7fffffff5ff0, args: x=4
 Locals at 0x7fffffff5ff0, Previous frame's sp is 0x7fffffff6000
 Saved registers:
  rbp at 0x7fffffff5ff0, rip at 0x7fffffff5ff8
```

(Съкратено; пропуснати са редове за версията и библиотеките.) Команда `bt` (backtrace) показва веригата от извиквания: `level2` е извикана от `level1`, а тя от `main`. Това е същата верига, която виждаш в съобщенията за грешки.

В `info frame` виж реда `saved rip = 0x55555555527b`: това е адресът, на който `level2` ще се върне, и той съвпада с адреса в `#1` в `bt`. Редът `rbp at ...5ff0, rip at ...5ff8` показва, че запазеният `rbp` и адресът за връщане лежат един до друг в стека.

Можем да ги прочетем директно с `x` (examine):

```
(gdb) print $rbp
$3 = (void *) 0x7fffffff5ff0
(gdb) x/4gx $rbp
0x7fffffff5ff0:	0x00007fffffff6020	0x000055555555527b
0x7fffffff6000:	0x00007fffffff6020	0x00000003555551dc
```

`x/4gx` значи „покажи 4 числа по 8 байта (giant) в шестнадесетичен вид“. Първото число на адрес `...5ff0` е запазеният `rbp` на `level1`. Второто е `0x55555555527b`: адресът за връщане. Същият, който видяхме в `bt`. Изгледът на една рамка:

```
по-високи адреси
   ...                 рамка на level1
   0x7fffffff6000  --- (дъното на рамката на level2)
   ...5ff8:  адрес за връщане  0x55555555527b
   ...5ff0:  запазен rbp       0x7fffffff6020   <- rbp сочи тук
   ...5fe4:  local2 (rbp - 12)
   ...5fd0:  rsp (върхът)
по-ниски адреси
```

Забележи `local2` на `...5fe4`: това е точно `rbp - 12`, както адресът, който програмата отпечата. Командата `x/s greeting` показва низа от областта само за четене, а `x/2i $rip` показва следващите две инструкции. С `set disassembly-flavor intel` GDB превключва към познатия ни синтаксис.

## Препълване на стека
Областта на стека е ограничена; на тази система границата е 8 MB (`ulimit -s` казва `8192` килобайта). Ако една функция вика себе си без край, всяка рамка отнема място и стекът свършва. Ето програма, която нарочно прави това (това е грешка, а не техника):

```c
void down(long depth) {
    char pad[100];
    pad[0] = (char)depth;
    if (depth % 20000 == 0) { fprintf(stderr, "глъбина %ld\n", depth); }
    down(depth + 1);
    pad[1] = pad[0];
}
```

```
$ ./rec 2>&1 | tail -3
глъбина 20000
глъбина 40000
код: 139
```

Процесът е прекратен със сигнал SIGSEGV (код 139 = 128 + 11) след около 40 000 – 60 000 рамки. Тази грешка се нарича **препълване на стека (stack overflow)**. Тук е предсказуема и сравнително безобидна: програмата просто пада. По-лошото е друго: ако програма записва данни **извън границите на локален масив**, тя може да презапише съседни неща в рамката, включително адреса за връщане. Затова C кодът трябва да проверява размерите, а компилаторите добавят защитни стойности (stack protector), каквито се виждат в началото на `level2`, където GDB ни показва инструкция с `%fs:0x28`. Как да пишеш безопасен код, се учи с проверки на граници и със санитайзерите от модул 3.

За ИИ и обратния инженеринг този урок е основата: когато четеш чужд код в дебъгер, веригата `bt` и картата на паметта ти казват къде се намираш. Повече за това има в курса `reverse-engineering`.

## Стъпка по стъпка
1. Запиши `mem.c`, компилирай с `-g -O0`.
2. Пусни програмата два пъти без `setarch` и сравни адресите на `local` и `heap`. Какво се променя?
3. Пусни я със `setarch -R` и подреди адресите на `main`, `counter`, `empty`, `heap`, `local` от най-ниския към най-високия.
4. Пусни `gdb -q ./mem`, напиши `break level2`, `run`, `bt`, `info frame`.
5. Изведи `x/4gx $rbp` и намери адреса за връщане. Сравни го с `bt`.
6. Напиши малка програма, която чете и печата първите няколко реда на `/proc/self/maps`, и посочи в нея реда на стека и на купчината.

## Пример от практиката
Да кажем, че Георги пише програма, която пада със SIGSEGV и не знае къде. Пуска я в GDB, чака сриването и пише `bt`. Вижда, че падането е дълбоко в рекурсивна функция, а верига от хиляди еднакви редове показва, че тя не спира. Намира липсващото условие за край, добавя го и проблемът изчезва. Без познанието за рамките `bt` би бил просто купчина редове.

## Чести грешки
- **Връщане на адрес на локална променлива.** След `return` рамката е свободна и адресът вече не е твой. Върни стойност или използвай `malloc`.
- **Забравено `free`.** Купчината не се чисти сама: програмата изтича памет. Санитайзерът от модул 3 хваща това.
- **Огромни локални масиви.** `int big[10000000]` е 40 MB и препълва стека още при влизане във функцията. Големите данни се заделят в купчината.
- **Рекурсия без базов случай.** Всяко извикване е нова рамка; без край стекът свършва.
- **Разчитане на твърди адреси.** Поради ASLR адресите се менят. Използвай имена и символи, не числа.
- **Бъркане на `.data` и `.bss`.** Промяната на начална стойност от `0` на `7` мести променливата от едната област в другата. Това е нормално.

## Упражнение
Напиши програма, която печата адресите на: функция, `static` променлива в нея, локална променлива, низов литерал, парче от `malloc` и по-голямо парче (например 1 000 000 байта).

Критерии за успех:
- Подреждаш адресите и казваш за всеки в коя област е.
- Показваш с `setarch -R`, че подредбата е една и съща при всяко пускане.
- Обясняваш с `/proc/self/maps` в коя област влиза всеки адрес.
- Със GDB показваш верига `bt` от поне три нива и намираш адреса за връщане с `x`.
- Обясняваш с две изречения защо стекът расте надолу, а купчината нагоре, и защо това не бива да се приема за закон на природата за всяка система.

## Бърза справка
```
setarch -R ./prog                  # изключи ASLR за един пуск
gdb -q ./prog                      # дебъгер
  break име / run / bt / up / down
  info frame / info registers rip rsp rbp
  x/4gx $rbp      x/s указател      x/2i $rip
  info proc mappings
cat /proc/self/maps                # карта на паметта (на самата команда)
size ./prog     nm ./prog          # размери и символи
ulimit -s                          # размер на стека в KB
```

## Обобщение
Работещата програма е процес с виртуална памет, разделена на код, данни, стек и купчина. Кодът е само за четене и изпълнение, глобалните данни са в `.data` и `.bss`, а `malloc` дава парчета от купчината. Стекът пази рамка за всяко извикване: запазен `rbp`, адрес за връщане и локални променливи, като расте към по-ниски адреси. GDB и `/proc/self/maps` ти позволяват да видиш всичко това със собствените си очи. Тази картина ще ти трябва във всяка следваща тема, която докосва паметта.

## Бележки за видеото
- Пусни `mem` два пъти без `setarch` и сравни адресите, после със `setarch -R`.
- Нарисувай картата на паметта и постави адресите на правилните места.
- Покажи `/proc/self/maps` и маркирай `[heap]` и `[stack]`.
- В GDB направи `break level2`, `bt`, `info frame` и `x/4gx $rbp`; свържи адреса за връщане с `bt`.
- Покажи `./rec` и сриването със SIGSEGV.
- Спомени курса `reverse-engineering` като продължение.
