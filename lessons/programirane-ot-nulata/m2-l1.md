> **Цел на урока:** да разделяш кода на собствени модули и пакети, да ползваш чужди библиотеки и да държиш зависимостите на всеки проект в отделна виртуална среда.

## Какво ще научиш
- Как работи `import` и къде Python търси модулите
- Какво е модул, какво е пакет и за какво служи `if __name__ == "__main__"`
- Как се създава виртуална среда с `venv` и защо е нужна
- Как се инсталира библиотека с `pip` и как се записват зависимостите във `requirements.txt`
- Как да разчиташ най-честите грешки при импорт

## Защо кодът се дели на файлове

Представи си кухня, в която всичко е в един голям чекмедже: ножове, подправки, кърпи, батерии. Готвиш, но половината време търсиш. Нормалната кухня има отделни чекмеджета и всяко има етикет. Със Python е същото: когато програмата ти порасне до няколкостотин реда, един файл става неудобен.

Затова кодът се разделя на **модули (modules)**. Модулът е просто файл с разширение `.py`, а името му е името на файла без разширението. Файлът `calc.py` е модул `calc`. Влизаш в него с `import`, когато ти трябва нещо от него.

Групата от модули в една папка се нарича **пакет (package)**. Пакетът е чекмеджето, а модулите са нещата в него. Ето малък проект за разходи, който ще ползваме в целия урок:

```
proekt/
├── main.py
└── expenses/
    ├── __init__.py
    └── calc.py
```

Файлът `expenses/__init__.py` показва на Python, че папката е пакет. В него може да няма нищо, а може да има кратко описание. Нашият съдържа само един ред с текст.

Ето `expenses/calc.py`:

```python
def total(amounts):
    return sum(amounts)

def average(amounts):
    return total(amounts) / len(amounts)

print("зареждам calc, __name__ =", __name__)

if __name__ == "__main__":
    print("пуснат директно:", total([12.5, 7.5]))
```

А ето `main.py`, който ползва пакета:

```python
from expenses.calc import total, average

print(total([10, 20, 5.5]), average([10, 20, 5.5]))
```

Пускаме го от папката `proekt`:

```
$ python3 main.py
зареждам calc, __name__ = expenses.calc
35.5 11.833333333333334
```

Забележи реда „зареждам calc“. Той се появи, макар че не сме викали нищо от `calc` изрично. Това е важно свойство: **при първия `import` Python изпълнява целия файл отгоре надолу.** Функциите се дефинират, а всичко останало (като `print`) се изпълнява веднага.

## Начини за импортиране

Има няколко форми на `import` и всяка има своето място. В таблицата са най-често срещаните.

| Запис | Какво прави | Как го ползваш |
|---|---|---|
| `import expenses.calc` | Зарежда модула, името остава с пътя | `expenses.calc.total(...)` |
| `from expenses.calc import total` | Взема само една функция | `total(...)` |
| `from expenses import calc` | Взема модула от пакета | `calc.total(...)` |
| `import expenses.calc as c` | Дава кратък псевдоним | `c.total(...)` |
| `from expenses.calc import *` | Взема всичко | Избягвай го |

Последната форма е подвеждаща за начинаещи. Тя пълни пространството на имената с неизвестно количество неща и после не знаеш откъде идва дадено име. По-добре винаги изреждай точно какво вземаш.

Стандартната библиотека на Python е същият механизъм. Когато в предишния урок пишеше `import csv`, Python намери вграден модул и го зареди по същия начин.

## Какво значи `__name__ == "__main__"`

Гледай внимателно изхода на трите начина за пускане на `calc.py`:

```
$ python3 main.py
зареждам calc, __name__ = expenses.calc

$ python3 expenses/calc.py
зареждам calc, __name__ = __main__
пуснат директно: 20.0

$ python3 -m expenses.calc
зареждам calc, __name__ = __main__
пуснат директно: 20.0
```

Всеки модул има вградена променлива `__name__`. Ако файлът е **импортиран**, `__name__` е името на модула (`expenses.calc`). Ако е **пуснат директно**, `__name__` е текстът `"__main__"`.

Условието `if __name__ == "__main__":` значи „изпълни това само когато файлът е стартиран, а не когато някой го импортира“. Това е най-удобното място за кратка проба на модула или за входната точка на програмата. Така един файл може да бъде едновременно библиотека и програма.

Третата форма, `python3 -m expenses.calc`, пуска модул по неговото име в пакета. Тя е полезна, когато модулът импортира други части от същия пакет, защото Python знае откъде да ги вземе.

## Къде Python търси модулите

Когато напишеш `import expenses.calc`, Python не гадае. Той обхожда списък от папки, който се пази в `sys.path`, и взема първото съвпадение. В този списък най-отпред стои папката на скрипта, който стартираш. Затова `main.py` намира пакета `expenses`: двете са в една папка. Следват папките на стандартната библиотека и папката `site-packages`, където се инсталират външните библиотеки.

Можеш да го видиш сам:

```python
import sys
print(sys.path)
```

Ако назовеш свой файл `csv.py`, `json.py` или `random.py`, той ще **засенчи** стандартния модул със същото име, защото папката на скрипта е първа в списъка. Тогава `import csv` ще зареди твоя файл и ще получиш странни грешки. Не давай на собствените си файлове имена на стандартни модули.

## Външни библиотеки и `pip`

Стандартната библиотека е голяма, но не покрива всичко. За другото има хиляди готови пакети, които други хора са публикували. Инструментът, който ги сваля и инсталира, се казва **pip**. Идва заедно с Python.

Ето проблема. Ако инсталираш всичко на едно общо място, проектите започват да си пречат. Проект A иска версия 1 на една библиотека, проект B иска версия 2. Да ги имаш и двете едновременно в общото място е невъзможно. Освен това нищо не ти казва кой проект какво ползва.

Решението е **виртуалната среда (virtual environment)**. Това е отделна папка с копие на интерпретатора и собствено място за пакети. Всеки проект си има своя среда. Аналогията е с кутии за инструменти: електротехникът и дърводелецът не ползват една кутия, макар да работят в една къща.

## Стъпка по стъпка

1. **Влез в папката на проекта** и създай средата:

   ```
   $ python3 -m venv .venv
   ```

   Името `.venv` е общоприето. Точката в началото я прави скрита папка на Linux и macOS. На Windows командата обикновено е `py -m venv .venv` или `python -m venv .venv`, в зависимост от инсталацията.

2. **Погледни какво е създадено.** В Linux:

   ```
   $ ls .venv
   bin  include  lib  lib64  pyvenv.cfg
   $ ls .venv/bin
   Activate.ps1  activate  activate.csh  activate.fish  pip  pip3  pip3.13  python  python3  python3.13
   ```

   На Windows вместо `bin` папката се казва `Scripts`.

3. **Провери, че средата е празна.** Всяка нова среда започва само с `pip`:

   ```
   $ .venv/bin/pip list
   Package Version
   ------- -------
   pip     26.2.2
   ```

   Номерът на версията при теб ще е друг.

4. **Активирай средата** (по желание). На Linux и macOS: `source .venv/bin/activate`. На Windows в PowerShell: `.venv\Scripts\Activate.ps1`. Пред командния ред се появява `(.venv)`. Активирането само слага папката на средата най-отпред в пътя за изпълнение. Можеш изобщо да не го правиш, ако викаш `.venv/bin/python` директно, както правим по-долу. Така няма двусмислие коя среда ползваш.

5. **Инсталирай библиотека.** Ще вземем `colorama`, малка библиотека за цветен текст в терминала:

   ```
   $ .venv/bin/pip install colorama
   Installing collected packages: colorama
   Successfully installed colorama-0.4.6
   ```

   Изходът в началото съдържа още редове за свалянето; тук е съкратен. Версията при теб може да е по-нова.

6. **Използвай я.** Файл `colors.py`:

   ```python
   from colorama import Fore, Style
   print(Fore.GREEN + "Остават 42,50 лв." + Style.RESET_ALL)
   ```

   Пуснат с интерпретатора на средата, той работи.

7. **Запиши зависимостите.** Командата `pip freeze` изброява всичко инсталирано с точните версии:

   ```
   $ .venv/bin/pip freeze | tee requirements.txt
   colorama==0.4.6
   ```

   Файлът `requirements.txt` е „рецептата“ на проекта.

8. **Пресъздай средата от рецептата.** Колега (или ти след година, на нов компютър) прави нова среда и инсталира от файла:

   ```
   $ python3 -m venv .venv2
   $ .venv2/bin/pip install -r requirements.txt
   Successfully installed colorama-0.4.6
   ```

9. **Изключи средата от Git.** Самата папка `.venv` не се качва в хранилището: тя е голяма, зависи от машината и може да се създаде наново. Във `.gitignore` напиши:

   ```
   .venv/
   __pycache__/
   ```

   В хранилището остава само `requirements.txt`.

## Изолацията в действие

Най-ясното доказателство, че средата е отделна, е това. На тази машина системният Python вижда `colorama`, а свежата среда не го вижда:

```
$ python3 -c "import colorama; print('системният python вижда colorama', colorama.__version__)"
системният python вижда colorama 0.4.6

$ .venv/bin/python -c "import colorama"
ModuleNotFoundError: No module named 'colorama'
```

Втората команда беше пусната преди инсталацията в средата. Средата не наследява пакетите на системата, освен ако изрично не го поискаш. Затова е чиста и предвидима. След `pip install` командата вече работи, а в `.venv2` библиотеката се оказа физически в собствената ѝ папка `site-packages`.

Забележка за по-старите примери в интернет: понякога се споменава `pip install` без `venv`. На някои дистрибуции на Linux системният Python е защитен и `pip` отказва да пише в него. Това е нормално и е още една причина да ползваш виртуална среда.

## Какво казва `pip` при грешка

Ако името на пакета е сгрешено или го няма, `pip` казва ясно:

```
$ .venv/bin/pip install no-such-package-xyz-123
ERROR: Could not find a version that satisfies the requirement no-such-package-xyz-123 (from versions: none)
ERROR: No matching distribution found for no-such-package-xyz-123
```

Ако нямаш интернет, ще видиш подобна грешка заради неуспешна връзка. Тогава инсталацията не е възможна и трябва да проверим мрежата, а не кода.

## Пример от практиката

Да кажем, че правиш две малки програми. Първата е инструмент за обработка на разходи с `colorama`. Втората е скрипт, който зарежда данни от уеб услуга и иска друга библиотека. След месец искаш да обновиш библиотеката във втората, но първата почва да се чупи.

Ако и двете живеят в една обща среда, обновяването засяга и двете. Ако всяка има своя `.venv` и свой `requirements.txt`, обновяваш само там, където трябва, и записът във файла ти казва точно коя версия работи. Освен това, когато някой друг иска да пусне програмата ти, му даваш хранилището и една команда `pip install -r requirements.txt`.

За ИИ-пътеките това е ежедневие: библиотеките за работа с модели се обновяват бързо и често си пречат помежду си. Курсовете „Работа с ИИ“ и „ИИ агенти и автоматизация“ ще разчитат на отделна среда за всеки проект.

## Чести грешки

- **`ModuleNotFoundError: No module named 'expenses.missing'`** – името е сгрешено или файлът не е на очакваното място. Провери правописа, дали папката има `__init__.py` и дали стартираш от правилната папка. Пример за изход: последният ред на трасировката съдържа точното име, което Python не намери.
- **Инсталираш с един Python, пускаш с друг.** `pip install` отива в средата на конкретния интерпретатор. Най-сигурният запис е `python3 -m pip install ...`, защото е вързан с интерпретатора пред него. Можеш да провериш `python3 -m pip --version`, който показва в коя папка работи `pip`.
- **Файл с име като стандартен модул.** `csv.py`, `random.py`, `json.py` засенчват истинските. Преименувай ги.
- **Забравена активация.** Мислиш, че си в средата, а си в системния Python. Провери с `python3 -c "import sys; print(sys.prefix)"`: в среда пътят сочи към папката `.venv`.
- **Качена в Git папка `.venv`.** Тя не е част от кода. Добави я във `.gitignore` преди първия къмит.
- **`requirements.txt` не е обновен.** Инсталирал си нова библиотека и не си пуснал `pip freeze` отново. Следващият човек няма да може да пусне програмата.
- **Безкраен цикъл от импорти.** Модул A импортира B, а B импортира A. Ако се случи, премести общото в трети модул.

## Упражнение

Направи проект „разходи“ със собствена среда.

1. Създай папка `proekt` с пакета `expenses` и два модула: `calc.py` (функции `total` и `average`) и `report.py` (функция `format_line(name, amount)`, която връща текст като `храна: 12.50 лв.`).
2. В `main.py` импортирай функциите и от трите модула (включително от стандартната библиотека, например `statistics`) и изведи малък отчет.
3. В `calc.py` сложи защита с `if __name__ == "__main__":` и кратка проба вътре.
4. Създай среда `.venv`, инсталирай една библиотека по избор (например `colorama`), използвай я в `report.py` и запиши `requirements.txt`.
5. Изтрий `.venv`, направи я наново и инсталирай от `requirements.txt`.
6. Напиши `.gitignore`, който изключва `.venv/` и `__pycache__/`.

Критерии за проверка:
- `python3 main.py` печата отчета, без да печата проби от модулите.
- `python3 -m expenses.calc` печата пробата.
- В свежата среда `import` на библиотеката не работи преди `pip install` и работи след него.
- `requirements.txt` съдържа библиотеката с точна версия.
- Можеш да обясниш с една дума на човек защо не качваш `.venv`.

## Бърза справка

| Задача | Команда |
|---|---|
| Създай среда | `python3 -m venv .venv` |
| Активирай (Linux/macOS) | `source .venv/bin/activate` |
| Активирай (Windows PowerShell) | `.venv\Scripts\Activate.ps1` |
| Инсталирай пакет | `python3 -m pip install име` |
| Списък на пакетите | `python3 -m pip list` |
| Запиши версиите | `python3 -m pip freeze > requirements.txt` |
| Инсталирай от файл | `python3 -m pip install -r requirements.txt` |
| Пусни модул от пакет | `python3 -m пакет.модул` |
| Само при директно пускане | `if __name__ == "__main__":` |

## Обобщение

Модулът е файл, пакетът е папка с модули и `import` изпълнява файла при първото зареждане. Условието `if __name__ == "__main__"` отделя кода за директно пускане от кода за импортиране. Всеки проект получава собствена виртуална среда, в която `pip` инсталира библиотеки, без да засяга другите проекти. Файлът `requirements.txt` пази точните версии, така че средата да може да се възстанови, а папката `.venv` остава извън Git.
