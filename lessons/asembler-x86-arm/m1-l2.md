> **Цел на урока:** да напишеш функция на асемблер и да я извикаш от C, да извикаш `printf` от асемблер и да четеш кода, който компилаторът генерира.

## Какво ще научиш
- Как се пише функция на NASM, която C вижда като обикновена функция
- Как се свързват обектни файлове от NASM и GCC
- Как се вика `printf` от асемблер и защо подравняването на стека има значение
- Как да гледаш асемблера на компилатора с `gcc -S` и `objdump`
- Каква е разликата между кода при `-O0` и `-O2`

## Един договор, два езика

В предишния урок видя, че конвенцията System V AMD64 определя къде са аргументите и резултатът. Точно това я прави мост между езиците: C не знае на какъв език е написана функцията, стига тя да спазва правилата. Следователно можеш да напишеш функция на асемблер, да я компилираш с NASM до обектен файл и да я свържеш с програма на C. Обратното също работи: асемблерът вика всичко от стандартната библиотека на C.

Връзката между двете страни се прави чрез **имена на символи** (symbols). Директивата `global име` казва на NASM, че този етикет е видим за линкера. Директивата `extern име` казва, че етикетът е дефиниран другаде. В C функцията се декларира с прототип, а в асемблера – само с етикет. Типовете не се проверяват никъде: ако прототипът на C и регистрите в асемблера не съвпадат, получаваш грешен резултат без предупреждение. Затова коментарът над функцията с прототипа е част от правилния стил.

## Стъпка по стъпка: сума на масив

**Стъпка 1. Прототип.** Искаме функция на C-страната да изглежда така:

```c
long sum_array(const long *a, size_t n);
```

Според конвенцията `a` е в `rdi`, `n` е в `rsi`, а резултатът се връща в `rax`.

**Стъпка 2. Функцията на асемблер.** Запиши като `sum_array.asm`:

```nasm
; long sum_array(const long *a, size_t n)  - a в rdi, n в rsi
global sum_array
section .text
sum_array:
    xor eax, eax            ; сума = 0
    xor ecx, ecx            ; i = 0
.next:
    cmp rcx, rsi
    jae .done               ; i >= n -> край
    add rax, [rdi + rcx*8]
    inc rcx
    jmp .next
.done:
    ret
section .note.GNU-stack noexec
```

Обърни внимание на три неща. Адресът `[rdi + rcx*8]` е „основа плюс индекс по осем байта“ – подробно за този запис ще говорим в следващия модул. Функцията променя само `rax` и `rcx`, и двата са caller-saved, така че не е нужно да запазваме нищо. А последният ред (`section .note.GNU-stack noexec`) казва на линкера, че програмата не изисква изпълним стек; без него `ld` в тази среда предупреждава „missing .note.GNU-stack section implies executable stack“.

Проверката `jae` е беззнакова, защото `n` е `size_t`. Така `n = 0` не влиза в цикъла.

**Стъпка 3. Програмата на C.** Запиши като `main.c`:

```c
#include <stdio.h>
#include <stddef.h>

long sum_array(const long *a, size_t n);

int main(void)
{
    long data[] = {10, 20, 30, 40, 50};
    size_t n = sizeof data / sizeof data[0];
    printf("Сума: %ld\n", sum_array(data, n));
    printf("Празен масив: %ld\n", sum_array(data, 0));
    return 0;
}
```

**Стъпка 4. Сглоби и свържи.** За да получиш правилен изпълним файл с библиотеката на C, остави `gcc` да свърже всичко (то знае пътищата и стартовия код):

```
$ nasm -f elf64 -g -F dwarf -Wall sum_array.asm -o sum_array.o
$ gcc -g -Wall -Wextra -o prog main.c sum_array.o
$ ./prog
Сума: 150
Празен масив: 0
```

Двете примерни стойности – 150 за масива и 0 за празния – съвпадат с очакваното.

**Стъпка 5. Провери в GDB.** Спри на входа на функцията и погледни аргументите:

```
$ gdb -q ./prog
(gdb) set disassembly-flavor intel
(gdb) break sum_array
(gdb) run
Breakpoint 1, sum_array () at sum_array.asm:5
(gdb) info registers rdi rsi
rdi            0x7fffffff6010      140737488314384
rsi            0x5                 5
(gdb) x/5gd $rdi
0x7fffffff6010:	10	20
0x7fffffff6020:	30	40
0x7fffffff6030:	50
```

В `rdi` е адресът на масива от `main`, а в `rsi` – броят 5. Командата `x/5gd` показва пет осембайтови десетични числа. Точно това очакваш.

## printf от асемблер

Да кажем, че искаш да форматираш число и текст без да пишеш собствено превръщане. Можеш да извикаш `printf` от libc, но първо трябва да спазиш още две правила: подравняването на стека и броя на векторните регистри.

```nasm
default rel
extern printf
global main

section .rodata
fmt     db "Число: %d, текст: %s", 10, 0
word_   db "асемблер", 0

section .text
main:
    sub rsp, 8              ; подравняване: при влизане rsp е 8 по модул 16
    lea rdi, [fmt]
    mov esi, 42
    lea rdx, [word_]
    xor eax, eax            ; 0 векторни регистъра за varargs
    call printf wrt ..plt
    add rsp, 8
    xor eax, eax            ; return 0
    ret
section .note.GNU-stack noexec
```

```
$ nasm -f elf64 hello_c.asm -o hello_c.o && gcc -o hello_c hello_c.o
$ ./hello_c
Число: 42, текст: асемблер
```

Тук функцията се казва `main`, защото стартовият код на C (`crt1`) вика `main`, а не `_start`. Накратко за ключовите детайли:

- **`default rel`** прави адресирането относително на `rip`, което е нужно на съвременните позиционно независими изпълними файлове.
- **`call printf wrt ..plt`** вика функцията през таблицата PLT, защото `printf` е в споделена библиотека.
- **`xor eax, eax`** задава, че `printf` (функция с променлив брой аргументи) не получава аргументи във векторни регистри. Ако подаваш `double`, там слагаш броя на ползваните `xmm`.
- **`sub rsp, 8`** подравнява стека. При влизане в `main` върху стека е адресът за връщане, затова `rsp` е „16 + 8“. Едно `sub rsp, 8` връща до кратно на 16.

### Какво става без подравняване

В тази среда версията на `printf` с `%d` и `%s` оцеляваше и без `sub rsp, 8`, защото не стига до инструкция, която изисква подравняване. Не разчитай на това. Следната програма с `%f` показва проблема:

```nasm
main:
    ; sub rsp, 8   <- липсва
    lea rdi, [fmt]
    movsd xmm0, [val]
    mov eax, 1              ; един векторен регистър
    call printf wrt ..plt
```

```
$ ./fl_ok
3.14
$ ./fl_bad
Segmentation fault
```

В GDB причината се вижда веднага:

```
Program received signal SIGSEGV, Segmentation fault.
=> 0x7ffff7c60136 <__printf+54>:	movaps %xmm0,-0x80(%rbp)
```

Библиотеката стига до `movaps` (запис на 16 байта, който изисква подравнен адрес) и процесорът отказва. Грешката е в **твоя** код, но се проявява в чужд – най-трудната комбинация. Ако срещнеш срив в `printf`, `puts` или `malloc`, първо провери подравняването.

## Да четеш какво генерира компилаторът

Най-добрият учител по асемблер е самият компилатор. Вземи функция на C:

```c
long sum_array(const long *a, unsigned long n)
{
    long s = 0;
    for (unsigned long i = 0; i < n; i++)
        s += a[i];
    return s;
}
```

Командата `gcc -S` дава асемблерен текст. По подразбиране синтаксисът е AT&T (`movq %rdi, -24(%rbp)`, получателят е втори). Опцията `-masm=intel` го превключва към същия вид, който пишем в NASM. Ето версията без оптимизация (`-O0`), съкратена:

```
sum_array:
	push	rbp
	mov	rbp, rsp
	mov	QWORD PTR -24[rbp], rdi
	mov	QWORD PTR -32[rbp], rsi
	mov	QWORD PTR -16[rbp], 0
	mov	QWORD PTR -8[rbp], 0
	jmp	.L2
.L3:
	mov	rax, QWORD PTR -8[rbp]
	lea	rdx, 0[0+rax*8]
	mov	rax, QWORD PTR -24[rbp]
	add	rax, rdx
	mov	rax, QWORD PTR [rax]
	add	QWORD PTR -16[rbp], rax
	add	QWORD PTR -8[rbp], 1
.L2:
	mov	rax, QWORD PTR -8[rbp]
	cmp	rax, QWORD PTR -32[rbp]
	jb	.L3
	mov	rax, QWORD PTR -16[rbp]
	pop	rbp
	ret
```

Всяка променлива живее в паметта и се зарежда и записва на всяка стъпка. Сравни с `-O2`:

```
sum_array:
	test	rsi, rsi
	je	.L4
	lea	rdx, [rdi+rsi*8]
	xor	eax, eax
.L3:
	add	rax, QWORD PTR [rdi]
	add	rdi, 8
	cmp	rdi, rdx
	jne	.L3
	ret
.L4:
	xor	eax, eax
	ret
```

Компилаторът е превърнал индекса в указател: вместо `a[i]` той движи `rdi` с 8 и сравнява с края `rdx`. Всичко е в регистри, цикълът е четири инструкции, а случаят `n = 0` е обработен отделно в началото. Нашият ръчен вариант също държи всичко в регистри, но проверява индекса във всяка итерация и ползва индексирано адресиране вместо движещ се указател. Това е добра причина да не гониш „по-бърз от компилатора“ ръчно, освен когато имаш конкретна причина (SIMD – в следващия модул).

За вече компилиран файл използвай `objdump`:

```
$ gcc -O2 -c cs.c -o cs.o
$ objdump -d -M intel cs.o
   0:	48 85 f6             	test   rsi,rsi
   3:	74 1b                	je     20 <sum_array+0x20>
   5:	48 8d 14 f7          	lea    rdx,[rdi+rsi*8]
   ...
  1c:	c3                   	ret
```

Така можеш да разгледаш и чужд обектен файл или изпълним файл без изходен код – основа на `reverse-engineering`.

## Пример от практиката

Да кажем, че имаш готова програма на C и искаш да замениш само най-горещата функция с асемблер. Подход:

1. Напиши функцията на C и тестове за нея (поне празен вход, един елемент, много).
2. Компилирай с `-O2 -S -masm=intel` и виж какво е направил компилаторът.
3. Ако имаш идея, която компилаторът не използва, напиши вариант на NASM.
4. Свържи двете версии под различни имена и сравни резултатите на едни и същи данни.
5. Измери времето (резултатите зависят от машината и са ориентировъчни).

Най-често ще откриеш, че компилаторът вече е направил добра работа. Ползата от асемблера не е винаги в скоростта – понякога е в контрола, а понякога е просто в знанието какво прави програмата ти.

## Чести грешки

- **Липсва `global`** – линкерът дава „undefined reference to `sum_array`“.
- **Грешни предположения за ширината на аргумента** – функция, която получава `int`, подава 32-битова стойност; горните 32 бита на `rdi` не са гарантирани. Ползвай `edi`, не `rdi`.
- **Връщане на резултат в друг регистър** – C чете само `rax` (за цели числа). Резултатът ти в `rbx` е загубен.
- **Развалени callee-saved регистри** – ако ползваш `rbx`, `rbp`, `r12`–`r15`, запази ги с `push`/`pop`.
- **Неподравнен стек преди `call`** – срив вътре в библиотека. Първо провери `rsp`.
- **Забравен `xor eax, eax` преди `printf`** – `al` се чете като брой векторни регистри; боклук там може да даде странно поведение.
- **Грешки при преместване (relocation)** – ако линкерът се оплаква при `-pie` изпълним файл, провери `default rel` и `wrt ..plt`.

## Упражнение

Напиши функция на асемблер `long max_array(const long *a, size_t n)`, която връща най-голямата стойност (приемай `n >= 1`), и тест на C.

Критерии:
1. Функцията е в отделен `.asm` файл и се сглобява с `-Wall` без предупреждения.
2. Тестът на C покрива масив с един елемент, с отрицателни числа и с най-голямото число в началото, в средата и в края.
3. Използваш знаково сравнение (`jl`/`jg`) и можеш да обясниш защо.
4. Сравняваш с `gcc -O2 -S -masm=intel` на същата функция на C и посочваш поне една разлика.
5. Допълнително: напиши програма на асемблер, която вика `printf` с твоя резултат.

## Бърза справка

| Нужда | Как |
|---|---|
| Функция, видима за C | `global име` и етикет `име:` |
| Функция от libc | `extern име` и `call име wrt ..plt` |
| Относително адресиране | `default rel` и `lea rdi, [етикет]` |
| Свързване на NASM и C | `nasm -f elf64 …` и `gcc -o prog main.c файл.o` |
| Подравняване преди `call` | `sub rsp, 8` при влизане в функция без други `push` |
| `printf` без плаващи числа | `xor eax, eax` |
| Асемблер на компилатора | `gcc -O2 -S -masm=intel файл.c -o -` |
| Дисасемблиране на обектен файл | `objdump -d -M intel файл.o` |
| Без изпълним стек | `section .note.GNU-stack noexec` |

## Обобщение

Конвенцията System V AMD64 позволява на C и асемблер да се викат взаимно: аргументите са в `rdi`, `rsi` и нататък, резултатът – в `rax`, а `global` и `extern` свързват имената. `gcc` свързва NASM обектния файл с програмата на C, а `printf` от асемблер изисква подравнен стек и правилно `al`. Опциите `gcc -S -masm=intel` и `objdump -d -M intel` показват какво прави компилаторът: при `-O0` всичко минава през паметта, при `-O2` – през регистри. Така можеш да учиш от компилатора и да разпознаваш шаблони в чужд код.

## Бележки за видеото
- Покажи `sum_array.asm` и `main.c` един до друг и свържи имената със стрелки.
- Изпълни трите команди за сглобяване и пусни `./prog`.
- В GDB спри в `sum_array` и покажи `rdi`, `rsi` и `x/5gd $rdi`.
- Пусни `fl_ok` и `fl_bad` и покажи ръчно `movaps` в GDB.
- Сложи `-O0` и `-O2` в два прозореца и маркирай цикъла в двата.
