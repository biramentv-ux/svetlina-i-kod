> **Цел на урока:** да сглобиш проект на C++ с CMake – библиотека, програма и тестове – и да го изграждаш и проверяваш с две команди, независимо от компилатора.

## Какво ще научиш
- какво прави CMake и защо не се пише `g++ a.cpp b.cpp c.cpp ...` на ръка;
- как се описват цели (targets): библиотека, изпълним файл, зависимости между тях;
- защо се строи в отделна папка и как се сменят вариантите (Debug, Release, санитайзъри);
- как се добавят тестове с CTest и как се чете провал;
- каква структура на папките е удобна за проект, който расте.

## Защо CMake
Когато имаш три файла, един ред за `g++` стига. При тридесет файлове, две библиотеки и тестове вече се нуждаеш от описание на проекта: кои файлове образуват коя част, коя част от коя зависи и с какви флагове се превежда. CMake е такъв описател. Той **не компилира сам**: чете `CMakeLists.txt` и генерира файлове за истинска система за изграждане (Make, Ninja, Visual Studio и други). Затова един и същи проект се строи на Linux, macOS и Windows.

Разликата е в начина на мислене. Не пишеш „компилирай с този флаг“, а описваш **цели** със свойства: „библиотеката `vec2` има тези заглавни файлове за потребителите си“. Всичко останало следва от това.

## Структура на проекта
За урока изградих малък проект `vec2` с вектор в равнината. Структурата е типична:

```
vec2/
  CMakeLists.txt
  include/vec2/vec2.hpp     # публични заглавни файлове
  src/vec2.cpp              # реализация
  app/main.cpp              # програма, която ползва библиотеката
  tests/
    CMakeLists.txt
    check.hpp               # мъничка помощна макро-проверка
    test_length.cpp
    test_normalize.cpp
```

Заглавните файлове са в `include/vec2/`, така че в кода пишеш `#include "vec2/vec2.hpp"`. Името на папката в пътя предпазва от сблъсък с чужди файлове със същото име.

## Главният CMakeLists.txt
```cmake
cmake_minimum_required(VERSION 3.20)
project(vec2 VERSION 0.1 LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)
set(CMAKE_CXX_EXTENSIONS OFF)
set(CMAKE_EXPORT_COMPILE_COMMANDS ON)

if(NOT CMAKE_BUILD_TYPE AND NOT CMAKE_CONFIGURATION_TYPES)
  set(CMAKE_BUILD_TYPE Release)
endif()

option(VEC2_SANITIZE "Включи AddressSanitizer и UBSan" OFF)
if(VEC2_SANITIZE)
  add_compile_options(-fsanitize=address,undefined -fno-omit-frame-pointer)
  add_link_options(-fsanitize=address,undefined)
endif()

add_library(vec2 src/vec2.cpp)
target_include_directories(vec2 PUBLIC include)
if(CMAKE_CXX_COMPILER_ID MATCHES "GNU|Clang")
  target_compile_options(vec2 PRIVATE -Wall -Wextra -Wpedantic)
endif()

add_executable(demo app/main.cpp)
target_link_libraries(demo PRIVATE vec2)

include(CTest)
if(BUILD_TESTING)
  add_subdirectory(tests)
endif()
```

Какво значи всяка част:
- `cmake_minimum_required` фиксира най-старата версия на CMake, която разбира файла; `project` дава име и казва, че проектът е само на C++;
- `CMAKE_CXX_STANDARD 20` и `CMAKE_CXX_EXTENSIONS OFF` искат чист ISO C++20 (`-std=c++20`, а не `-std=gnu++20`);
- `CMAKE_EXPORT_COMPILE_COMMANDS` пише файл `compile_commands.json`, който редакторите и инструментите за анализ ползват, за да знаят флаговете;
- `option(...)` е превключвател, който се задава от командния ред с `-D<ИМЕ>=ON`;
- `add_library` и `add_executable` създават цели;
- `target_include_directories(vec2 PUBLIC include)` е най-важният ред: `PUBLIC` означава, че пътят важи и за самата библиотека, и за всеки, който се свърже с нея. Затова `demo` и тестовете получават `include/` автоматично;
- `target_link_libraries(demo PRIVATE vec2)` казва „`demo` ползва `vec2`, но това е вътрешна подробност“;
- `include(CTest)` включва поддръжката на тестове и променливата `BUILD_TESTING`.

Предпочитай команди, които започват с `target_` (за конкретна цел), пред глобални като `include_directories` или `add_definitions`. Глобалните настройки се разливат върху всичко и после трудно се проследяват.

## Строеж в отделна папка
Винаги строй извън изходния код (out-of-source build). Генерираните файлове отиват в отделна папка, обикновено `build`, и изтриването ѝ връща проекта в чисто състояние.

```
cmake -S vec2 -B build
cmake --build build
```

`-S` е папката с изходния код, `-B` е папката за строежа. Реален изход (съкратен; тук е CMake 3.28 и g++ 13):

```
-- Configuring done
-- Generating done
[ 25%] Linking CXX static library libvec2.a
[ 25%] Built target vec2
[ 50%] Linking CXX executable demo
[ 50%] Built target demo
[ 75%] Linking CXX executable test_length
[100%] Linking CXX executable test_normalize
```

И програмата работи:

```
дължина: 5
единичен: (0.6, 0.8)
```

Командата `cmake --build` е една и съща, колкото и да е генераторът. В тази среда подразбиращият се е „Unix Makefiles“. Ако е инсталиран Ninja, можеш да поискаш `-G Ninja`: обикновено е по-бърз при частични прегенерирания. На Windows с Visual Studio се добавя `--config Release` към строежа, защото там конфигурацията се избира при строежа, а не при настройката. За паралелен строеж пиши `cmake --build build --parallel`.

## Варианти на строежа
Една и съща изходна папка може да има няколко папки за строеж едновременно:

```
cmake -S vec2 -B build-san -G Ninja -DCMAKE_BUILD_TYPE=Debug -DVEC2_SANITIZE=ON
cmake --build build-san
```

| Настройка | Ефект |
|---|---|
| `-DCMAKE_BUILD_TYPE=Debug` | без оптимизации, с отладъчна информация (за GDB) |
| `-DCMAKE_BUILD_TYPE=Release` | оптимизации, `-DNDEBUG` |
| `-DVEC2_SANITIZE=ON` | нашият превключвател за AddressSanitizer и UBSan |
| `-G Ninja` | избор на генератор |
| `-DBUILD_TESTING=OFF` | пропуска тестовете |

Забележка: на Windows с MSVC флагове като `-Wall` и `-fsanitize=address,undefined` са други. Затова предупрежденията са затворени в проверка на `CMAKE_CXX_COMPILER_ID`, а за MSVC се пише отделен клон (например `/W4`).

## Тестове с CTest
CTest е вграденият пускач на тестове. Тест е просто изпълнима програма, която връща 0 при успех и друго число при провал. Не ти трябва външна рамка, за да започнеш (GoogleTest, Catch2 и подобни са добър следващ избор, когато проектът порасне). В `tests/CMakeLists.txt`:

```cmake
add_executable(test_length test_length.cpp)
target_link_libraries(test_length PRIVATE vec2)
add_test(NAME length COMMAND test_length)
```

А самият тест ползва малко макро, което печата реда на провала и излиза с код 1:

```cpp
#define CHECK(cond) do { if (!(cond)) { \
    std::cerr << __FILE__ << ':' << __LINE__ << ": провал: " #cond << '\n'; \
    std::exit(1); } } while (0)

int main() {
    using namespace vec2;
    CHECK_NEAR(length({3, 4}), 5.0);
    CHECK_NEAR(length({0, 0}), 0.0);
}
```

Пускането е `ctest --test-dir build --output-on-failure`:

```
    Start 1: length
1/2 Test #1: length ...........................   Passed    0.01 sec
    Start 2: normalize
2/2 Test #2: normalize ........................   Passed    0.01 sec

100% tests passed, 0 tests failed out of 2
```

### Какво става при провал
Да махнем умишлено проверката за нулев вектор от `normalized`. Делението на нула дава NaN и вторият тест пропада:

```
2/2 Test #2: normalize ........................***Failed    0.00 sec
tests/test_normalize.cpp:7: провал: normalized({0, 0}).x == 0.0

50% tests passed, 1 tests failed out of 2

The following tests FAILED:
	  2 - normalize (Failed)
Errors while running CTest
```

(Пътят във файловата система е съкратен.) Точно това е смисълът: промяна на едното място не руши тихо другото. Полезни опции:

- `ctest -N` показва списъка без изпълнение;
- `ctest -R norm` пуска само тестовете, чието име съдържа „norm“;
- `ctest -j4` пуска тестове паралелно;
- `ctest --rerun-failed --output-on-failure` повтаря само пропадналите.

## Стъпка по стъпка: от нула до работещ проект
1. Създай папките `include/<име>/`, `src/`, `app/`, `tests/`.
2. Напиши библиотека с един публичен файл и една реализация; преди това в `CMakeLists.txt` сложи `add_library` и `target_include_directories(... PUBLIC include)`.
3. Добави `add_executable` за програмата и я свържи с `target_link_libraries`.
4. Включи `include(CTest)` и `add_subdirectory(tests)`; за всяка проверка направи малка програма и `add_test`.
5. Настрой и построй в `build`: `cmake -S . -B build`, после `cmake --build build`.
6. Пусни `ctest --test-dir build --output-on-failure`. Чак когато е зелено, продължавай.
7. Направи втора папка за строеж с `Debug` и санитайзъри и пусни същите тестове там.

## Пример от практиката
Да кажем, че пишеш малка библиотека за математика на векторите, която после ще ползваш в симулацията от проекта в края на курса. Вместо да я копираш в проекта, я държиш като отделна цел `vec2` с тестове. Когато променяш `normalized` или добавяш скаларно произведение, пускаш `ctest` и за секунди знаеш дали старото още работи. Ако по-късно друг проект поиска същата библиотека, ѝ добавяш `add_subdirectory(vec2)` и `target_link_libraries(... vec2)`. Заглавните файлове идват автоматично заради `PUBLIC`.

## Чести грешки
- **Строеж в изходната папка** – замърсява хранилището и спъва повторното настройване. Ползвай `-B build` и добави `build/` в `.gitignore`.
- **`include_directories` и глобални флагове** – после не се знае кой какво ползва. Предпочитай `target_*`.
- **Тест без `add_test`** – програмата се строи, но `ctest` не я знае и показва „No tests were found“.
- **Забравено `enable_testing()`/`include(CTest)` в главния файл** – `add_test` в поддиректорията тогава не се регистрира.
- **Сравняване на числа с плаваща запетая с `==`** – в тестовете ползвай допуск, както `CHECK_NEAR` по-горе.
- **Ръчно описани файлове с `file(GLOB ...)`** – новият файл не се забелязва, докато не пуснеш CMake отново. Изброявай файловете изрично, докато проектът е малък.
- **Смяна на `CMAKE_BUILD_TYPE` в стара папка** – ако нещо се обърка, изтрий кеша (`build/CMakeCache.txt`) или цялата папка.

## Упражнение
Сглоби проект с библиотека, програма и тестове:
1. библиотеката `textstats` предлага `std::size_t count_words(std::string_view)` и `std::string to_upper_ascii(std::string_view)`;
2. програмата чете ред от стандартния вход и печата броя думи;
3. най-малко три CTest теста: празен низ, няколко интервала, един вход с главни и малки букви;
4. вариант на строежа със санитайзъри.

Критерии:
- `cmake -S . -B build && cmake --build build && ctest --test-dir build` минава без ръчни стъпки;
- няма предупреждения при `-Wall -Wextra -Wpedantic`;
- пропаднал тест (който умишлено чупиш) се вижда ясно в изхода;
- `build/` не влиза в хранилището.

## Бърза справка
| Команда | Какво прави |
|---|---|
| `cmake -S . -B build` | настройва проекта |
| `cmake --build build --parallel` | строи |
| `ctest --test-dir build --output-on-failure` | пуска тестовете |
| `add_library(x src/x.cpp)` | цел-библиотека |
| `target_include_directories(x PUBLIC include)` | пътища за заглавни файлове |
| `target_link_libraries(app PRIVATE x)` | зависимост |
| `add_test(NAME n COMMAND prog)` | регистрира тест |

Същата идея работи и за проекти на C (в `project` се пише `LANGUAGES C`).

## Обобщение
CMake описва проекта чрез цели и зависимости, а не чрез флагове, и генерира файлове за Make, Ninja или Visual Studio. Строи се в отделна папка, а вариантите се избират с `-D` настройки. CTest пуска обикновени програми като тестове и показва кой е пропаднал. Така промените в кода са защитени и проектът остава преносим.
